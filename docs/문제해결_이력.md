# 문제 해결 이력

이 프로젝트를 만들면서 부딪힌 문제와 해결 과정을 모두 적은 기록이다.
몇 달 뒤 다시 보거나, 같은 환경을 처음 꾸리는 사람이 읽어도 이해되게 썼다.

**읽는 법**
- 각 항목은 같은 순서로 적었다: **증상**(실제로 본 화면·메시지) → **원인** → **해결**(명령·코드) → **교훈** → **관련**(파일·커밋).
- 커밋 번호는 `git show <번호>`로 그때 바뀐 내용을 볼 수 있다.
- 날짜는 모두 2026-10-04(한국 시간)이다. 1~2주차를 하루에 몰아서 진행했다.
- 분류
  - **A**: 노트북 환경 구축
  - **B**: Git 작업 흐름
  - **C**: 외부 프로그램 버전·배포
  - **D**: 측정·해석. 코드가 아니라 **판단이 틀렸던** 경우이며, 포트폴리오에서 가장 쓸모 있는 부분이다.
  - **E**: 기록 실수
  - **F**: 무시해도 되는 경고
  - **G**: 작업 환경의 제약

## A. 노트북 환경 구축

노트북 사양:
- 그래픽카드: RTX 5070 Laptop 8GB (Blackwell, CUDA 13.1, 드라이버 592.19)
- 메모리: RAM 24GB
- 운영체제: Windows 11 + WSL2 Ubuntu 24.04
- Docker: Docker Desktop이 아니라 **Ubuntu 안에 Docker 엔진을 직접 설치**한 구성

### A1. Windows 사용자 폴더 경로가 깨짐

- **증상:** WSL 메모리 설정 파일(`.wslconfig`)을 찾으려고 `cmd.exe /c 'echo %USERPROFILE%'`로 Windows 사용자 폴더를 얻었더니, 경로의 한글이 깨져 나와 그 폴더로 이동할 수 없었다.
- **원인:** Windows 사용자 이름이 한글이다. `cmd.exe`는 한글을 옛 인코딩(CP949)으로 내보내고, WSL은 UTF-8로 읽어서 글자가 깨진다.
- **해결:** cmd를 거치지 않고 WSL에서 직접 폴더 목록을 봤다.
  ```bash
  ls /mnt/c/Users/          # → (한글 사용자 이름)  Public  Default ...
  cat /mnt/c/Users/<사용자 이름>/.wslconfig
  ```
- **교훈:** 한글 사용자 이름은 Windows 도구를 거칠 때 자주 깨진다. 경로는 WSL 쪽에서 직접 확인한다.

### A2. WSL 메모리 부족

- **증상:** `free -h`로 보니 WSL이 쓸 수 있는 메모리가 약 11GB였다. 임베딩 모델, 벡터DB 5개, vLLM을 동시에 띄우기에는 빠듯하다.
- **원인:** 이미 있던 `.wslconfig`에 `memory=12GB`가 적혀 있었다. 숫자가 11GB로 보인 건 커널이 일부를 쓰기 때문이다.
- **해결:** 덮어쓰지 않고 그 줄만 고쳤다. 그런 다음 Windows PowerShell에서 WSL을 다시 시작했다.
  ```bash
  sed -i 's/^memory=.*/memory=16GB/' /mnt/c/Users/<사용자 이름>/.wslconfig
  ```
  ```powershell
  wsl --shutdown
  ```
- **교훈:** 설정 파일이 이미 있으면 통째로 덮어쓰지 말고 필요한 줄만 바꾼다. 다른 설정이 들어 있을 수 있다.

### A3. Docker 컨테이너가 GPU를 못 봄

- **증상:**
  ```
  docker: Error response from daemon: failed to discover GPU vendor from CDI: no known GPU vendor found
  ```
  WSL에서 `nvidia-smi`는 GPU를 잘 보는데, `docker run --gpus all ...`만 실패했다.
- **원인:** Docker Desktop은 GPU 연결을 알아서 해 주지만, 이 노트북은 Ubuntu 안에 Docker 엔진을 직접 설치했다. 그래서 컨테이너에 GPU를 넘겨주는 NVIDIA 도구가 없었다.
- **해결:**
  ```bash
  sudo apt-get install -y nvidia-container-toolkit
  sudo nvidia-ctk runtime configure --runtime=docker
  sudo systemctl restart docker
  docker run --rm --gpus all ubuntu nvidia-smi   # GPU 표가 나오면 성공
  ```
- **확인 결과:** vLLM 0.31.0 컨테이너로 Qwen3-1.7B를 띄우고, 도구 호출(tool calling, `hermes` 파서)까지 동작을 확인했다.
- **교훈:** "WSL이 GPU를 본다"와 "Docker 컨테이너가 GPU를 본다"는 따로 확인해야 하는 별개의 단계다.

## B. Git 작업 흐름

### B1. `git pull`이 계속 멈춤

- **증상:** 노트북에서 측정한 뒤 `git pull`을 하면 이렇게 멈췄다.
  ```
  error: The following untracked working tree files would be overwritten by merge:
      reports/retrieval_vectordb.md
  ```
- **원인:** 평가 스크립트가 결과를 `reports/`에 썼다. 그런데 같은 이름의 정리본을 저장소에도 올렸기 때문에, 노트북의 결과 파일과 GitHub의 파일이 부딪혔다.
- **처음 안내의 실수:** `git checkout -- 파일`로 되돌리라고 안내했다. 하지만 이 명령은 **Git이 관리하는 파일**에만 통하고, 관리 밖(untracked) 파일에는 소용이 없다. 그다음엔 `rm`으로 지우라고 다시 안내했다.
- **근본 해결 (커밋 `7511471`):**
  - 평가 결과는 항상 `results/`에 쓴다. 이 폴더는 `.gitignore`로 Git이 관리하지 않는다.
  - `reports/`에는 측정을 확인하고 해석을 붙인 **확정본만** 사람이 골라서 넣는다.
  - 혹시 `reports/`의 파일이 바뀌어 부딪히면 이렇게 한다.
    ```bash
    git checkout -- reports/ && git pull
    ```
- **교훈:** 프로그램이 자동으로 만드는 파일과 사람이 관리하는 파일은 폴더를 나눈다.

## C. 외부 프로그램 버전·배포

### C1. Milvus 실행 실패: MinIO 이미지를 받을 수 없음

- **증상:**
  ```
  Error pull access denied for minio/minio, repository does not exist or may require 'docker login'
  ```
- **원인:** Milvus 공식 예제는 저장소로 MinIO를, 설정 저장으로 etcd를 따로 띄운다. 그런데 MinIO가 Docker Hub 이미지 배포를 중단했다. 예전 설명서의 이미지 주소가 더는 동작하지 않는다.
- **해결 (커밋 `65eda3a`):** Milvus를 **혼자** 띄우게 바꿨다. `docker-compose.yml`의 Milvus에 아래를 넣었다.
  ```yaml
  ETCD_USE_EMBED: "true"        # etcd 를 Milvus 안에 내장
  COMMON_STORAGETYPE: local     # MinIO 대신 컨테이너 안 디스크에 저장
  ```
  설정 파일 `docker/milvus/embedEtcd.yaml`과 `user.yaml`도 함께 연결했다.
- **교훈:** 오픈소스의 공식 예제도 외부 이미지 배포 정책이 바뀌면 깨진다. 온프렘 설치 번들(8주차)에는 쓰는 이미지를 직접 보관해야 한다는 근거가 됐다.

### C2. Elasticsearch 접속 오류

- **증상:** Elasticsearch 서버는 떠 있는데 파이썬에서 접속하면 `media_type_header_exception` 오류가 났다.
- **원인:** `pip install elasticsearch`가 최신 **9버전** 클라이언트를 설치했다. 서버는 8.17이다. 9버전 클라이언트는 8버전 서버가 모르는 형식의 요청 머리말을 보낸다.
- **해결 (커밋 `d65b1be`):** `pyproject.toml`에서 `elasticsearch>=8.15,<9`로 고정했다.
- **교훈:** 클라이언트 라이브러리는 서버의 주 버전(major version)에 맞춰 고정한다.

### C3. Qdrant 버전 불일치 경고

- **증상:**
  ```
  UserWarning: Qdrant client version 1.19.1 is incompatible with server version 1.13.4.
  ```
- **원인:** C2와 같다. 클라이언트만 최신으로 설치됐다.
- **해결 (커밋 `4637f01`):** `qdrant-client>=1.12,<1.14`로 고정했다.

### C4. pgvector 비밀번호 실패, Weaviate 403

- **증상:**
  ```
  bge-m3·pgvector  건너뜀: OperationalError: connection to server at "127.0.0.1", port 5432 failed:
                   FATAL: password authentication failed for user "agent"
  bge-m3·weaviate  건너뜀: InsufficientPermissionsError: forbidden! Unexpected status code: 403
  ```
  두 컨테이너 모두 정상으로 떠 있었다.
- **원인:** 노트북에 이미 다른 프로그램이 같은 포트를 쓰고 있었던 것으로 판단했다. 5432는 PostgreSQL의 기본 포트이고, 8080은 여러 웹 프로그램이 흔히 쓴다. 그래서 접속이 **우리 컨테이너가 아니라 그 프로그램**으로 갔다. 비밀번호가 다르니 거절당하고(pgvector), 다른 웹 서버가 403을 돌려준(Weaviate) 것이다.
- **해결 (커밋 `4637f01`):**
  - pgvector는 15432, Weaviate는 18080(gRPC 15051)으로 옮겼다.
  - 모든 포트는 처음부터 `127.0.0.1`에만 열려 있다(외부 접속 차단). 충돌은 노트북 안의 다른 프로그램과 생긴 것이다.
  - 평가 하네스는 DB 접속에 실패해도 멈추지 않는다. 그 갈래만 "건너뜀"으로 표시하고 나머지를 계속 잰다. 이 덕분에 문제를 빨리 찾았다.
- **교훈:** "비밀번호 틀림"이나 "403"이 나왔는데 설정이 맞다면, 다른 서버에 접속하고 있는 건 아닌지 먼저 의심한다.

### C5. 노트북의 pgvector에 iterative_scan이 없음

- **증상:** `SET hnsw.iterative_scan = relaxed_order`가 "알 수 없는 설정"이라는 오류를 냈다.
- **원인:** 이 설정은 pgvector **0.8 이상**에만 있다. 당시 쓰던 설치본은 0.6이었다.
- **해결:** 오류를 "iterative_scan 은 pgvector 0.8 이상에서만 된다"는 알아보기 쉬운 메시지로 감쌌다(`stores/pgvector.py`). 이후 노트북 Docker 이미지에서는 0.8 이상으로 동작을 확인했다(D9).

### C6. psycopg "연결을 닫지 않았다" 경고

- **증상:** `ResourceWarning: <psycopg.Connection ...> was deleted while still open`
- **원인:** pgvector 저장소 객체가 DB 연결을 열기만 하고 닫지 않았다.
- **해결:** 객체가 사라질 때 연결을 닫는 `__del__`을 넣었다.

## D. 측정·해석: 판단이 틀렸던 것들

이 프로젝트의 원칙은 "**재 보고 고른다**"이다. 아래는 재 보기 전의 판단이 틀렸거나, 숫자를 처음에 잘못 읽었던 기록이다.

### D1. "하이브리드 검색이 항상 낫다"는 틀렸다 (1주차)

- **처음 생각:** BM25(낱말 검색)와 벡터 검색을 RRF로 합친 하이브리드를 기본값으로 둘 계획이었다. 예전 설계서도 그랬다.
- **측정:** bge-m3로 재 보니 같은 비중의 하이브리드가 벡터 단독보다 **낮았다**.
  - 어려운 질문: 0.75 → 0.62
  - 코드 질문: 1.00 → 0.75
  - BM25 비중을 0.3으로 낮춘 가중 하이브리드도 회복하지 못했다.
- **결정 (커밋 `67b9487`):** 질문에 코드가 있을 때만 다르게 처리하는 **코드 라우팅**을 기본값으로 정했다.
- **교훈:** 업계에서 흔히 권하는 구성도 자기 데이터에서 재 보기 전에는 가설일 뿐이다.

### D2. 문서를 키우자 벡터 검색이 코드를 헷갈림 (2주차)

- **증상:** 문서를 매뉴얼 45절에서 매뉴얼 45절 + 정비 이력 2,400건으로 키우자, bge-m3 단독의 코드 질문 R@3이 **1.00 → 0.31**로 떨어졌다.
- **원인:** `CRB-01 조치 순서`를 물으면, 같은 코드를 언급한 작업 이력이 매뉴얼보다 위로 올라왔다. 벡터는 뜻이 비슷하면 가깝게 보기 때문에 `CRB-01`과 `CRB-03`도 잘 구별하지 못한다.
- **결정 (커밋 `b4080c3`):** "코드가 있으면 BM25, 없으면 bge-m3" 라우팅을 기본값으로 정했다. 전체 R@3은 0.95였다.
- **교훈:** 1주차에 "문서가 커지면 벡터만으로는 코드를 헷갈릴 수 있다"고 적어 둔 가설이 그대로 확인됐다. 작은 데이터에서의 결론은 데이터를 키워 다시 잰다.

### D3. pgvector 정답률 급락: 버그가 아니었다

- **증상:** pgvector를 붙이자 정답 R@3이 다른 DB(0.70)보다 훨씬 낮은 **0.30**이었다. 처음에는 어댑터 코드의 버그를 의심했다.
- **확인 과정:**
  1. 새 지표 **근사 재현율@10**을 만들었다. "전수 비교로 구한 진짜 상위 10개 중 몇 개를 DB가 되찾았나"를 잰다.
  2. pgvector의 근사 재현율 평균은 0.81로, 나쁘지 않아 보였다.
  3. 그런데 놓친 문서를 하나씩 보니 **거의 다 매뉴얼 절**이었다.
- **원인:** HNSW(근사 검색 인덱스)의 손실은 고르게 나지 않는다. 다수인 작업 이력 2,400건 사이에서, 소수인 매뉴얼 45절은 그래프 연결이 약해져 잘 안 찾아진다. 그런데 사용자가 찾는 정답이 바로 그 소수 문서다.
- **교훈:** 평균 지표만 보면 속는다. 놓친 것이 **무엇인지** 열어 봐야 한다.

### D4. Chroma 점수가 낮은 이유를 잘못 설명함

- **증상:** Chroma의 근사 재현율이 0.95로 다른 DB보다 낮았다.
- **나의 첫 설명 (틀림):** "Chroma의 기본 검색 폭(search_ef)이 10이라서 그렇다"고 사용자에게 말했다.
- **확인:** HNSW 설정(M, construction_ef, search_ef)을 명시적으로 넣고 실제 적용됐는지 확인했다(커밋 `4637f01`). 설정은 제대로 들어가 있었다. 그런데도 같은 숫자에서 Chroma는 실제로 더 낮았다.
- **정정:** 사용자에게 첫 설명이 틀렸다고 알렸다. "같은 설정에서 Chroma가 실제로 덜 정확하다"로 기록했다.
- **교훈:** 그럴듯한 원인을 말하기 전에 확인부터 한다. 틀렸으면 바로 정정하고 기록에 남긴다.

### D5. "같은 설정 숫자면 공정하다"는 틀렸다

- **처음 생각:** 모든 DB에 같은 HNSW 설정(m=16, 구축 폭 100, 검색 폭 128)을 주면 공정한 비교라고 봤다.
- **측정 (커밋 `6c22fb9`, 3회 반복):**
  - 같은 숫자에서 Qdrant, Milvus, Elasticsearch는 정확했지만 pgvector와 Chroma는 아니었다.
  - pgvector와 Chroma도 설정을 m=32, 구축 200, 검색 400으로 키우자 정답 상한(0.70)을 회복했다.
  - 대가로 pgvector의 질의 지연이 약 24ms에서 37ms로 늘었다.
- **결론:** 엔진 결함이 아니라 설정 문제였다. 같은 숫자라도 엔진마다 품질이 다르다. 공정한 비교는 **"근사 재현율 목표(예: 0.99)를 엔진마다 맞춘 뒤 속도를 비교"**하는 것이다.
- **교훈:** 벤치마크의 "같은 조건"은 입력 숫자가 아니라 결과 품질로 맞춘다.

### D6. 측정할 때마다 숫자가 흔들림

- **증상:** 같은 측정을 다시 돌리면 pgvector R@3이 0.32, 0.38처럼 달라졌다.
- **원인:** HNSW 그래프는 만들 때마다 조금씩 다르게 만들어진다.
- **해결 (커밋 `7511471`):** `--repeat N` 옵션을 추가해 N번 재고, 최소~최대 범위를 표로 남기게 했다. 설정을 키운 쪽은 세 번 모두 같은 값이었다. 즉 기본 설정이 불안정하다는 것도 하나의 결과다.
- **교훈:** 숫자 하나만 보고 결론 내리지 않는다. 흔들리는 측정은 반복해서 범위를 적는다.

### D7. 질문 의도 분류가 4개 틀림

- **배경:** "매뉴얼을 찾을지, 작업 이력을 찾을지"를 질문 문장만 보고 정하는 규칙 분류기(`retrieval/intent.py`)를 만들었다.
- **증상:** 첫 규칙이 78개 질문(검사 대상 전체) 중 4개를 틀렸다.
  - 코드나 숫자 뒤에 "월"이 붙은 표현을 날짜("○월")로 잘못 읽었다.
  - "언제"를 이력 질문의 신호로 썼는데, "언제 교체하나요?"처럼 매뉴얼 질문에도 나왔다.
- **해결:** 숫자 앞에 글자나 `-`가 붙으면 날짜로 보지 않게 했고, "언제"는 규칙에서 뺐다.
  ```python
  HISTORY_RE = re.compile(r"\d{4}\s*년|(?<![\w-])\d{1,2}월|\d+\s*호기|이력|기록|지난|했었|했던")
  ```
  오분류가 0개가 됐다. 평가 표에 "의도 오분류 N건"을 항상 출력해 다시 틀리면 바로 보이게 했다.
- **교훈:** 규칙 기반 분류는 단순하지만, 틀린 사례를 측정해 표에 남겨야 믿고 쓸 수 있다.

### D8. 이력 질문 0점: 리랭커 대신 원인을 고침

- **배경:** "2025년 7월 1호기 LVL-06 이력"처럼 날짜로 작업 이력을 찾는 질문 10개를 추가했다(커밋 `521f521`).
- **증상 (노트북 측정):**

  | 갈래 | 이력 R@3 | 지연 p50 |
  |---|---|---|
  | 라우팅 | 0.00 | 16 ms |
  | 리랭커 + 라우팅 | 1.00 | 521 ms |

  리랭커를 붙이면 바로 해결됐다. 하지만 질문마다 0.5~0.8초가 더 든다.
- **원인:**
  - 이력 질문에는 `LVL-06` 같은 코드가 있어서 라우팅이 BM25로 보낸다.
  - BM25는 낱말이 같은지만 본다. 질문의 "2025년 **7**월"은 토큰 `7`이 되고, 문서의 "2025-**07**-14"는 `07`이 된다. 서로 다른 낱말이다.
  - 같은 코드, 같은 호기의 기록이 수십 건이라 날짜 말고는 구별할 단서가 없다.
  - 리랭커는 질문과 문서를 함께 읽어서 날짜가 같다는 걸 알아봤다.
- **해결 (커밋 `0841786`):** 토크나이저(`tokenize_ko.py`)가 날짜와 호기를 같은 모양으로 바꾸게 했다.
  - `2025년 7월` → `2025-07`, `2025-07-14` → `2025-07`
  - `1 호기` → `1호기`
  - 테스트 `test_dates_and_lines_normalize_to_same_token`을 추가했다.
- **결과 (노트북 재측정, 커밋 `967e429`):**

  | 갈래 | 전체 R@3 | 이력 R@3 | 지연 p50 |
  |---|---|---|---|
  | 의도필터 + 라우팅 | **0.96** | **1.00** | **19 ms** |
  | 의도필터 + 리랭커 + 라우팅 | 0.96 | 1.00 | 844 ms |

  리랭커 없이 같은 점수가 나왔고, 지연은 약 1/45이다. 기본값을 "의도필터 + 라우팅"으로 정하고 리랭커는 껐다.
- **교훈:** 비싼 모델을 붙이면 문제가 가려진다. 붙이기 전에 **왜 틀렸는지**를 먼저 본다.

### D9. pgvector 필터 검색이 데이터가 커지면 무너짐

- **배경:** 의도 필터는 DB에 "매뉴얼 중에서만 찾아라"(`WHERE doc_type='manual'`)라는 조건을 건다. DB마다 이 조건을 처리하는 방식이 다르다.
- **증상:**

  | pgvector 동작 | R@3 |
  |---|---|
  | PostgreSQL이 알아서 고름 | 0.77 (정답 상한과 같음) |
  | HNSW 인덱스를 강제로 쓰게 함 | **0.32** |
  | 인덱스 강제 + `iterative_scan` | 0.77 |

- **원인:**
  - PostgreSQL은 표가 작으면 인덱스 대신 **모든 행을 읽는 방법**(순차 스캔)을 고른다. 이 방법은 정확하다.
  - 표가 커지면(실제 운영 규모) HNSW 인덱스를 쓴다. 이때 pgvector는 **가까운 후보 128개를 먼저 뽑고, 그다음에 조건으로 거른다**(post-filtering).
  - 매뉴얼은 전체의 1.8%뿐이라, 거르고 나면 결과가 거의 남지 않는다.
  - 운영에서 데이터가 늘어나는 순간 **오류 메시지 없이** 정확도만 떨어진다. 가장 찾기 어려운 종류의 문제다.
- **재현 방법:** `SET enable_seqscan = off`로 순차 스캔을 막아, 큰 데이터 상황을 작은 데이터에서 미리 만들었다(`force_index: true`).
- **해결:** pgvector 0.8의 `SET hnsw.iterative_scan = relaxed_order`를 켠다. 거르고 나서 결과가 부족하면 더 탐색한다.
- **다른 DB:** Qdrant(payload 인덱스 필요), Milvus, Elasticsearch, Weaviate, Chroma는 모두 **검색하는 도중에** 조건을 적용해서 0.77로 정답 상한과 같았다.
- **결정:** pgvector로 필터 검색을 할 때는 `iterative_scan`을 반드시 켠다. CI에도 "필터를 걸면 요청한 종류의 문서만 정확히 10개 나와야 한다"는 테스트(`test_store_filter_returns_only_requested_doc_type`)를 넣었다.

### D11. SGLang 캐시 재사용률이 비어 있음 (3주차)

- **증상:** SGLang 동작 확인 결과의 `캐시` 칸이 모든 줄에서 `—`였다. 그런데 3턴 대화의 첫 글자 시간이 더 짧은 단일 질문보다 짧아(48ms vs 78ms) 캐시는 분명히 일하고 있었다.
- **원인:** SGLang 은 응답의 사용량 정보(usage)에 '캐시에서 꺼낸 토큰 수'를 기본으로 싣지 않는다. vLLM 도 마찬가지라 처음부터 `--enable-prompt-tokens-details` 를 켜 두었는데, SGLang 쪽 옵션을 빠뜨렸다.
- **해결 (커밋 `9e4b0ac`):** SGLang 실행 옵션에 `--enable-cache-report` 를 추가했다(`serving/compose.yml`).
- **교훈:** 측정기가 `—`를 찍으면 "값이 0"이 아니라 "엔진이 안 알려 줌"이다. 다른 지표(첫 글자 시간)와 맞춰 보면 어느 쪽인지 드러난다.

### D12. 3턴 대화의 처리량이 이상하게 낮음 (3주차)

- **증상:** SGLang 동작 확인에서 3턴 대화(multiturn)의 동시 4 처리량이 1.23 요청/s 로, 다른 요청 모양(2.1~2.7)의 절반이었다.
- **원인:** 측정기 실수. 빠른 모드는 요청 8개를 3턴짜리 대화로 묶어 대화가 2개뿐이었다. 대화 하나는 한 사용자가 맡으므로 동시 4명 중 2명이 놀았다.
- **해결 (커밋 `9e4b0ac`):** 대화 수를 최소한 동시 사용자 수만큼 만들게 했다(`scripts/bench_serving.py`).
- **교훈:** 결과가 이상하게 나쁘면 엔진보다 측정기를 먼저 의심한다. "동시 N명"이 정말 N명이었는지 확인한다.

### D13. LiteLLM 게이트웨이 경유 요청이 전부 실패 (3주차)

- **증상:** 노트북 동작 확인에서 `LiteLLM → vLLM` 줄만 요청 16개가 모두 오류였다. vLLM 을 직접 부른 줄은 정상이었다. 결과 파일에 오류 메시지가 없어 처음엔 원인을 바로 볼 수 없었다.
- **원인 (설정 실수로 판단):** 게이트웨이 설정이 엔진을 `http://host.docker.internal:8000` 으로 찾게 되어 있었다. 이 주소는 컨테이너에서 '호스트 컴퓨터'를 가리키는데,
  엔진 포트는 보안을 위해 호스트의 `127.0.0.1` 에만 열어 두었다(`127.0.0.1:8000:8000`). 호스트 바깥(컨테이너)에서 오는 접속은 받지 않으므로 게이트웨이가 엔진에 닿지 못했다.
- **해결:** 게이트웨이와 엔진은 같은 compose 파일이라 같은 Docker 네트워크에 있다. 서비스 이름과 컨테이너 안 포트(`http://vllm:8000/v1`, `http://sglang:30000/v1`, `http://llamacpp:8080/v1`)로 붙게 바꿨다.
  결과 파일에 오류 메시지 예시를 함께 찍게 했다(`serving/report.py`).
- **교훈:** 컨테이너끼리는 서비스 이름으로 붙인다. '외부 노출 차단(127.0.0.1)'과 '컨테이너 간 통신'은 서로 다른 경로다. 그리고 실패를 셀 때는 왜 실패했는지도 함께 남긴다.

### D14. SGLang 이 동시 16명에서 갑자기 느려짐 (3주차)

- **증상:** 노트북 본 측정에서 SGLang 은 동시 8명까지 vLLM 보다 18~25% 빨랐는데, 16명에서 글자 간격(TPOT)이 11.9 → 20.4 ms 로 뛰어 짧은 질문 처리량이 vLLM 보다 28% 낮아졌다. 캐시를 꺼도 똑같아서 캐시 문제는 아니었다.
- **추정:** 디코드 'CUDA 그래프'(매 토큰 반복하는 GPU 계산을 미리 녹화해 두고 재생하는 최적화)의 배치 크기 상한이 작다.
- **확인:** 첫 시도는 서버 준비 전에 정보를 요청해 빈 응답(`Expecting value`)을 받았다. 준비될 때까지 기다리게 바꿔 다시 보니 시작 로그에
  `Capture target decode CUDA graph begin. ... bs=[1, 2, 4, 8], avail mem=0.32 GB` — 그래프를 8명분까지만 만들었다. 9명 이상이 동시에 오면 녹화 없이 계산한다.
  모델·KV 캐시를 올린 뒤 GPU 여유가 0.3GB 뿐이라 SGLang 이 스스로 상한을 낮게 잡은 것으로 본다. 1~8명분 그래프에 든 메모리는 0.03GB.
- **해결:** `--cuda-graph-max-bs 16` 을 준 변형(`sglang-g16` 프로필)을 만들고, 기본과 같은 실행 안에서 비교한다(`configs/serving_sglang_graph.yaml`).
- **첫 시도 실패 (내 실수):** 위 옵션 이름은 예전 버전 기준으로 기억에 의존해 썼다. SGLang 0.5.21 은 이 옵션을 디코드용·프리필용으로 나눠서
  `error: ambiguous option: --cuda-graph-max-bs could match --cuda-graph-max-bs-decode, --cuda-graph-max-bs-prefill` 을 내고 시작 직후 종료했다.
  측정기는 이걸 모른 채 20분을 기다렸다(D15). → `--cuda-graph-max-bs-decode 16` 으로 고쳤다. 교훈: 엔진 옵션은 쓰는 버전의 `--help` 로 확인한다.
- **결과 (같은 실행에서 기본과 비교):** 동시 16명 짧은 질문의 글자 간격 20.4 → 12.6 ms, 처리량 5.91 → 9.04 (+53%). 에이전트 질문 +18%, 3턴 대화 +22%.
  동시 1·4·8명은 차이 2% 이내 — 그래프가 이미 있던 구간이라 같아야 정상이고, 실제로 같아서 원인을 정확히 짚었다는 대조 확인이 됐다.
  이 결과로 게이트웨이 1순위 엔진을 vLLM → SGLang 으로 바꿨다(잠정).
- **교훈:** 같은 엔진이라도 GPU 메모리 크기에 따라 기본 최적화 범위가 달라진다. 큰 GPU 에서 잰 남의 벤치마크 숫자를 작은 GPU 에 그대로 옮기면 안 되고,
  성능이 특정 지점에서 '계단처럼' 꺾이면 엔진 시작 로그부터 본다.

### D15. 엔진이 안 뜨면 20분을 기다리고, 원인 로그까지 지워짐 (3주차)

- **증상:** SGLang 을 `--cuda-graph-max-bs 16` 으로 띄운 측정이 `TimeoutError: ... 1200s 안에 준비되지 않음` 으로 끝났다. 원인을 보려 했지만 로그가 없었다.
- **원인 (측정기 결함 두 가지):**
  1. 준비 대기 중에 컨테이너가 이미 죽었는지 확인하지 않아, 죽은 컨테이너를 20분 동안 기다렸다.
  2. 실패하든 성공하든 마지막에 `docker compose down` 으로 컨테이너를 지우는데, 그 전에 로그를 남기지 않아 원인이 함께 사라졌다.
- **해결:** 대기 중 30초마다 컨테이너 상태를 확인해 죽었으면 바로 실패로 끝낸다. 실패하면 내리기 전에 로그 300줄을 `results/logs/<설정>_<프로필>.log` 에 저장하고 마지막 25줄을 화면에 찍는다.
- **교훈:** 실패를 기록할 때는 '실패했다'만이 아니라 '왜'를 남길 수 있게, 증거(로그)를 지우는 단계 앞에서 먼저 저장한다. (D13 의 "오류 메시지 예시도 남긴다"와 같은 교훈)

## G. 작업 환경의 제약

### G1. 클라우드 작업 환경에서 막힌 것

- 코드 작성은 Claude의 클라우드 작업 환경에서, 실측은 사용자 노트북에서 했다.
- 클라우드 작업 환경은 Docker Hub와 Hugging Face에 접속할 수 없다. 그래서 이런 것은 그곳에서 실행할 수 없다.
  - bge-m3 임베딩 모델, bge-reranker 모델
  - Elasticsearch, Weaviate, Milvus 서버
- **분담:**
  - 클라우드 작업 환경: 모델 없는 해시 임베더와 BM25로 코드가 맞는지 확인
  - GitHub Actions(CI): 실제 DB 서버로 통합 테스트
  - 노트북: 실제 모델로 최종 수치 측정
  - 보고서에는 숫자마다 어디서 쟀는지 적는다.

### G2. GitHub Actions 로그를 볼 수 없음

- **증상:** CI가 실패해도 클라우드 작업 환경의 네트워크 제한 때문에 상세 로그를 내려받을 수 없었다.
- **해결 (커밋 `6e84442`):** 실패 내용을 `::error::` 주석으로 출력하게 했다. 주석은 GitHub API로 읽을 수 있다.
