## 1주차에 알게 된 것
- Kiwi 형태소 분석기는 `CRB-03` 을 `CRB`·`-`·`03` 으로 쪼갠다. 그대로 두면 `SPK-03` 과 `03` 이 겹쳐 BM25 가 코드를 구별하지 못한다.
  → 코드형 토큰은 정규식으로 먼저 떼어 통째로 보존한다 (`tokenize_ko.py`, 테스트 `test_code_tokens_are_kept_whole`).
- 질문을 세 유형으로 나눠 채점해야 차이가 보인다. 코드·바꿔 말하기 질문에서는 BM25 가 거의 만점이지만,
  문서와 낱말이 겹치지 않는 '어려운' 질문에서는 Recall@3 이 0.5 안팎으로 떨어진다. 의미 임베딩이 필요한 곳이 바로 여기다.
- bge-m3 로 재 보니 같은 무게 RRF 하이브리드가 벡터 단독보다 낮았다(어려운 질문 0.75→0.62, 1.00→0.75).
  예전 설계서에서 하이브리드를 기본값으로 둔 판단은 측정 없이 내린 것이었고, 이 데이터에서는 틀렸다.
  → 가중 RRF(BM25 0.3)는 회복하지 못했고, 코드 라우팅이 벡터 단독과 같은 최고점(0.95 / 0.97)을 냈다. 기본값으로 채택.
  → 2주차: 문서 규모를 키워 '벡터만으로도 코드를 구별한다'는 결과가 유지되는지, 리랭커가 남은 오답을 줄이는지 같은 표에서 잰다.

## 2주차에 알게 된 것 (진행 중)
- 문서를 매뉴얼 45절 + 정비 이력 2,400건으로 키웠다. 이력은 같은 경보 코드·부품 이름을 써서 매뉴얼 절을 찾는 검색의 현실적인 경쟁자가 된다.
- 저장소 비교를 공정하게: 모든 저장소가 같은 벡터(한 번만 임베딩), 같은 HNSW 설정(m=16, 구축 폭 100, 검색 폭 128)을 쓰고,
  색인 시간에서 임베딩 시간을 분리했다. 지연도 질의 임베딩을 뺀 'DB 검색만'을 따로 잰다.
- 새 지표 **근사 재현율@10**: 각 DB 가 전수 비교 상위 10개를 몇 % 되찾는지. 처음 pgvector 를 붙였을 때 정답 재현율이 0.38→0.08 로 무너져
  어댑터 버그를 의심했지만, 원인은 HNSW 근사 손실이었다. 구축 폭 64 에서 근사 재현율 0.78, 200 에서 0.97.
  손실이 고르게 나지 않고 **소수인 매뉴얼 절에 몰렸다** — 다수인 작업 이력 사이에서 그래프 연결이 약해진 것으로 본다.
  → 벡터DB 비교에서는 정확도·속도와 함께 근사 재현율을 반드시 본다. 기본 설정을 그대로 믿지 않는다.
