# 로드맵 (8주)

각 단계는 "같은 평가셋으로 재서 표로 남긴다"로 끝난다. 기술 이름을 늘어놓는 게 아니라, 재 보고 고른 근거를 남기는 것이 목표다.

계획은 8주였고, 실제로는 벡터DB(계획 2~3주차)를 2주차에 끝내서 서빙을 3주차에 했다. 아래 표의 '주'는 실제 진행 순서다.

## 1주차에 알게 된 것
- Kiwi 형태소 분석기는 `CRB-03` 을 `CRB`·`-`·`03` 으로 쪼갠다. 그대로 두면 `SPK-03` 과 `03` 이 겹쳐 BM25 가 코드를 구별하지 못한다.
  → 코드형 토큰은 정규식으로 먼저 떼어 통째로 보존한다 (`tokenize_ko.py`, 테스트 `test_code_tokens_are_kept_whole`).
- 질문을 세 유형으로 나눠 채점해야 차이가 보인다. 코드·바꿔 말하기 질문에서는 BM25 가 거의 만점이지만,
  문서와 낱말이 겹치지 않는 '어려운' 질문에서는 Recall@3 이 0.5 안팎으로 떨어진다. 의미 임베딩이 필요한 곳이 바로 여기다.
- bge-m3 로 재 보니 같은 무게 RRF 하이브리드가 벡터 단독보다 낮았다(어려운 질문: 운영 장애 0.75→0.62, 고객 상담 1.00→0.75).
  예전 설계서에서 하이브리드를 기본값으로 둔 판단은 측정 없이 내린 것이었고, 이 데이터에서는 틀렸다.
  → 가중 RRF(BM25 0.3)는 회복하지 못했고, 코드 라우팅이 벡터 단독과 같은 최고점(0.95 / 0.97)을 냈다. 기본값으로 채택(2주차에 '코드 → BM25 단독' 라우팅으로 바뀜).
  → 2주차에 문서를 키워 다시 쟀다: 벡터 단독의 코드 구별이 무너져 라우팅을 바꿨고, 리랭커는 원인(날짜 표기)을 고친 뒤 껐다.

## 2주차에 알게 된 것
- 문서를 매뉴얼 45절 + 정비 이력 2,400건으로 키웠다. 이력은 같은 경보 코드·부품 이름을 써서 매뉴얼 절을 찾는 검색의 현실적인 경쟁자가 된다.
- 저장소 비교를 공정하게: 모든 저장소가 같은 벡터(한 번만 임베딩), 같은 HNSW 설정(m=16, 구축 폭 100, 검색 폭 128)을 쓰고,
  색인 시간에서 임베딩 시간을 분리했다. 지연도 질의 임베딩을 뺀 'DB 검색만'을 따로 잰다.
- 새 지표 **근사 재현율@10**: 각 DB 가 전수 비교 상위 10개를 몇 % 되찾는지. [클라우드 작업 환경, 해시 임베더로 배선 확인 중] 처음 pgvector 를 붙였을 때 정답 재현율이 0.38→0.08 로 무너져
  어댑터 버그를 의심했지만, 원인은 HNSW 근사 손실이었다. 구축 폭 64 에서 근사 재현율 0.78, 200 에서 0.97.
  손실이 고르게 나지 않고 **소수인 매뉴얼 절에 몰렸다** — 다수인 작업 이력 사이에서 그래프 연결이 약해진 것으로 본다.
  → 벡터DB 비교에서는 정확도·속도와 함께 근사 재현율을 반드시 본다. 기본 설정을 그대로 믿지 않는다.
- [노트북 측정] 문서를 키우자 bge-m3 단독의 코드 질문 R@3 이 1.00→0.31 로 무너졌다. 1주차 가정이 확인됨.
  코드 질문을 BM25 단독으로 보내는 라우팅이 전체 0.95 로 최고 → 기본값 변경.
- [노트북 측정] pgvector 근사 재현율 0.81 이지만 정답 R@3 0.30 (전수 비교 0.70). 손실이 소수(매뉴얼) 문서에 몰리는 현상이 실제 임베딩에서도 재현됨.
- 운영 이슈 기록: MinIO 가 Docker Hub 배포를 중단해 Milvus 를 etcd 내장·로컬 저장으로 전환. 노트북 포트 충돌(5432·8080)로 15432·18080 사용.
- [노트북 측정, 3회 반복] pgvector·Chroma 는 HNSW 를 키우면(m32·구축200·검색400) 정답 상한 회복 → 엔진 결함이 아니라 설정 문제.
  같은 설정 숫자라도 엔진마다 품질이 다르므로, DB 비교는 '설정 통일'이 아니라 '근사 재현율 목표(예: 0.99)를 맞춘 뒤 속도 비교'로 해야 한다.
- [노트북 측정] 이력 질문이 라우팅에서 0점, 리랭커로 만점. 원인은 날짜 표기("7월" ↔ "07") — 토크나이저에서 `2025-07` 로 통일하자 리랭커 없이 만점.
  → 비싼 모델을 붙이기 전에 실패 원인을 본다. 기본값을 '의도필터 + 라우팅'(R@3 0.96, 19 ms)으로, 리랭커(844 ms, 같은 점수)는 끈다.
- [노트북 측정] pgvector 는 HNSW 후 WHERE 필터라 소수 문서 필터 검색에서 0.32 로 무너진다. 작은 표에선 플래너가 순차 스캔을 써서 숨는다. iterative_scan 으로 회복.

## 3주차(서빙)에 알게 된 것
- [노트북 측정] 에이전트 요청은 입력의 66~84% 가 앞 요청과 같다(시스템 프롬프트·업무 기능(도구) 설명·앞 대화). 접두사 캐시를 켜면 받을 수 있는 최대 처리량이 2~3배, 동시 16명에서는 14~26배 차이.
  → 엔진 선택보다 캐시가 크다. 에이전트는 시스템 프롬프트·업무 기능(도구) 설명을 고정해 앞에 둬야 캐시를 살린다.
- [노트북 측정] llama.cpp 는 혼자 쓸 때 가장 빠르지만 그건 Q8_0 양자화(가중치 절반) 덕이고, 긴 입력이 몰리면 동시 4명부터 무너진다. 1인용·장애 대체로 한정.
- [노트북 측정] 우선순위 문항("급하지 않아요" → low)을 세 엔진이 똑같이 틀렸다 → 엔진이 아니라 모델 크기 문제. 에이전트 단계에서 4B·8B 를 같은 20문항으로 잰다.
- [노트북 측정] SGLang 은 동시 8명까지 vLLM 보다 18~25% 빠르지만 16명에서 글자 간격이 11.9 → 20.4 ms 로 뛰었다. 디코드 CUDA 그래프를 8명분까지만 만든 것이었다(작은 GPU 에서 엔진이 고른 기본값). 16명분으로 올리자 동시 16명 처리량 +18~53%, vLLM 보다 12~29% 앞서 게이트웨이 1순위를 SGLang 으로 바꿨다(잠정).
  → 기본 설정 그대로의 엔진 비교는 '그 GPU 에서 엔진이 고른 기본값'의 비교다. 계단처럼 꺾이는 지점은 시작 로그부터 본다.
- [노트북 측정] 1순위(GPU SGLang)를 정상 종료해도(62개), 갑자기 강제 종료해도(60개) 게이트웨이가 CPU llama.cpp 로 넘겨 요청 손실 0. 대신 대체 중 응답이 약 40배 느림 → '끊기지 않음'과 '같은 품질'은 다르다. 실서비스는 GPU 이중화, 에이전트는 지연 안내.

## 4주차(에이전트)에 알게 된 것
- 정확한 값(이력·고객·요금)은 SQL 업무 기능(도구)으로, 문서는 검색 업무 기능(도구)으로 나눴다. 2주차에 문서 검색이 날짜로 찾는 이력 질문에서 0점이었던 것을 설계로 옮긴 결정.
- MCP 어댑터의 기본 사용법은 업무 기능(도구)을 부를 때마다 서버 프로세스를 새로 띄운다(PID 로 확인, 호출당 약 0.8초 + 색인 재생성). 연결을 유지하도록 바꿨다.
- 규칙 기준선이 처음엔 83% 로 후하게 나왔다 — 평가셋 문장 모양에 맞춰진 탓. 키워드로는 못 알아듣는 과업을 더하자 73%.
- [노트북 측정] 작은 LLM(Qwen3-1.7B 46%, 4B 27%)이 규칙(88%)보다 낮았다. 주된 실패는 업무 기능(도구)을 건너뛰고 지어내기와 근거 표기. 엔진(SGLang·vLLM)은 품질 차이가 없었다 → 품질은 모델, 속도는 엔진.
  → 위험 행동·개인정보 노출 0 은 모델이 아니라 구조로 막아서 지켜졌다. 같은 방식(구조로 보장)으로 근거와 '업무 기능(도구) 먼저'를 고쳐 다시 잰다.
- [노트북 측정] 2차: 근거를 코드가 붙이자 1.7B 54% → 65%. "업무 기능(도구)을 먼저 써라"는 글은 4B 에 효과가 없었다(글로 대답함). 작은 모델은 지시를 따르기보다 글자를 베낀다 — 프롬프트 예시 번호까지 복사했다.
  → 작은 모델에게는 글로 부탁하지 말고 형식으로 강제한다(3차: 업무 기능(도구) 선택 필수).
- [노트북 측정] 3차: 생각 모드를 켜자 4B 가 54% → 92%, 처음으로 규칙(88%)을 넘었다. 대신 과업당 13초(5배). '생각 모드 끔'은 서빙 측정용으로 정한 설정을 에이전트에 그대로 물려 쓴 것이었다.
  → 한 측정을 위해 정한 설정이 다른 측정의 결론을 바꿀 수 있다. 설정은 측정 목적마다 다시 정한다.
- [노트북 측정] 4차: 92% 재현(실패 과업까지 같음). 생각 모드만 62%, 안전 기능을 더하면 92% — 서로 곱해지는 관계(생각 모드만 줄은 처음 69% 로 적었다가 생각 글을 떼고 재채점해 고침). 1.7B 도 생각 모드로 85%. 기본값을 4B + 생각 모드 + 안전 기능으로(잠정).
  → 모든 모델이 '상식으로 답할 수 있어 보이는' 안전 질문에서 매뉴얼을 찾지 않았다. 아는 것 같은 질문일수록 찾아보게 하는 규칙이 필요하다.

## 5주차(에이전트 마무리)에 알게 된 것
- [노트북 측정] '생각은 첫 단계만'은 시간을 절반으로 줄였지만(15.6 → 7.3초) 여러 단계 과업에서 두 번째 선택을 놓쳤다(92 → 85%). 결과를 읽고 다음을 정하는 것도 '고르는' 일이다.
- [노트북 측정] 안전 질문 규칙을 프롬프트에 넣어도 `ops-m5` 는 그대로 실패 — 4B 는 매뉴얼 대신 작업 이력을 찾았다. 그래프가 먼저 매뉴얼을 찾게 하자 96%. 꼭 지켜야 하는 규칙은 프롬프트가 아니라 구조에 둔다(네 번째 같은 결론).
- [측정기] 생각 글이 답에 섞여 와 채점이 부풀 수 있었다. 답에서 항상 떼고, 저장된 결과를 다시 채점하는 도구를 만들었다(한 줄 69% → 62%, 결론은 유지). 새 옵션을 켜면 점수표보다 답 원문을 먼저 본다.
