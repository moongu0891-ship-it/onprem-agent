# AI 에이전트 클라우드 실습 워크북 — minikube 위에 온프레미스 에이전트 올리기

7주차까지 만든 에이전트(상담 화면 · 에이전트 그래프 · 업무 기능(도구) 서버 · 모델 서버 · 게이트웨이)를 **실제 클라우드 서비스의 층**대로 minikube 위에 올린다. 형식은 'Minikube에서 AWS EKS까지' 워크북과 같다 — 장마다 **완료 목표 → 그림 → 실행(명령 한 줄씩 해설) → 관찰 → 장애·복구 → 정리 → 성공 확인**. 그리고 이 저장소답게 장마다 **잰다**.

- 환경: Windows 11 · WSL2 Ubuntu · Docker · minikube(docker 드라이버) · RTX 5070 Laptop 8GB · WSL2 메모리 15GB
- 상용 클라우드 없이 노트북 한 대로. 진짜로 못 만드는 칸(전 세계 CDN, 노드 자동 확장)은 흉내와 설명으로 채우고 그렇게 적는다.
- 명령은 모두 `~/onprem-agent` 에서 실행한다. 결과는 `results/cloud/` 에 남고(Git 제외), 확정본은 `reports/cloud_*.md` 로 옮긴다.

## 00. 실습 지도와 사용 방법

**완료 목표** · 어느 층을 어느 장에서 채우는지, 노트북 메모리를 어떻게 나눠 쓰는지 이해한다.

```
 사용자 ─▶ ① 엣지 ─▶ ② 나눠 주기 ─▶ ③ 관문 ─▶ ④ 앱 계층 ─▶ ⑤ 무거운 일 ─▶ ⑥ 데이터
             TLS·방화벽   로드 밸런서    게이트웨이   상담 화면 ×N    모델 서버(GPU)   검색 색인·업무 DB
             (Ingress)    (Service)     인증·속도    에이전트 그래프  작업 큐          대화 저장
                                       제한                                           ⑦ 옆단: 관측 · CI/CD(Jenkins) · 설정·비밀 · IaC
```

| 층 (그림의 칸) | 실제 클라우드에서는 | 이 워크북에서 만드는 것 | 장 | 잰다 |
|---|---|---|---|---|
| 화면 | 브라우저가 보는 프런트엔드 | 7주차 상담 화면(`/`)·관리자 화면(`/admin`)을 Pod 로 | 04 | 화면이 뜨기까지 |
| ① 엣지 · TLS·방화벽 | ACM · WAF | Ingress-NGINX + 자체 서명 인증서(https), NetworkPolicy 로 모델 서버는 앱만 접근 | 08 | http→https 되돌림, 막힌 통신 확인 |
| ① CDN | CloudFront | **없음(흉내만)** — 정적 파일에 캐시 머리말(Cache-Control) 붙이고 두 번째 요청이 304 인지 본다 | 08 | 304 비율 |
| ② 로드 밸런서 | ALB · NLB | Service(ClusterIP) 가 상담 화면 Pod N 개에 나눠 준다 — 어느 Pod 가 받았는지 답 머리말로 본다 | 05 | Pod 별 요청 수 |
| ② 오토스케일링 | HPA · Auto Scaling | HPA 로 상담 화면 Pod 1 → 4 (CPU 기준) · 노드 자동 확장은 **없음(설명)** | 06 | 부하 중 Pod 수와 p95 |
| ③ API 게이트웨이 · 인증 · 속도 제한 | API Gateway · Cognito · rate limit | Ingress 에 기본 인증(Basic Auth) + 분당 요청 제한 · LiteLLM 게이트웨이가 모델 앞 | 09 | 429 가 나오는 요청률 |
| ④ 앱 서버(무상태) ×N | ECS · Cloud Run | 상담 화면 Pod 는 **무상태** — 대화·승인 대기는 ⑥ 의 DB 에 | 05 | Pod 를 죽여도 승인 대기가 이어지나 |
| ④ 컨테이너 오케스트레이터 | Kubernetes · ECS | minikube 자체 | 02 | — |
| ⑤ 모델 서빙(GPU) | SageMaker · Triton | SGLang Qwen3-4B(FP8) — **GPU 가 Pod 에 보이면 클러스터 안, 아니면 호스트 Docker 에 두고 클러스터에서 붙음**(01장이 정함) | 01·07 | 첫 글자 시간·처리량(3주차 측정기 그대로) |
| ⑤ 작업 큐 · 워커 | SQS · Celery | 전체 시험(1시간)을 Job 으로 — 큐는 Jenkins 가 맡는다 | 12 | — |
| ⑤ 배치 파이프라인 | Airflow · Batch | 검색 색인 만들기를 Job 으로(앱 시작 전에 한 번) | 10 | 색인 시간 |
| ⑥ 벡터 DB · 관계형 DB | pgvector · RDS | PostgreSQL + pgvector StatefulSet 하나로 둘 다(2주차 어댑터 그대로) · 대화·승인 대기 저장도 여기 | 10 | Pod 재시작 뒤 데이터가 남나 |
| ⑥ 객체 저장소 · 캐시 | S3 · Redis | PVC 에 모델·색인 파일 · 캐시는 모델 서버의 접두사 캐시(3주차) — Redis 는 **없음(설명)** | 10 | — |
| ⑦ 관측 | CloudWatch · Datadog | Prometheus + Grafana(가벼운 구성) + Langfuse(에이전트 추적) | 11 | 대시보드에 p95·승인 수 |
| ⑦ CI/CD | GitHub Actions · ArgoCD | **Jenkins** 를 minikube 에, 노트북(GPU)을 일꾼으로 — 올릴 때 단위·모듈, 매일 밤 전체 시험 | 12 | 밤 시험이 돌고 빨간불 보고서가 남나 |
| ⑦ 설정 · 비밀 | Secrets Manager | ConfigMap(창구 정의 `desk.yaml`) · Secret(게이트웨이 키, DB 비밀번호) | 04 | — |
| ⑦ IaC | Terraform | `deploy/` 의 매니페스트·Helm 값 파일이 그 자체. `make cloud-up` 한 줄로 전부 | 13 | 처음부터 다시 올리는 시간 |

**메모리 예산 (WSL2 15GB):** minikube 노드 6GB(앱·DB·관측·Jenkins) + 모델 서버 4~5GB(호스트 Docker 또는 Pod) + 전체 시험 중 임베더 2GB. **전체 시험(12장)은 관측·Jenkins 외 실습 서비스를 내린 상태에서만** 돌린다 — Jenkins 가 시작 전에 확인한다. 장마다 '이 장에 필요한 것만' 띄우고 끝에 내린다.

**장 순서와 의존:** 00 → 01(GPU 판정) → 02 → 03 → 04 → 05 → … 순서대로. 01 의 결과가 07 의 모양을 정하므로 **01 을 먼저 노트북에서 돌리고 결과를 적은 뒤** 뒤 장을 쓴다(이 문서는 그 순서대로 자란다).

### 코드와 해설을 읽는 순서

각 코드 상자의 왼쪽 숫자는 해설을 찾는 행 번호다. 터미널에는 숫자를 빼고 명령만 넣는다. 상자 이름은 `장-번호`(예 `01-003`). 행 끝의 `\` 는 다음 줄까지 한 명령이다. 모든 명령은 `~/onprem-agent` 에서, WSL2 Ubuntu 터미널에서 실행한다. 긴 스크립트는 `deploy/scripts/` 에 있고 부록에서 한 줄씩 읽는다.

| 표현 | 읽는 방법 |
|---|---|
| `-n lab` | 조작할 네임스페이스(작업 구역) 이름. 이 워크북은 전부 `lab` |
| `-p agent` | minikube 프로필(클러스터 이름). 이 워크북은 전부 `agent` |
| `kubectl get/describe/logs` | 조회 / 상세와 사건 / 컨테이너 출력 |
| `--overrides='{...}'` | 명령 한 줄로 Pod 를 만들 때 자원 요구 같은 세부를 JSON 으로 덧붙임 |
| 성공 판정 | 종료 코드 0 + 각 장의 '성공 확인' 에 적은 출력 |

## 01. GPU 를 클러스터에 넘길 수 있는가 — 이 판정이 뒤 장의 모양을 정한다

**완료 목표** · minikube 안의 Pod 가 `nvidia-smi` 로 노트북 GPU 를 보는지 확인하고, 결과를 적는다.

```
 그림 01 | GPU 가 어디까지 보이나
   노트북 GPU ─▶ WSL2 (nvidia-smi 됨, 3주차 확인) ─▶ Docker (--gpus, 3주차 서빙 확인) ─▶ minikube 노드(컨테이너) ─▶ Pod   ← 여기가 물음표
```

minikube docker 드라이버는 노드 자체가 Docker 컨테이너다. 그 안에서 또 컨테이너(Pod)가 도는 구조라, GPU 가 두 겹을 통과해야 한다. minikube 는 `--gpus all` 옵션과 NVIDIA 장치 플러그인으로 이를 지원하지만 WSL2 에서는 되는 조합이 좁다. 그래서 **먼저 잰다**.

**실행**

```
 Ubuntu Bash | 01-001
   1  bash deploy/scripts/install-minikube.sh
   2  minikube start -p agent --driver=docker --container-runtime=docker --gpus=all --memory=6g --cpus=4
   3  kubectl create namespace lab
   4  minikube -p agent addons enable nvidia-device-plugin
   5  kubectl -n kube-system get pods | grep nvidia
```

1행 kubectl · minikube · helm 을 설치한다(이미 있으면 건너뜀). 스크립트 한 줄씩 읽기는 부록.
2행 클러스터를 만든다. `-p agent`: 프로필 이름. `--driver=docker`: 노드를 Docker 컨테이너로. `--gpus=all`: 노드 컨테이너에 GPU 를 넘긴다(docker 의 `--gpus all` 과 같음). `--memory=6g --cpus=4`: 노드 상한 — 15GB 중 모델 서버 몫을 남긴다.
3행 작업 구역 `lab` 을 만든다. 이 워크북의 모든 자원은 여기에.
4행 NVIDIA 장치 플러그인을 켠다 — 노드의 GPU 를 Kubernetes 가 `nvidia.com/gpu` 자원으로 세게 한다.
5행 플러그인 Pod 가 떴는지 본다. `Running` 이어야 한다.

```
 Ubuntu Bash | 01-002
   1  bash deploy/scripts/probe-gpu.sh
```

1행 CUDA 기본 이미지로 Pod 하나를 띄워 `nvidia-smi -L` 을 찍고, 노드가 광고하는 GPU 수와 Pod 의 사건(Events)을 `results/cloud/01_gpu_probe.txt` 에 남긴다. 스크립트 한 줄씩 읽기는 부록.

**관찰 — 둘 중 하나가 나온다**

| 결과 | 보이는 것 | 뒤 장의 모양 |
|---|---|---|
| **A. 된다** | `GPU 0: NVIDIA GeForce RTX 5070 Laptop GPU (UUID: …)`, 노드 `gpu=1` | 07장에서 SGLang 을 **Pod** 로 올린다. 모델 가중치는 PVC(10장) |
| **B. 안 된다** | Pod 가 `Pending`(사건: `Insufficient nvidia.com/gpu`) 또는 `nvidia-smi` 실패, 노드 `gpu=`(빈 값) | 07장에서 SGLang 은 **호스트 Docker**(3주차 compose 그대로)에 두고, 클러스터의 게이트웨이가 `host.minikube.internal:30000` 로 붙는다. 실제 클라우드로 치면 'GPU 노드 풀을 따로 둔 것'과 같은 그림 |

B 가 나와도 실습은 모두 된다 — 모델 서버만 클러스터 밖이다. 어느 쪽이든 결과를 아래 표에 적는다.

**장애·복구** · `minikube start` 가 `--gpus` 에서 실패하면 옵션을 빼고 다시 만든다(`minikube delete -p agent` 뒤 `--gpus` 없이). 그 경우는 B 다.

**정리** · 이 장은 내리지 않는다 — 02장이 이 클러스터를 쓴다. `kubectl -n lab delete pod gpu-probe`.

**성공 확인** · `results/cloud/01_gpu_probe.txt` 가 있고, 아래 표를 채웠다.

| 항목 | 결과 (노트북에서 채움) |
|---|---|
| minikube 버전 / 드라이버 | |
| `--gpus=all` 로 start 됐나 | |
| 노드 `nvidia.com/gpu` 광고 수 | |
| Pod 의 `nvidia-smi -L` | |
| **판정 (A/B)** | |

## 02. 클러스터 둘러보기 — 노드 · 네임스페이스 · 첫 Pod

**완료 목표** · 노드 하나짜리 클러스터의 자원과 작업 구역을 읽고, 상담 화면 Pod 하나를 띄워 본다(이미지는 03장에서 만들므로 여기선 공개 이미지로 흐름만).

```
 그림 02 | minikube 한 대 = 제어부 + 노드 하나
   kubectl ─▶ API 서버 ─▶ 스케줄러 ─▶ 노드(agent) ─▶ Pod(컨테이너)
                └ etcd(상태 저장)                  └ 네임스페이스 lab 안에만 만든다
```

**실행**

```
 Ubuntu Bash | 02-001
   1  kubectl get nodes -o wide
   2  kubectl describe node agent | sed -n '/Allocatable/,/System Info/p'
   3  kubectl get ns
   4  kubectl -n lab run hello --image=python:3.12-slim --restart=Never -- python -c "print('lab ok')"
   5  kubectl -n lab wait --for=jsonpath='{.status.phase}'=Succeeded pod/hello --timeout=120s
   6  kubectl -n lab logs hello
   7  kubectl -n lab delete pod hello
```

1행 노드 목록과 주소·버전. `-o wide`: 내부 IP 와 컨테이너 런타임까지.
2행 노드 상세 중 '할당 가능' 자원(cpu·memory·`nvidia.com/gpu`)만 잘라 본다. 01장의 판정과 같아야 한다.
3행 네임스페이스 목록. `lab` 과 시스템용 `kube-system` 이 보인다.
4행 Pod 하나를 만들어 파이썬 한 줄을 실행한다. `--restart=Never`: 끝나면 그대로 둔다(Job 처럼). `--`: 뒤는 컨테이너 안 명령.
5행 Pod 가 `Succeeded` 될 때까지 기다린다(최대 120초 — 이미지 받기 포함).
6행 컨테이너 출력. `lab ok`.
7행 지운다.

**관찰** · `kubectl -n lab get events --sort-by=.lastTimestamp | tail` 로 Pod 하나가 만들어지는 사건 순서(Scheduled → Pulling → Pulled → Created → Started)를 본다. 클라우드의 모든 배포가 이 다섯 단계다.

**장애·복구** · 4행에서 `ImagePullBackOff` 면 인터넷(Docker Hub) 문제다. `minikube -p agent ssh -- docker pull python:3.12-slim` 로 노드 안에서 직접 받아 본다.

**정리** · 없음(Pod 는 7행에서 지움).

**성공 확인** · 2행의 `Allocatable` 에 `memory` 가 6Gi 근처, 6행 출력이 `lab ok`.
