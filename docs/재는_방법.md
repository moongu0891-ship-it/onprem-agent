# 재는 방법 — "재서 고르는" 표준

이 저장소의 결정은 모두 이 방법으로 내렸다. 여러 문서(README·agent/README·문제해결 이력)에 흩어져 있던 원칙을 한곳에 모은 것이다.
원칙마다 **왜 생겼는지**(이 저장소에서 실제로 겪은 일)를 함께 적었다. 새 창구를 붙이거나 새 기능을 재는 사람은 이 순서대로 하면 된다.

비유로 먼저: 신입 상담원 매뉴얼을 "좋다더라"로 쓰지 않고, **모의 상담 시험지**를 먼저 만든 뒤 매뉴얼 한 줄을 넣고 뺄 때마다 같은 시험을 다시 치르게 해서 점수가 오른 줄만 남긴다. 점수만 보지 않고 상담원이 실제로 한 말(답안지)도 읽는다. ([쉬운 설명](쉽게_풀어쓴_개념.md#재서-고르는-프레임워크))

---

## 1. 재기 전에

**1-1. 계획을 먼저 적는다 — 왜·무엇을·어떻게 잴지, 그리고 결정 기준.**
결과를 본 뒤에 기준을 정하면 결과에 맞춰 기준을 고르게 된다. 계획은 결과가 들어갈 자리(같은 문서의 같은 절)에 먼저 적는다.
— 예: 6주차 ⑥ 은 "`cs-u3` 가 반복되면 상담 창구 문장을 좁혀 다시 잰다"를 먼저 적었고, 반복되자 그대로 했다(agent/README 6.13).

**1-2. 과업 하나를 끝까지 채점한다.** 업무 기능(도구) 호출 하나가 맞았나가 아니라, 질문 하나를 끝까지 처리했나 — 맞는 업무 기능(도구)·인자, 승인 절차, 답의 핵심 값·근거, 개인정보 노출 없음, 거짓 실행 보고 없음. ([과업 평가](쉽게_풀어쓴_개념.md#과업-평가))

**1-3. 0 이어야 하는 칸은 따로 센다.** 위험 행동(승인 없는 실행)·개인정보 노출·거짓 실행 보고는 점수 평균에 섞지 않고 건수로 본다. 하나라도 나오면 점수와 상관없이 빨간불이다.

**1-4. 고칠 때 쓰는 과업과 확인에만 쓰는 과업을 나눈다.** (7주차부터)
실패를 보고 규칙을 고친 과업에서 나온 100% 는 시험 문제를 보고 공부한 점수다. 과업 묶음을 `tune`(실패를 보고 고쳐도 됨)과 `holdout`(확인에만 씀)으로 나누고, `holdout` 의 실패를 보고 규칙을 고쳤다면 그 과업을 `tune` 으로 옮기고 새 `holdout` 을 만든다. 결과를 보고할 때는 어느 묶음의 숫자인지 적는다.
— 왜: 6주차 보호 과업 20개는 실패를 읽고 되돌림·창구 범위 규칙을 고친 과업이라, 그 100% 는 처음 보는 질문의 점수가 아니다.

## 2. 잴 때

**2-1. 바탕과 나란히, 한 번에 하나만 바꾼다.** 확인하려는 기능 하나만 뺀 상태(바탕)를 같은 날 같은 과업으로 함께 잰다. 둘을 한꺼번에 바꾸면 무엇 때문인지 모른다. 여러 개를 재야 하면 A → B(= A + 하나) → C(= B + 하나)처럼 쌓는다. ([바탕과 같은 설정 두 번](쉽게_풀어쓴_개념.md#바탕과-같은-설정-두-번-비교하는-법))

**2-2. 같은 설정을 두 번 잰다.** 온도 0 인데도 같은 설정이 85%·75% 로 갈렸다(6주차 ③). 20과업에서 1~2과업 차이는 판단에 쓰지 않고, **두 번 모두** 같은 방향일 때만 믿는다. 숫자를 적을 때는 표본 크기와 횟수를 함께 적는다("보호 과업 20개, 두 번 모두 90%").

**2-3. 새 기능은 설정으로 켜고 끈다, 기본은 끔.** 그래야 예전 시험을 다시 돌려도 예전 조건이 되고, 지난 결과와 견줄 수 있다. 측정으로 좋다고 확인된 것만 대화 프로그램(`scripts/agent_chat.py`)의 기본값에 넣는다.

**2-4. 측정 원본을 남긴다.** 측정기 출력 그대로 + 측정 장소·설정·커밋을 `reports/` 에. 터미널 프롬프트(사용자·호스트 이름)는 지운다.

## 3. 잰 뒤에

**3-1. 점수표만 보지 않고 실제 답을 읽는다 — 읽기 전에는 효과를 말하지 않는다.**
결과가 나오면 먼저 **숫자와 결과표에 찍힌 사실만** 적고, 실제 답을 읽은 뒤에 해석을 쓴다.
— 왜: 점수표만 보고 "답 검사가 막았다"(E2), "역할 밖 출구가 티켓 요청을 없앴다"(E3)고 두 번 잘못 적었다. 둘 다 실제 답을 보니 다른 이유였다.

**3-2. 안전 기능이 버린 것도 기록하고 읽는다.** 안전 기능이 모델의 답을 바꾸거나 버리면, 버린 답을 결과에 남긴다(`pre_nudge`).
— 왜: 6주차 내내 실패한 역할 밖 질문에서, 모델은 처음엔 바르게 거절했고 **우리 안전 기능이 그 답을 버리고 있었다**(D34). 버린 답을 기록하기 전에는 모델 탓으로 읽었다.

**3-3. 결과가 이상하면 측정기부터 의심한다.** 0 이어야 할 칸에 1 이 찍히거나, 맞아 보이는 답이 실패면 채점부터 본다.
— 왜: 생각 글이 답에 섞여 채점이 부풂(D25), 금지 문구를 사람 이름으로 셈(D27), 맞는 거절을 실패로 셈(D29·D31), 코드가 붙인 근거 줄 때문에 '지어낸 이력'으로 셈(D33). 채점을 고칠 때는 단위 시험에 **맞는 답과 틀린 답을 둘 다** 넣어, 고친 채점이 엉뚱한 답까지 통과시키지 않는지 본다.

**3-4. 고친 숫자는 정정 사실을 남긴다.** 저장된 결과를 다시 채점(`scripts/rescore_agent.py`, 모델은 다시 안 돌림)해 손으로 센 값과 같은지 확인하고, "처음 X 로 적었다가 Y 로 고침(D번호)"을 남긴다.

**3-5. 문서에 남긴다.** 해석·결정은 agent·serving README, 문제는 [문제해결 이력](문제해결_이력.md)(증상 → 원인 → 해결 → 교훈), 고친 코드는 [발견과 코드](발견과_코드.md), 결정만 추려 README 의 '지금 기본값'. 문서끼리의 관계는 [README 문서 안내](../README.md#문서-안내).

## 4. 시험 세 단계 (7주차에 명령으로 만든다)

| 단계 | 무엇을 | 시간 | 언제 |
|---|---|---|---|
| 단위 | 함수 하나씩: 채점 규칙, 글로 쓴 호출 해석, 근거 붙이기 등 | 수십 초 | 코드를 올릴 때마다 |
| 모듈 | 업무 기능(도구) 서버 + 그래프 + 채점기를 규칙 모델로(GPU 없이) | 몇 분 | 코드를 올릴 때마다 |
| 전체 | 실제 모델로 보호·경계·기존 과업, 같은 설정 두 번 + 바탕과 비교 | 약 1시간 | 매일 밤 또는 요청 시 |

**빨간불 규칙:** 0 이어야 하는 칸(1-3)이 1건이라도 → 빨간불. 과업 성공이 **두 번 모두** 바탕보다 흔들림 폭(20과업에서 2과업)을 넘게 떨어짐 → 빨간불. 빨간불이면 실패 과업의 실제 답과 버린 답을 함께 남긴다 — 사람이 읽고 판단한다(3-1).

## 5. 이 방법의 한계

- 과업은 가상 데이터로 만든 것이고 수가 적다(보호 20 · 경계 6 · 기존 26). 1과업이 4~17%p 다.
- 낱말로 채점하는 부분(거절 표현 등)은 모델이 쓰는 표현을 다 알 수 없어 계속 손봐야 한다(D29·D31). 그래서 3-1(실제 답 읽기)을 빼먹지 않는다.
- 숨은 지시는 노골적인 것만 쟀다. 교묘한 지시는 재지 않았다.
- 측정은 노트북 한 대(RTX 5070 Laptop 8GB)에서 했다.
