# 쉽게 풀어쓴 개념

README 와 보고서에 나오는 용어를 비유로 풀어 둔 문서다. 결과와 결정은 README 에, 원리는 여기에 둔다.
각 항목은 **한 줄 요약 → 비유 → 이 프로젝트에서 어디에 나왔나** 순서로 적었다.

비유는 두 가지를 계속 쓴다.
- **검색 = 도서관.** 질문에 맞는 책(문서)을 찾아오는 일.
- **LLM 서빙 = 상담 창구.** 손님(사용자)이 서류(입력)를 내면 상담원(GPU 위의 모델)이 읽고 답을 한 글자씩 써 준다.

## 검색

### BM25 와 임베딩

**한 줄:** BM25 는 같은 낱말이 있는지 세고, 임베딩은 뜻이 가까운지 본다.

| | BM25 | 임베딩 (bge-m3) |
|---|---|---|
| 비유 | 책 뒤의 '찾아보기'(색인)에서 낱말로 찾는 사서 | 내용을 읽고 "이 책은 대략 이런 얘기"라고 기억하는 사서 |
| 잘하는 것 | `CRB-03` 처럼 한 글자만 달라도 다른 코드 | "설비 만지기 전에 뭘 해야 해요?"처럼 표현이 다른 질문 |
| 못하는 것 | 낱말이 안 겹치는 질문 | `CRB-01` 과 `CRB-03` 을 거의 같다고 봄 |

**이 프로젝트에서:** 문서를 2,445개로 키우자 임베딩 단독의 코드 질문 정답률이 1.00 → 0.31 로 무너졌다(README 2주차).

### 라우팅

**한 줄:** 질문을 보고 어느 사서에게 보낼지 정한다.

**비유:** 질문에 코드(`LVL-06`)가 있으면 '찾아보기' 사서(BM25)에게, 없으면 '내용 기억' 사서(임베딩)에게 보낸다. 각자 잘하는 질문만 맡긴다.

**이 프로젝트에서:** 기본 검색 방식. 전체 정답률 0.94~0.96.

### 의도 필터

**한 줄:** 어느 서가에서 찾을지 먼저 정한다.

**비유:** 도서관에 '설비 매뉴얼' 서가(45절)와 '정비 일지' 서가(2,400건)가 있다. "2025년 7월 1호기 **이력**"이면 일지 서가만, "어떻게 **조치**하나요"면 매뉴얼 서가만 찾는다.
판단은 모델 없이 규칙(날짜·호기·"이력" 같은 말이 있는지)으로 한다.

**이 프로젝트에서:** 47문항 중 오분류 0. 매뉴얼을 묻는 코드 질문에서 같은 코드가 적힌 일지가 끼어드는 걸 막아 코드 질문을 0.92 → 1.00 으로 올렸다.

### 리랭커

**한 줄:** 빨리 대충 30개를 고른 뒤, 그 30개만 꼼꼼히 다시 읽고 순서를 고친다.

**비유:** 채용. 지원자 2,445명을 서류로 30명까지 줄이고(1단계 검색), 30명만 면접한다(리랭커).
임베딩은 책을 **미리 혼자** 요약해 두고 질문 요약과 비교하므로 날짜 같은 세부가 요약에서 뭉개진다.
리랭커는 질문과 책을 **나란히 놓고 함께** 읽으니 "질문은 7월인데 이 기록도 7월이네"를 알아본다. 대신 한 명씩 면접하니 느리다(30개에 약 0.5초).

**이 프로젝트에서:** 이력 질문을 0 → 1.00 으로 올렸지만, 원인(날짜 표기)을 고치자 리랭커 없이 같은 점수가 나와서 껐다.

### 날짜 표기 통일

**한 줄:** "2025년 7월"과 "2025-07-14"를 같은 낱말로 바꾼다.

**비유:** '찾아보기' 사서는 글자가 똑같아야 같은 낱말로 본다. 질문의 "7"과 일지의 "07"은 다른 낱말이라, 같은 코드·같은 호기 기록 수십 건 중 날짜로 고르지 못했다.
둘 다 `2025-07` 로 적게 하자 바로 찾았다.

**이 프로젝트에서:** 토크나이저 한 줄 수정으로 이력 질문 0 → 1.00, 지연은 리랭커의 1/45. "비싼 모델을 붙이기 전에 실패 원인을 본다"의 사례.

### HNSW 근사 검색과 근사 재현율

**한 줄:** 모든 책과 비교하는 대신, 비슷한 책끼리 이어 둔 연결망을 따라가며 빨리 찾는다. 대신 가끔 놓친다.

**비유:** 책마다 "나랑 비슷한 책" 몇 권을 메모해 둔다(연결망 = 그래프). 질문이 오면 아무 책에서 출발해 메모를 따라 점점 비슷한 쪽으로 이동한다. 전부 비교하는 것보다 훨씬 빠르지만, 연결이 약한 책은 못 찾을 수 있다.
**근사 재현율** = 전부 비교했을 때의 진짜 상위 10권 중 몇 권을 되찾았나. 1.00 이면 놓친 게 없다.

**이 프로젝트에서:** pgvector 는 근사 재현율 평균 0.81 로 괜찮아 보였지만, 놓친 게 거의 다 **소수인 매뉴얼 절**이라 정답률이 0.70 → 0.30 으로 무너졌다. 다수인 일지 사이에서 매뉴얼의 연결이 약했다. 연결을 늘리는 설정(m=32 등)으로 회복.

### 인덱스 강제와 iterative scan

**한 줄:** PostgreSQL(pgvector)은 "먼저 찾고 나중에 거르기" 때문에 소수 문서를 필터로 찾으면 결과가 빈다.

**비유:** "매뉴얼 중에서 비슷한 책 10권"을 부탁했다.
- 표가 작을 때 PostgreSQL 은 서가를 **전부 훑는다**(순차 스캔). 정확하다.
- 표가 커지면 연결망(HNSW 인덱스)을 쓴다. 이때 사서는 도서관 **전체**에서 비슷한 책 128권을 가져오고, 그다음 매뉴얼만 남긴다. 매뉴얼은 1.8% 뿐이라 거르고 나면 한두 권만 남는다.
- **인덱스 강제** = 작은 표에서도 연결망을 쓰게 해서, 표가 커졌을 때의 상황을 미리 재현한 것.
- **iterative scan** = "거르고 나서 모자라면 더 가져와"(pgvector 0.8 이상).

**이 프로젝트에서:** 인덱스 강제 시 0.77 → 0.32, iterative scan 으로 0.77 회복. 오류 메시지 없이 데이터가 커질 때 조용히 정확도가 떨어지는 유형이라 결정 사항으로 남겼다.

## 서빙

### 토큰

**한 줄:** 모델이 읽고 쓰는 단위. 단어 조각이고, 한국어는 대략 1~2글자.

**이 프로젝트에서:** 에이전트 질문 하나는 입력 약 1,600토큰, 답은 128토큰으로 고정해 쟀다.

### 프리필과 디코드 (TTFT·TPOT)

**한 줄:** 상담원은 먼저 서류 전체를 읽고(프리필), 그다음 답을 한 글자씩 쓴다(디코드).

**비유:**
- **프리필 = 서류 읽기.** 서류가 길수록 오래 걸리고, 그동안 손님은 첫 마디를 기다린다 → **TTFT**(첫 글자까지 걸린 시간).
- **디코드 = 한 글자씩 쓰기.** 글자 하나를 쓸 때마다 상담원은 자기 두뇌(모델 가중치 약 3.4GB) 전체를 한 번 훑는다 → **TPOT**(글자 하나 나오는 간격).

**이 프로젝트에서:** 짧은 질문은 첫 글자 약 30ms, 에이전트 질문(긴 서류)은 약 80ms. 글자 간격은 12~14ms(사람이 읽는 속도보다 훨씬 빠름).

### 배칭

**한 줄:** 여러 손님의 다음 글자를 한 번에 같이 쓴다. 거의 공짜다.

**비유:** 상담원이 글자 하나를 쓸 때 두뇌 전체를 훑는 게 시간의 대부분이다. 한 번 훑을 때 손님 4명 몫의 다음 글자를 같이 쓰면, 시간은 거의 그대로인데 4명을 동시에 응대한다.

**이 프로젝트에서:** 동시 1명 → 4명으로 처리량 4배, 글자 간격은 11.2 → 11.5ms 로 거의 그대로.
단, 새 손님의 긴 서류 읽기(프리필)가 끼어들면 다른 손님의 글쓰기가 잠깐 멈춘다 → 에이전트 질문이 몰리면 첫 글자와 글자 간격이 함께 늘어난다.

### 접두사 캐시

**한 줄:** 앞부분이 같은 서류는 다시 읽지 않고 기억해 둔 걸 쓴다.

**비유:** 에이전트 질문에는 매번 똑같은 20쪽짜리 업무 지침서(시스템 프롬프트·도구 설명)가 맨 앞에 붙는다. 손님마다 다른 건 뒤의 질문 한 줄뿐.
캐시를 끄면 손님마다 20쪽을 다시 읽고, 켜면 "아까 읽었다" 하고 새 질문만 읽는다. 같은 대화를 이어 가면 앞 대화 전체도 기억한다.
주의: 지침서 **첫 장에서 글자 하나만 바꿔도** '처음 보는 서류'가 되어 전부 다시 읽는다. 그래서 지침서는 고정해 맨 앞에 둔다.
vLLM 은 automatic prefix caching, SGLang 은 radix cache 라고 부른다.

**이 프로젝트에서:** 에이전트 입력의 66~84% 를 재사용. 받을 수 있는 손님이 약 2배, 16명이 몰릴 때는 약속을 지킨 처리량이 15배 차이. 엔진 선택보다 큰 변수였다.

### 굿풋과 SLO, p50·p95

**한 줄:** 약속(SLO)을 지킨 손님만 센 처리량이 굿풋이다.

**비유:** 창구가 시간당 손님을 많이 받아도, 손님이 10분씩 기다렸다면 좋은 창구가 아니다.
"첫 마디 1초 이내, 글자당 0.05초 이내"(SLO)를 약속으로 정하고, 그걸 지킨 손님만 센다(굿풋).
손님을 늘리다 굿풋이 처리량보다 작아지기 시작하는 지점이 '실제로 받을 수 있는 인원'이다.
- **p50** = 손님 100명을 대기 시간순으로 세웠을 때 50번째. 보통 손님이 겪는 시간.
- **p95** = 95번째. 운 나쁜 손님이 겪는 시간. 서비스 품질은 이쪽을 본다.

**이 프로젝트에서:** 노트북으로 에이전트 손님 약 8명까지 전원 약속을 지켰다.

### 양자화

**한 줄:** 모델의 숫자를 덜 정밀하게 저장해 크기를 줄인다.

**비유:** 두뇌의 요약본. 숫자 하나를 16비트 대신 8비트(Q8_0)로 적어 크기가 절반이 된다. 글자 하나마다 두뇌 전체를 훑으므로 두뇌가 가벼우면 글자를 빨리 쓴다. 대신 아주 조금 덜 정확할 수 있다.

**이 프로젝트에서:** llama.cpp 가 혼자 쓸 때 가장 빨랐던(글자 간격 7.4ms) 이유. 엔진이 좋아서가 아니라 양자화의 효과라 엔진 비교와 구분해서 적었다.

### CUDA 그래프

**한 줄:** GPU 에 시킬 일 수백 개를 한 번 녹화해 두고, 다음부터 "녹화한 대로 해" 한 번으로 재생한다.

**비유:** CPU = 매니저, GPU = 주방.
- **그래프 없이:** 매니저가 "양파 썰어", "기름 둘러", "볶아"… 를 한 단계씩 소리쳐 지시한다. 글자 하나에 이런 지시가 수백 번. 주방은 빠른데 지시 전달 시간이 쌓여 주방이 논다.
- **그래프 사용:** 순서를 **레시피 카드**로 한 번 적어 두고(녹화), 이후엔 "이 카드대로" 한마디로 끝(재생).
- 카드는 **인분(동시 손님 수)마다 따로** 만들어야 한다. 5~8명이면 8인분 카드를 쓰고, 카드보다 손님이 많으면 다시 한 단계씩 지시해야 해서 느려진다.
- 카드도 보관 자리(GPU 메모리)가 필요해서, 메모리가 작은 GPU 에서는 엔진이 카드를 적게 만든다.
- 모델이 작을수록 계산 하나하나가 금방 끝나 지시 전달 시간의 비중이 커지므로 효과가 크다.
- 통신으로 비유하면: 매번 신호를 주고받으며 경로를 설정하는 것과, 경로를 미리 만들어 두고 바로 흘려보내는 것의 차이. 미리 만들어 둔 경로는 빠르지만 경로마다 자원을 차지한다.

**이 프로젝트에서:** 노트북의 SGLang 은 1·2·4·8인분 카드만 만들었다(시작 로그 `bs=[1, 2, 4, 8]`, GPU 여유 0.3GB). 동시 16명에서 글자 간격이 12 → 20ms 로 뛴 원인으로 추정, 16인분까지 만들게 해서 비교 측정 중(문제해결 이력 D14).

### 게이트웨이

**한 줄:** 손님(에이전트)은 접수 창구 하나만 알고, 어느 상담원에게 보낼지는 창구가 정한다.

**비유:** 에이전트는 상담원 이름(엔진 주소)을 몰라도 된다. "agent-llm 에게"라고만 하면 창구(LiteLLM)가 1순위 상담원(vLLM)에게 보내고, 그 상담원이 자리를 비우면 대체 상담원(llama.cpp)에게 넘긴다. 엔진 교체, 장애 대체, 요청 기록을 한곳에서 한다.

**이 프로젝트에서:** 창구를 거쳐도 첫 글자 +7~85ms, 처리량 −4% 이내라 유지하기로 했다.

### 도구 호출

**한 줄:** 모델이 직접 답하지 않고 "매뉴얼 검색", "작업 이력 조회" 같은 기능을 불러 달라고 요청하는 것.

**비유:** 상담원이 모르는 걸 지어내지 않고 "전산에서 조회해 볼게요" 하고 조회 화면에 호기·코드·연월을 입력하는 것. 정확도는 두 가지다 — **맞는 화면을 열었나**(도구 선택), **칸을 맞게 채웠나**(인자).
엔진마다 모델의 출력을 이 요청 형식으로 바꾸는 부품(파서)이 다르다.

**이 프로젝트에서:** 세 엔진 모두 형식 오류 0. 세 엔진이 똑같이 "급하지 않아요"를 우선순위 '보통'으로 넣는 실수를 했다 → 엔진이 아니라 1.7B 모델의 한계. 에이전트에는 더 큰 모델을 재 보기로 했다.
