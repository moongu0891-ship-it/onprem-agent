# 쉽게 풀어쓴 개념

README 와 보고서에 나오는 용어를 비유로 풀어 둔 문서다. 결과와 결정은 README 에, 원리는 여기에 둔다.
각 항목은 **한 줄 요약 → 비유 → 이 프로젝트에서 어디에 나왔나** 순서로 적었다.

비유는 두 가지를 계속 쓴다.
- **검색 = 도서관.** 질문에 맞는 책(문서)을 찾아오는 일.
- **LLM 서빙 = 상담 창구.** 손님(사용자)이 서류(입력)를 내면 상담원(GPU 위의 모델)이 읽고 답을 한 글자씩 써 준다.

용어 규칙 — 이 저장소의 문서는 아래처럼 쓴다.
- **시험 조건**: 결과표의 각 행. 같은 과업을 설정만 바꿔 다시 돌린 것 하나하나(예: "Qwen3-4B · 생각 켬 · 안전 기능 끔"). '줄'이라고 쓰지 않는다.
- **모델 이름은 줄이지 않는다**: Qwen3-4B(FP8), Qwen3-1.7B 처럼 전체 이름으로. '4B', '1.7B' 만 쓰지 않는다(코드의 식별자 `sglang-4b`, `qwen3-4b` 는 예외).
- **안전 기능**: 그래프에 코드로 넣은 되돌림·근거 자동·안전 질문 검색 같은 기능. '장치'라고 쓰지 않는다(하드웨어로 들린다).
- **업무 기능(도구)**: 이 저장소의 문서는 **업무 기능(도구)** 이라고 쓴다. AI 가 직접 못 하는 일(매뉴얼 찾기, DB 조회, 작업 요청 등록)을 대신 해 주는 프로그램 기능이다. 업계 용어는 '도구(tool)', 그래서 코드·결과에는 `tool_calls`, `tools` 처럼 영어로 남아 있다. AI 에게 보내는 프롬프트 안의 '도구'는 측정 조건이 바뀌지 않도록 그대로 두었다.

## 검색

### Recall@3 과 MRR

**한 줄:** 검색 성적표. Recall@3 은 "정답이 상위 3개 안에 들었나", MRR 은 "정답이 몇 번째에 나왔나"를 점수로 본다.

**비유:** 사서에게 책을 부탁했을 때
- **Recall@3**(R@3) = 사서가 가져온 앞의 세 권 안에 원하던 책이 있었던 비율. 질문 100개 중 94개면 0.94.
- **MRR** = 원하던 책이 1번째면 1점, 2번째면 1/2점, 3번째면 1/3점… 을 평균한 것. 1등으로 가져올수록 높다.
- **R@1** 은 첫 번째 책이 바로 정답인 비율.

**이 프로젝트에서:** 에이전트는 상위 몇 개 문서만 읽고 답하므로 R@3 을 주 지표로 쓴다. 질문 유형(코드·바꿔 말하기·어려운·이력)별로 따로 채점한다 — 평균 하나로 뭉치면 약점이 숨는다.

### BM25 와 임베딩

**한 줄:** BM25 는 같은 낱말이 있는지 세고, 임베딩은 뜻이 가까운지 본다.

| | BM25 | 임베딩 (bge-m3) |
|---|---|---|
| 비유 | 책 뒤의 '찾아보기'(색인)에서 낱말로 찾는 사서 | 내용을 읽고 "이 책은 대략 이런 얘기"라고 기억하는 사서 |
| 잘하는 것 | `CRB-03` 처럼 한 글자만 달라도 다른 코드 | "설비 만지기 전에 뭘 해야 해요?"처럼 표현이 다른 질문 |
| 못하는 것 | 낱말이 안 겹치는 질문 | `CRB-01` 과 `CRB-03` 을 거의 같다고 봄 |

**이 프로젝트에서:** 문서를 청크 2,445개(매뉴얼 45절 + 정비 이력 2,400건)로 키우자 임베딩 단독의 코드 질문 정답률이 1.00 → 0.31 로 무너졌다(README 2주차).

### 토크나이저 (형태소 분석)

**한 줄:** 문장을 검색에 쓸 낱말 단위로 쪼개는 부품. BM25 는 이 낱말이 같은지만 본다.

**비유:** 찾아보기(색인)에 올릴 낱말을 고르는 사람. "밸브를"과 "밸브의"는 조사를 떼고 둘 다 "밸브"로 올린다(Kiwi 형태소 분석).
그런데 그대로 쪼개면 경보 코드 `CRB-03` 이 `CRB`·`-`·`03` 으로 흩어져 `SPK-03` 과 `03` 이 겹친다. 그래서 코드는 먼저 떼어 **통째로** 올린다.

**이 프로젝트에서:** 코드 통째 보존(1주차), 날짜·호기 표기 통일(2주차)이 모두 이 부품에서 했다(`tokenize_ko.py`).

### 하이브리드 검색과 RRF

**한 줄:** BM25 와 임베딩 두 사서의 추천 목록을 하나로 합치는 방법. RRF 는 '순위'만 보고 합친다.

**비유:** 두 사서가 각자 책 순위표를 낸다. RRF(Reciprocal Rank Fusion)는 각 책에 "1등이면 큰 점수, 뒤로 갈수록 작은 점수"를 주고 두 표의 점수를 더해 새 순위를 만든다. 점수 단위가 서로 달라도 순위만 쓰니 합치기 쉽다.
업계에서 흔히 권하는 기본값이지만, 한 사서가 엉뚱한 책을 상위에 올리면 그 순위가 섞여 들어와 정답을 밀어낸다.

**이 프로젝트에서:** bge-m3 로 재 보니 같은 무게 하이브리드가 벡터 단독보다 **낮았다**(어려운 질문 0.75 → 0.62). BM25 무게를 0.3 으로 낮춰도 회복되지 않았다 → 합치지 않고 질문에 따라 한쪽으로 보내는 [라우팅](#라우팅)을 택했다.

### 라우팅

**한 줄:** 질문을 보고 어느 사서에게 보낼지 정한다.

**비유:** 질문에 코드(`LVL-06`)가 있으면 '찾아보기' 사서(BM25)에게, 없으면 '내용 기억' 사서(임베딩)에게 보낸다. 각자 잘하는 질문만 맡긴다.

**이 프로젝트에서:** 기본 검색 방식의 뼈대. 라우팅만 R@3 0.94~0.95, [의도 필터](#의도-필터)를 앞에 붙인 지금 기본값은 0.96.

### 의도 필터

**한 줄:** 어느 서가에서 찾을지 먼저 정한다.

**비유:** 도서관에 '설비 매뉴얼' 서가(45절)와 '정비 일지' 서가(2,400건)가 있다. "2025년 7월 1호기 **이력**"이면 일지 서가만, "어떻게 **조치**하나요"면 매뉴얼 서가만 찾는다.
판단은 모델 없이 규칙(날짜·호기·"이력" 같은 말이 있는지)으로 한다.

**이 프로젝트에서:** 47문항 중 오분류 0. 매뉴얼을 묻는 코드 질문에서 같은 코드가 적힌 일지가 끼어드는 걸 막아 코드 질문을 0.92 → 1.00 으로 올렸다.

### 리랭커

**한 줄:** 빨리 대충 30개를 고른 뒤, 그 30개만 꼼꼼히 다시 읽고 순서를 고친다.

**비유:** 채용. 지원자 2,445명을 서류로 30명까지 줄이고(1단계 검색), 30명만 면접한다(리랭커).
임베딩은 책을 **미리 혼자** 요약해 두고 질문 요약과 비교하므로 날짜 같은 세부가 요약에서 뭉개진다.
리랭커는 질문과 책을 **나란히 놓고 함께** 읽으니 "질문은 7월인데 이 기록도 7월이네"를 알아본다. 대신 한 명씩 면접하니 느리다(30개에 약 0.5초).

**예:** "2025년 7월 1호기 LVL-06 경보 이력 알려줘"
| 1단계 순위 | 후보 | 1단계 점수 | 리랭커 점수 |
|---|---|---|---|
| 1 | 2024-03-02 1호기 LVL-06 경보, 센서 청소 | 12.1 | 0.08 |
| 2 | 2025-01-19 1호기 LVL-06 경보, 배선 점검 | 12.0 | 0.05 |
| … | (같은 코드·같은 호기 기록 수십 건, 점수가 거의 같음) | | |
| 17 | **2025-07-14 1호기 LVL-06 경보, 레벨 센서 교체** ← 정답 | 11.2 | **0.97** → 1위로 |

"1호기·LVL-06·경보"는 모든 후보에 같으니 1단계는 날짜로만 가를 수 있는데, 1단계는 "7월"과 "07"을 같은 것으로 못 봤다. 리랭커는 질문과 기록을 함께 읽어 날짜를 맞췄다. (표의 점수는 원리를 보이려는 예시)
2,445개 전부를 리랭커로 읽으면 질문당 40초쯤 걸린다 — 그래서 1단계로 줄인 30개만 읽는다.

**이 프로젝트에서:** 이력 질문을 0 → 1.00 으로 올렸지만, 원인(날짜 표기)을 고치자 리랭커 없이 같은 점수가 나와서 껐다.

### 날짜 표기 통일

**한 줄:** "2025년 7월"과 "2025-07-14"를 같은 낱말로 바꾼다.

**비유:** '찾아보기' 사서는 글자가 똑같아야 같은 낱말로 본다. 질문의 "7"과 일지의 "07"은 다른 낱말이라, 같은 코드·같은 호기 기록 수십 건 중 날짜로 고르지 못했다.
둘 다 `2025-07` 로 적게 하자 바로 찾았다.

**이 프로젝트에서:** 토크나이저 한 줄 수정으로 이력 질문 0 → 1.00, 지연은 리랭커의 1/45. "비싼 모델을 붙이기 전에 실패 원인을 본다"의 사례.

### HNSW 근사 검색과 근사 재현율

**한 줄:** 모든 책과 비교하는 대신, 비슷한 책끼리 이어 둔 연결망을 따라가며 빨리 찾는다. 대신 가끔 놓친다.

**비유:** 책마다 "나랑 비슷한 책" 몇 권을 메모해 둔다(연결망 = 그래프). 질문이 오면 아무 책에서 출발해 메모를 따라 점점 비슷한 쪽으로 이동한다. 전부 비교하는 것보다 훨씬 빠르지만, 연결이 약한 책은 못 찾을 수 있다.
**근사 재현율** = 전부 비교했을 때의 진짜 상위 10권 중 몇 권을 되찾았나. 1.00 이면 놓친 게 없다.

**이 프로젝트에서:** pgvector 는 근사 재현율 평균 0.81 로 괜찮아 보였지만, 놓친 게 거의 다 **소수인 매뉴얼 절**이라 정답률이 0.70 → 0.30 으로 무너졌다. 다수인 일지 사이에서 매뉴얼의 연결이 약했다. 연결을 늘리는 설정(m=32 등)으로 회복.

### 인덱스 강제와 iterative scan

**한 줄:** PostgreSQL(pgvector)은 "먼저 찾고 나중에 거르기" 때문에 소수 문서를 필터로 찾으면 결과가 빈다.

**비유:** "매뉴얼 중에서 비슷한 책 10권"을 부탁했다.
- 표가 작을 때 PostgreSQL 은 서가를 **전부 훑는다**(순차 스캔). 정확하다.
- 표가 커지면 연결망(HNSW 인덱스)을 쓴다. 이때 사서는 도서관 **전체**에서 비슷한 책 128권을 가져오고, 그다음 매뉴얼만 남긴다. 매뉴얼은 1.8% 뿐이라 거르고 나면 한두 권만 남는다.
- **인덱스 강제** = 작은 표에서도 연결망을 쓰게 해서, 표가 커졌을 때의 상황을 미리 재현한 것.
- **iterative scan** = "거르고 나서 모자라면 더 가져와"(pgvector 0.8 이상).

**이 프로젝트에서:** 인덱스 강제 시 0.77 → 0.32, iterative scan 으로 0.77 회복. 오류 메시지 없이 데이터가 커질 때 조용히 정확도가 떨어지는 유형이라 결정 사항으로 남겼다.

## 서빙

### 토큰

**한 줄:** 모델이 읽고 쓰는 단위. 단어 조각이고, 한국어는 대략 1~2글자.

**이 프로젝트에서:** 에이전트 질문 하나는 입력 약 1,600토큰, 답은 128토큰으로 고정해 쟀다.

### KV 캐시

**한 줄:** 모델이 지금까지 읽은 내용(입력과 앞서 쓴 답)을 GPU 메모리에 적어 두는 공책. 다음 글자를 쓸 때마다 이걸 다시 본다.

**비유:** 상담원이 서류를 읽으며 적어 둔 메모. 메모가 있어야 다음 말을 이어 간다. 손님마다 메모가 필요하고, 서류가 길수록 메모도 길다.
GPU 메모리 = 모델 가중치(두뇌) + 메모 자리(KV 캐시). 메모 자리가 동시에 응대할 수 있는 손님 수를 정한다.
[접두사 캐시](#접두사-캐시)는 이 메모를 손님끼리 **같은 앞부분만큼 돌려쓰는** 것이다.

**이 프로젝트에서:** 노트북 8GB 에서 Qwen3-1.7B 가중치가 약 3.4GB(=3.2GiB, vLLM 로그 기준)를 차지하고 메모 자리는 2.4GiB(약 22,000토큰) — 8천 토큰짜리 요청이면 동시 2.7개분. 본 벤치마크를 24GB GPU 에서 하는 이유.
[양자화](#양자화)로 가중치를 줄이면 그만큼 메모 자리가 늘어 동시 처리 수가 는다.

### 에이전트 부하의 모양

**한 줄:** 에이전트가 모델에 보내는 요청은 일반 채팅과 세 가지가 다르다.

1. **매번 긴 앞부분이 반복된다.** 시스템 프롬프트와 업무 기능(도구) 정의가 모든 호출의 맨 앞에 붙는다 → [접두사 캐시](#접두사-캐시)가 크게 듣는다.
2. **출력은 짧다.** 대부분 "이 업무 기능(도구)을 이 인자로 불러 달라"는 짧은 JSON → 글자 쓰기보다 **입력 읽기(첫 글자 시간)**가 중요해진다.
3. **단계가 줄줄이 이어진다.** 업무 기능(도구) 호출 → 결과 받기 → 다음 호출… 각 단계가 앞 단계 응답을 기다린다 → 사용자가 체감하는 건 요청 하나가 아니라 **과업 전체 시간**(단계별 시간의 합)이다.

**비유:** 일반 채팅은 손님이 질문 하나 하고 긴 답을 듣는 상담. 에이전트는 매번 같은 업무 지침서를 낸 뒤 "이거 조회해 주세요"를 여러 번 짧게 주고받는 상담.

**이 프로젝트에서:** 첫 업무 기능(도구) 호출 시험에서 입력 179토큰(대부분 업무 기능(도구) 정의), 출력 29토큰. 서빙 측정의 요청 모양(rag·multiturn)과 24GB 측정 계획이 모두 이 모양에 맞췄다.

### 프리필과 디코드 (TTFT·TPOT)

**한 줄:** 상담원은 먼저 서류 전체를 읽고(프리필), 그다음 답을 한 글자씩 쓴다(디코드).

**비유:**
- **프리필 = 서류 읽기.** 서류가 길수록 오래 걸리고, 그동안 손님은 첫 마디를 기다린다 → **TTFT**(첫 글자까지 걸린 시간).
- **디코드 = 한 글자씩 쓰기.** 글자 하나를 쓸 때마다 상담원은 자기 두뇌(모델 가중치 약 3.4GB) 전체를 한 번 훑는다 → **TPOT**(글자 하나 나오는 간격).

**이 프로젝트에서:** 짧은 질문은 첫 글자 약 30ms, 에이전트 질문(긴 서류)은 약 80ms. 글자 간격은 12~14ms(사람이 읽는 속도보다 훨씬 빠름).

### 배칭

**한 줄:** 여러 손님의 다음 글자를 한 번에 같이 쓴다. 거의 공짜다.

**비유:** 상담원이 글자 하나를 쓸 때 두뇌 전체를 훑는 게 시간의 대부분이다. 한 번 훑을 때 손님 4명 몫의 다음 글자를 같이 쓰면, 시간은 거의 그대로인데 4명을 동시에 응대한다.

**이 프로젝트에서:** vLLM 짧은 질문에서 동시 1명 → 16명으로 처리량 0.58 → 8.09 요청/s(14배), 글자 간격은 13.4 → 14.4ms 로 거의 그대로(본 측정).
단, 새 손님의 긴 서류 읽기(프리필)가 끼어들면 다른 손님의 글쓰기가 잠깐 멈춘다 → 에이전트 질문이 몰리면 첫 글자와 글자 간격이 함께 늘어난다.
vLLM·SGLang 은 이걸 줄이려고 손님이 오는 대로 끼워 넣고(연속 배칭), 긴 서류는 조각내 읽으며 글쓰기와 번갈아 한다(청크 프리필). llama.cpp 는 이 능력이 약해 긴 입력이 몰리면 먼저 무너졌다.

### 접두사 캐시

**한 줄:** 앞부분이 같은 서류는 다시 읽지 않고 기억해 둔 걸 쓴다.

**비유:** 에이전트 질문에는 매번 똑같은 20쪽짜리 업무 지침서(시스템 프롬프트·업무 기능(도구) 설명)가 맨 앞에 붙는다. 손님마다 다른 건 뒤의 질문 한 줄뿐.
캐시를 끄면 손님마다 20쪽을 다시 읽고, 켜면 "아까 읽었다" 하고 새 질문만 읽는다. 같은 대화를 이어 가면 앞 대화 전체도 기억한다.
주의: 지침서 **첫 장에서 글자 하나만 바꿔도** '처음 보는 서류'가 되어 전부 다시 읽는다. 그래서 지침서는 고정해 맨 앞에 둔다.
vLLM 은 automatic prefix caching, SGLang 은 radix cache 라고 부른다.

**이 프로젝트에서:** 에이전트 입력의 66~84% 를 재사용. 받을 수 있는 손님이 2~3배, 16명이 몰릴 때는 약속을 지킨 처리량이 14~26배 차이. 엔진 선택보다 큰 변수였다.

### 굿풋과 SLO, p50·p95

**한 줄:** 약속(SLO)을 지킨 손님만 센 처리량이 굿풋이다.

**비유:** 창구가 시간당 손님을 많이 받아도, 손님이 10분씩 기다렸다면 좋은 창구가 아니다.
"첫 마디 1초 이내, 글자당 0.05초 이내"(SLO)를 약속으로 정하고, 그걸 지킨 손님만 센다(굿풋).
손님을 늘리다 굿풋이 처리량보다 작아지기 시작하는 지점이 '실제로 받을 수 있는 인원'이다.
- **p50** = 손님 100명을 대기 시간순으로 세웠을 때 50번째. 보통 손님이 겪는 시간.
- **p95** = 95번째. 운 나쁜 손님이 겪는 시간. 서비스 품질은 이쪽을 본다.

**이 프로젝트에서:** 노트북으로 에이전트 손님 약 8명까지 전원 약속을 지켰다.

### Hugging Face (모델 저장소)

**한 줄:** AI 모델 파일을 올리고 내려받는 공개 저장소. 모델계의 GitHub·앱스토어다. 설정의 `Qwen/Qwen3-4B-FP8` 은 그 안의 '회사/모델' 주소다.

**하는 일 — 받아 오기만, 돌리는 건 노트북:**
1. 처음 한 번 인터넷으로 모델 파일을 내려받는다(Qwen3-4B 는 약 4GB, 첫 실행에 19분 — 문제해결 이력 D19).
2. 받은 파일은 노트북 캐시(`~/.cache/huggingface`)에 두고 다음부터는 거기서 읽는다.
3. 계산은 노트북 GPU 가 한다. 질문·답이 Hugging Face 로 나가지 않는다.

**왜 모델이 그렇게 많은가:** Hugging Face 가 만든 게 아니라 **누구나 올리는 곳**이라서다. 큰 회사 모델(Qwen·Llama·Gemma), 대학·연구소 모델, 그리고 원본을 고쳐 다시 올린 변형(양자화판, 특정 분야 추가 학습판)이 섞여 있다. 원본 하나에서 변형이 수십~수백 개 나온다. 공개 모델은 2024년 9월 100만 개 → 2026년 8월 **300만 개**, 하루 약 3천 개씩 는다([Hugging Face 블로그](https://huggingface.co/blog/ivanfioravanti/three-million-models-and-counting)).

**용량은 얼마나 되나:** 정확한 총용량은 공개 자료에서 확인하지 못했다. 모델 하나가 수 GB(작은 것) ~ 수백 GB·1TB 넘게(큰 것)이니 전체는 페타바이트(PB, 100만 GB) 단위일 수밖에 없다.

**어떻게 감당하나:**
- **같은 내용은 한 번만 저장:** 파일을 잘게 쪼개 같은 조각은 한 번만 둔다(Xet 저장 방식). 원본을 조금 고친 변형 100개를 올려도 바뀐 조각만 늘어난다. 내려받는 사람은 완전한 파일 하나를 그대로 받는다.
- **자주 받는 것만 가까이:** 유튜브처럼 내려받기는 소수 인기 모델에 몰리고, 대다수는 거의 받지 않는다. 그래서 위치를 나눈다.

| 위치 | 비유 | 무엇을 두나 |
|---|---|---|
| 기본 저장소 | 본사 대형 창고 | **모든 모델의 원본 파일** (300만 개 전부, 실물) |
| 전 세계 복사 서버(CDN) | 지역마다 둔 편의점 | 인기 모델의 **복사본**만 — 가까워서 빨리 받는다 |

거의 안 받는 모델도 지워지거나 링크로 바뀌는 게 아니다. 본사 창고에서 직접 꺼내 와서 조금 느릴 뿐, 파일은 그대로 받을 수 있다. 통신으로 치면 자주 거는 번호는 단축번호·캐시에 두고 나머지는 전화번호부 전체에서 찾는 것.
- **비용:** 개인이 올리고 받는 건 무료. 기업용 요금제와 유료 서비스(모델 실행 서버 등)로 번다.

**이 프로젝트에서:**
- 받는 것: Qwen3-1.7B·Qwen3-4B(서빙 엔진이 켜질 때), bge-m3 임베딩·리랭커(검색이 처음 실행될 때).
- 모델이 많다는 건 고르기가 어렵다는 뜻이다. Qwen3-4B 하나에도 원본·FP8판·AWQ판이 있다 — 그래서 몇 개를 골라 직접 재 보고 정한다.
- 폐쇄망에서는 Hugging Face 에 접속할 수 없으므로, 모델 파일을 미리 받아 설치 묶음에 넣는다(7주차).
- 로그의 `HF_TOKEN` 경고는 "로그인 없이 받고 있다"는 안내일 뿐이다(문제해결 이력 F).

### 모델 크기 (Qwen3-1.7B · Qwen3-4B)

**한 줄:** 모델 이름 끝의 숫자는 **파라미터(매개변수) 개수**다. B 는 billion(10억). Qwen3-1.7B = 17억 개, Qwen3-4B = 40억 개.

**비유:** 파라미터는 모델이 공부하면서 조정해 둔 '경험의 손잡이'다. 손잡이가 많을수록 더 미묘한 것을 구별할 수 있다 — 대체로 더 똑똑하지만, 그만큼 GPU 메모리를 많이 차지하고 한 글자를 쓰는 데 계산도 많이 든다. 상담원 비유로는 신입(Qwen3-1.7B)과 몇 년 차(Qwen3-4B)의 차이.

**메모리 계산:** 파라미터 하나를 보통 2바이트(BF16)로 저장한다.

| 모델 | 파라미터 | 2바이트로 저장하면 | 이 프로젝트에서 |
|---|---|---|---|
| Qwen3-1.7B | 17억 | 약 3.4GB | 그대로 올림 (8GB GPU) |
| Qwen3-4B | 40억 | 약 8GB → 8GB GPU 에 안 들어감 | **FP8**(1바이트)로 줄여 약 4.2GB (SGLang 로그 `mem usage=4.19 GB`) |
| 참고: 8B · 14B · 32B · 70B | 80억 ~ 700억 | 16GB ~ 140GB | 24GB 이상 GPU 나 여러 장이 필요 |

**이 프로젝트에서:** 크다고 저절로 낫지는 않았다. 에이전트 1차 측정에서 Qwen3-4B(27%)가 Qwen3-1.7B(46%)보다 낮았다 — Qwen3-4B 는 이력 과업에서 업무 기능(도구)을 부른 뒤 날짜·부품을 맞게 쓰기도 했지만(근거 번호만 빠뜨림), 번호가 없는 질문에서 업무 기능(도구)을 건너뛰고 바로 답하는 경향이 컸다(문제해결 이력 D21). 모델 크기는 측정으로 고른다.

### 양자화

**한 줄:** 모델의 숫자를 덜 정밀하게 저장해 크기를 줄인다.

**비유:** 두뇌의 요약본. 숫자 하나를 16비트 대신 8비트(Q8_0)로 적어 크기가 절반이 된다. 글자 하나마다 두뇌 전체를 훑으므로 두뇌가 가벼우면 글자를 빨리 쓴다. 대신 아주 조금 덜 정확할 수 있다.

**이 프로젝트에서:** llama.cpp 가 혼자 쓸 때 가장 빨랐던(글자 간격 7.4ms) 이유. 엔진이 좋아서가 아니라 양자화의 효과라 엔진 비교와 구분해서 적었다.

### CUDA 그래프

**한 줄:** GPU 에 시킬 일 수백 개를 한 번 녹화해 두고, 다음부터 "녹화한 대로 해" 한 번으로 재생한다.

**비유:** CPU = 매니저, GPU = 주방.
- **그래프 없이:** 매니저가 "양파 썰어", "기름 둘러", "볶아"… 를 한 단계씩 소리쳐 지시한다. 글자 하나에 이런 지시가 수백 번. 주방은 빠른데 지시 전달 시간이 쌓여 주방이 논다.
- **그래프 사용:** 순서를 **레시피 카드**로 한 번 적어 두고(녹화), 이후엔 "이 카드대로" 한마디로 끝(재생).
- 카드는 **인분(동시 손님 수)마다 따로** 만들어야 한다. 5~8명이면 8인분 카드를 쓰고, 카드보다 손님이 많으면 다시 한 단계씩 지시해야 해서 느려진다.
- 카드도 보관 자리(GPU 메모리)가 필요해서, 메모리가 작은 GPU 에서는 엔진이 카드를 적게 만든다.
- 모델이 작을수록 계산 하나하나가 금방 끝나 지시 전달 시간의 비중이 커지므로 효과가 크다.
- 통신으로 비유하면: 매번 신호를 주고받으며 경로를 설정하는 것과, 경로를 미리 만들어 두고 바로 흘려보내는 것의 차이. 미리 만들어 둔 경로는 빠르지만 경로마다 자원을 차지한다.

**이 프로젝트에서:** 노트북의 SGLang 은 1·2·4·8인분 카드만 만들었다(시작 로그 `bs=[1, 2, 4, 8]`, GPU 여유 0.3GB). 그래서 동시 16명에서 글자 간격이 12 → 20ms 로 뛰었다. 16인분까지 만들게 하자 글자 간격 12.6ms, 처리량 +53% 로 회복했고, 1~8명 구간은 그대로였다(카드가 이미 있던 구간). 이 결과로 게이트웨이 1순위 엔진이 vLLM 에서 SGLang 으로 바뀌었다(문제해결 이력 D14).

### 서빙 엔진: vLLM · SGLang · llama.cpp

**한 줄:** 모델을 메모리에 올려 두고, 질문이 오면 답을 만들어 돌려주는 프로그램. 셋 다 같은 일을 하지만 태생이 다르다.

| | vLLM · SGLang | llama.cpp |
|---|---|---|
| 만든 목적 | 여러 사용자를 받는 GPU 서버 | 개인 PC·노트북·휴대폰 같은 작은 기기 |
| 도는 곳 | NVIDIA GPU | GPU, **CPU 만으로도** (맥, 라즈베리파이까지) |
| 모델 형식 | 원본 그대로 (BF16) | GGUF 압축 형식 (양자화) |
| 설치 | Python·CUDA 등 무거움 | 실행 파일 하나 |
| 여러 명 동시 응대 | 강함 (연속 배칭·접두사 캐시·CUDA 그래프) | 약함 |

**비유:** vLLM·SGLang 은 큰 콜센터 — 여러 손님을 동시에 능숙하게 받지만 전용 건물(GPU 서버)이 있어야 한다.
llama.cpp 는 어디든 들고 가는 출장 상담원 — 노트북 하나, GPU 없는 컴퓨터에서도 일하지만 손님이 몰리면 버거워한다.

**이 프로젝트에서:**
- 1순위는 SGLang(CUDA 그래프 상한 16). 노트북의 모든 동시 사용자 구간에서 vLLM 보다 처리량·굿풋이 높았다.
- llama.cpp 는 혼자 쓸 때 가장 빨랐지만(양자화 효과) 동시 4명부터 에이전트 질문의 약속 시간을 못 지켰다 → **주력이 아니라 비상용·소형 환경용.**
  게이트웨이의 대체 엔진으로 CPU 에서 돌린다(8GB GPU 에 엔진 두 개가 동시에 못 올라가므로 GPU 자원을 두고 다투지 않게).
  GPU 없는 지점·현장 단말에 에이전트를 넣을 때의 선택지이기도 하다.

### 게이트웨이 (LiteLLM)

**한 줄:** LLM 앞에 두는 중계 서버. 에이전트는 게이트웨이에만 요청하고, 게이트웨이가 실제 엔진에 전달한다.

**비유 1 (상담 창구):** 에이전트는 상담원 이름(엔진 주소)을 몰라도 된다. "agent-llm 에게"라고만 하면 창구가 1순위 상담원(SGLang)에게 보내고, 그 상담원이 자리를 비우면 대체 상담원(CPU llama.cpp)에게 넘긴다.

**비유 2 (통신):** 교환기·SIP 프록시와 거의 같은 역할이다.

| 통신 | LiteLLM |
|---|---|
| 가입자는 대표번호만 누른다 | 에이전트는 `agent-llm-4b` 같은 이름만 안다(3주차 서빙 측정은 `agent-llm`) |
| 교환기가 실제 회선으로 연결한다 | LiteLLM 이 실제 엔진(SGLang)으로 보낸다 |
| 회선이 죽으면 우회 경로로 돌린다 | SGLang 이 죽으면 llama.cpp 로 돌린다 |
| 호 기록(CDR)·과금 | 요청 기록, 사용량·비용 집계 |
| 가입자 인증, 통화량 제한 | 접근 키, 사용자별 요청 한도 |

**왜 필요한가:** 게이트웨이가 없으면 엔진 주소와 장애 대체 규칙을 에이전트 코드에 직접 적어야 하고, 엔진을 바꿀 때마다 코드를 고쳐야 한다.
게이트웨이를 두면 엔진 교체·장애 대체·기록·접근 제한을 한곳에서 하고, 에이전트는 '모델을 부른다'에만 집중한다.
같은 역할의 다른 업무 기능(도구): Kong AI Gateway, Envoy 기반 AI 게이트웨이, 클라우드 업체 게이트웨이. LiteLLM 을 고른 이유는 오픈소스이고, 폐쇄망에 Docker 하나로 띄울 수 있고, vLLM·SGLang·llama.cpp 가 모두 쓰는 OpenAI 호환 형식을 그대로 받기 때문.

**이 프로젝트에서:**
- 비용이 작다: 거쳐 가도 첫 글자 +7~85ms, 처리량 −4% 이내.
- 장애 대체가 실제로 된다: 1순위 SGLang 을 정상 종료해도, 갑자기 강제 종료해도 요청 손실 0(대신 대체 중엔 약 40배 느림).
- 엔진 교체가 쉽다: 측정 결과로 1순위를 vLLM → SGLang 으로 바꿀 때 에이전트 쪽은 건드리지 않고 설정 파일 한 줄만 고쳤다.
- 5주차: 에이전트도 게이트웨이 이름(`agent-llm-4b`)으로 부른다. 엔진 직접과 품질이 같았고(96%) 시간은 약 3% 더 걸렸다. 일하는 도중 1순위 엔진을 강제로 꺼도 남은 과업이 CPU 대체 엔진으로 넘어가 모두 끝났고, 대체 엔진이 답한 답에는 "지금은 대체 엔진이라 느리고 정확도가 낮을 수 있다"는 안내가 자동으로 붙는다 — 교환기로 치면 대타 직원이 받으면서 "담당자가 자리를 비워 제가 대신 받았습니다"라고 먼저 말하는 것.


### 업무 기능(도구) 호출

**한 줄:** 모델이 직접 답하지 않고 "매뉴얼 검색", "작업 이력 조회" 같은 업무 기능(도구)을 불러 달라고 요청서를 쓰는 것. 실행은 프로그램이 하고, 모델은 결과를 읽고 답한다. 업계 용어는 tool calling(도구 호출).

**비유:** 상담원이 모르는 걸 지어내지 않고 "전산에서 조회해 볼게요" 하고 조회 화면에 호기·코드·연월을 입력하는 것. 정확도는 두 가지다 — **맞는 화면을 열었나**(업무 기능(도구) 선택), **칸을 맞게 채웠나**(인자).
엔진마다 모델의 출력을 이 요청 형식으로 바꾸는 부품(파서)이 다르다.

**이 프로젝트에서:** 세 엔진 모두 형식 오류 0. 세 엔진이 똑같이 "급하지 않아요"를 우선순위 '보통'으로 넣는 실수를 했다 → 엔진이 아니라 Qwen3-1.7B 모델의 한계. 에이전트에는 더 큰 모델을 재 보기로 했다.

## 에이전트

### 에이전트와 LangGraph

**한 줄:** 에이전트 = 모델이 "어떤 업무 기능(도구)을 쓸지" 정하고, 프로그램이 그 업무 기능(도구)을 실행해 결과를 다시 모델에 주는 **반복**. LangGraph 는 이 반복의 단계와 갈림길을 그림(그래프)으로 짜는 라이브러리.

**비유:** 상담원(모델)과 전산 담당(프로그램). 상담원이 "이력 조회해 주세요"라고 쪽지를 쓰면 전산 담당이 조회해서 결과를 돌려주고, 상담원은 결과를 보고 다음 쪽지를 쓰거나 손님에게 답한다.
LangGraph 는 이 쪽지가 오가는 길을 정한 업무 흐름도다 — "티켓 쪽지는 팀장 결재(승인)를 거쳐야 전산으로 간다", "쪽지가 6번 넘게 오가면 그만 쓰고 답하라" 같은 규칙을 흐름도에 그린다.

**이 프로젝트에서:** 모델 → (승인 관문) → 업무 기능(도구) 실행 → 모델 … 을 한 그래프로 짜고, 설비·상담 두 시나리오가 같은 그래프를 쓴다. [agent/README.md](../agent/README.md#1-설계)

### MCP (Model Context Protocol)

**한 줄:** 업무 기능(도구)을 에이전트 코드에 붙박지 않고, 정해진 규약으로 따로 띄운 '업무 기능(도구) 서버'에 붙이는 방법.

**비유:** 전산 담당과 주고받는 쪽지 양식을 회사 표준으로 정해 둔 것. 양식이 같으니 어느 상담원(에이전트)이든 같은 전산 창구(업무 기능(도구) 서버)를 쓸 수 있고, 전산 창구 쪽에서 권한·기록을 따로 관리할 수 있다.
USB 처럼 "꽂으면 되는" 표준 연결이라고 보면 된다.

**MCP 없이도 되지 않나:** 된다. 업무 기능(도구)은 결국 파이썬 함수라 에이전트 코드 안에 넣고 바로 불러도 이 프로젝트는 돈다. MCP 가 값을 하는 건 **업무 기능(도구)과 에이전트가 많아질 때**다.

| | MCP 없이 (함수를 에이전트 안에) | MCP 로 (업무 기능(도구) 서버를 따로) |
|---|---|---|
| 에이전트 3개 × 시스템 4개 | 연결 코드 12벌, 프레임워크마다 형식이 달라 다시 짬 | 업무 기능(도구) 서버 4개를 한 번 만들면 어느 에이전트든 연결 |
| 다른 AI 앱(Claude Desktop, IDE 등)에서 같은 업무 기능(도구) 쓰기 | 다시 만들어야 함 | 그대로 연결 |
| 누가 관리하나 | 에이전트 팀이 남의 시스템 코드까지 떠안음 | 고객 DB 팀이 고객 업무 기능(도구) 서버를 소유·관리 |
| 권한·기록 | 에이전트 프로그램 권한 = 업무 기능(도구) 권한 | 업무 기능(도구) 서버 단위로 권한·접근 기록을 따로 |

통신으로 치면 SIP 같은 표준 신호 규약이다. 규약이 정해져 있으니 어느 회사 단말이든 어느 회사 교환기에 붙는다. 표준이 없으면 장비 조합마다 연동 개발을 새로 한다.
대가도 있다: 프로세스 사이 통신이 하나 끼고, 잘못 쓰면 매 호출마다 서버를 새로 띄우는 함정이 있다(문제해결 이력 D17).

**이 프로젝트에서:** 설비용·상담용 MCP 서버 두 개. '서버'라고 해서 컴퓨터가 두 대인 게 아니라, 같은 컴퓨터에서 도는 **별도 프로그램(프로세스) 두 개**다. 시나리오마다 자기 창구 하나만 연결한다.

| 서버 | 띄우는 명령 | 업무 기능(도구)(창구에서 하는 일) | 뒤에 있는 것 |
|---|---|---|---|
| 설비(ops) | `python -m onprem_agent.agent.mcp_servers ops` | `search_manual` 매뉴얼 검색 · `get_work_orders` 작업 이력 조회 · `create_ticket` 작업 요청 등록(**승인 필요**) | 매뉴얼 검색 색인 + 작업 이력 SQL 표 |
| 상담(cs) | `python -m onprem_agent.agent.mcp_servers cs` | `get_customer` 고객 조회(이름·전화 가림) · `get_plan` 요금제 조회 · `search_terms` 약관·FAQ 검색 | 약관 검색 색인 + 고객·요금제 SQL 표 |

**왜 하나로 합치지 않고 둘로 나눴나:** 실제 회사라면 두 창구는 **다른 부서의 시스템**(생산 설비 DB · 고객 DB)에 붙어 있고 권한도 다르다. 설비 에이전트는 고객 정보를 볼 이유가 없으니, 애초에 상담 서버에 연결하지 않으면 실수로라도 볼 수 없다. 그리고 새 고객사에 붙일 때는 이 업무 기능(도구) 서버와 시스템 프롬프트만 바꾸면 된다(그래프·평가 코드는 그대로).

고객 이름·전화번호는 상담 서버에서부터 가려서 내보낸다(모델이 원문을 볼 일이 없게).
기본 연결 방식은 업무 기능(도구)을 부를 때마다 서버를 새로 띄워서, 한 번 띄운 서버에 계속 붙어 쓰게 바꿨다(문제해결 이력 D17).

### 지어내기 (환각, hallucination)

**한 줄:** AI 가 모르는 것을 모른다고 하지 않고, **그럴듯한 말을 지어내 자신 있게 답하는 것.**

**왜 생기나:** 언어 모델은 '사실을 꺼내는 기계'가 아니라 '그럴듯한 다음 글자를 이어 쓰는 기계'다. 정답을 모르는 질문에도 문장 모양은 자연스럽게 만들어 낸다. 작은 모델일수록 아는 것이 적어 더 자주 지어내고, 찾아보라는 지시를 건너뛰기도 한다.

**비유:** 신입 상담원이 전산 조회를 귀찮아해서 기억나는 대로 "그 요금제는 59,000원이에요"라고 답하는 것. 말투는 확신에 차 있는데 금액은 틀렸다. 손님은 틀린 줄 모른다 — 그래서 위험하다.

**이 프로젝트에서 (노트북 1차, 실제 답):**

| 질문 | 모델 | 한 일 | 답 | 사실 |
|---|---|---|---|---|
| CRB-06 경보 점검할 곳? | Qwen3-4B | 매뉴얼을 안 찾음 | "수직 풀링 시스템의 수평 풀링 펌프…" | 매뉴얼엔 보조 순환 펌프 P-22·B측 스트레이너. '수직 풀링'은 없는 말 |
| C0050 고객 요금제의 월 요금? | Qwen3-1.7B | 고객 조회를 건너뜀 | "59,000원입니다" | 고객의 요금제는 PLN-5G89, 89,000원 |
| 작업 요청 올려 줘 | Qwen3-4B | 티켓 업무 기능(도구)을 안 부름 | "티켓을 생성합니다" | 아무것도 만들지 않았다 (**행동을 지어냄**) |
| (여러 질문) | 둘 다 | 찾지 않음 | 답 끝에 "[근거: 1]" | 찾은 게 없으니 **출처도 지어낸 것** |

**막는 방법:** 프롬프트로 "지어내지 마"라고만 하면 작은 모델은 지키지 않았다. 그래서 프로그램 구조로 막는다. 그래프에 넣은 **안전 기능** 두 개(하드웨어가 아니라 코드, 설정 한 줄로 켜고 끈다) — 찾지 않고 답하면 되돌리고(되돌림), 출처는 실제로 찾은 결과에서 코드가 붙인다(근거 자동). 그리고 채점은 '매뉴얼을 읽어야만 쓸 수 있는 내용'(부품 번호·전화번호·수치)이 답에 있는지 본다. 효과는 노트북 2~5차 측정으로 확인했다 — 생각 모드와 함께 켜서 92%, 안전 질문 검색까지 더해 96%(agent/README 4.5·5.2).

### 안전 기능 (되돌림 · 근거 자동)

**한 줄:** AI 가 자주 하는 실수를 **프로그램이 대신 막아 주는 기능 두 개**. 하드웨어가 아니라 그래프 코드(`agent/graph.py`)에 넣은 기능이고, 설정 한 줄로 켜고 끈다 — `graph: {require_tool: true, auto_cite: true}`.

**안전 기능 ① 되돌림** (`require_tool`)
- 막는 실수: 매뉴얼·기록을 찾아보지 않고 아는 척 지어내기([지어내기](#지어내기-환각-hallucination)).
- 하는 일: 이번 질문에 업무 기능(도구)을 한 번도 쓰지 않고 답하려 하면 그 답을 내보내지 않고, "업무 기능을 **반드시 하나 골라라**"고 강제해 한 번 더 묻는다. 고를 수 있는 것 중에 '필요 없음'(`no_tool_needed`)도 있어서 인사·잡담은 그대로 통과한다.
- 예 (설명을 위한 흐름): "CRB-06 경보 뭘 점검해?" → AI 가 찾지 않고 "수직 풀링 시스템을 점검하세요" → 프로그램이 막고 "하나 골라" → AI 가 매뉴얼 검색을 골라 실제로 읽고 "보조 순환 펌프 P-22 를 점검하세요".
- 바뀐 과정: 2차에는 "먼저 찾아보라"는 **글**을 덧붙였는데, AI 가 그 글에 "시스템 확인 완료. 다음 질문은 도구를 사용하여 답변해야 합니다"처럼 글로만 대답했다(Qwen3-4B 13번 되돌려 업무 기능(도구) 호출 증가 0). 3차부터 API 의 '업무 기능(도구) 선택 필수'(`tool_choice="required"`)로 강제한다(문제해결 이력 D23).

**안전 기능 ② 근거 자동** (`auto_cite`)
- 막는 실수: 출처를 엉터리로 적기 — `[근거: 1, 2]` 처럼 순번을 적거나, 찾지도 않은 출처를 붙이거나, 프롬프트 예시 번호를 베끼기.
- 하는 일: AI 가 쓴 출처는 지우고, 이번 질문에서 **실제로 찾아본 자료**의 번호(`[OPS-CRB-06]`, `[WO-00125]`, `[TK-0001]`)를 프로그램이 답 끝에 붙인다. 찾아본 게 없으면 출처도 붙지 않는다.
- 예: AI 가 쓴 답 "…감시 강화로 처리했습니다. [근거: 1, 2]" → 사용자가 받는 답 "…감시 강화로 처리했습니다. [근거: WO-00125]"
- AI 가 원래 쓴 답은 따로 보관해, 채점에서 '모델 스스로 근거'(AI 실력)를 따로 잰다. 그리고 근거를 코드가 붙이므로 채점은 근거만이 아니라 **내용**(부품 번호·날짜·금액)도 본다 — 근거는 맞는데 내용을 지어내면 실패.

**왜 필요한가:** "지어내지 마", "출처를 정확히 적어"라고 **글로 부탁해도 작은 AI 는 잘 지키지 않았다.** 그래서 구조로 막는다. 처음부터 같은 생각으로 넣어 둔 장치가 둘 더 있다 — 티켓을 만들기 전 **사람 승인**, 고객 이름·전화번호를 **업무 기능(도구) 서버에서부터 가리기**. 이 둘 덕에 모든 측정에서 위험 행동·개인정보 노출이 0 이었고, 이번 두 안전 기능은 같은 방식으로 지어내기와 가짜 출처를 막는다.

**효과 (노트북, Qwen3-4B, 과업 26개):**

| 생각 모드 | 안전 기능 | 과업 성공 |
|---|---|---|
| 끔 | 끔 → 켬 | 46% → 54% (+8%p) |
| 켬 | 끔 → 켬 | 62% → **92%** (+30%p) |

(생각 모드만 켠 시험 조건은 처음 69% 로 적었다가, 생각 글이 답에 섞여 채점이 부푼 것을 찾아 다시 채점해 62% 로 고쳤다 — 문제해결 이력 D25.)

같은 생각으로 5주차에 하나를 더했다 — **안전 질문 검색**(`safety_search`). "감전·전원 차단·잠금·잔압" 같은 말이 들어간 질문은 AI 에게 묻기 전에 프로그램이 먼저 매뉴얼을 찾아 건넨다. 프롬프트에 "꼭 매뉴얼을 찾아라"라고 써도 AI 가 엉뚱한 업무 기능(도구)을 골라서다(D26). 켜자 Qwen3-4B 96%, 업무 기능(도구)·인자 100%(안전 질문은 프로그램이 대신 검색한 몫이 들어 있다).

생각 모드가 꺼져 있으면 효과가 작다 — AI 가 업무 기능(도구)을 부를 판단을 못 하면 근거를 붙여 줄 결과가 없다. **생각할 줄 알아야 안전 기능도 제 몫을 한다**([생각 모드](#생각-모드-thinking), agent/README 4.5).

### 생각 모드 (thinking)

**한 줄:** AI 가 답을 쓰기 전에 **속으로 먼저 따져 보는 글**을 쓰게 하는 기능. 그 글은 사용자에게 보이면 안 되고 최종 답만 보내야 한다. 엔진의 생각 글 분리기를 켜지 않으면 생각 글이 답에 섞여 오므로(5주차 발견, D25), 이 프로젝트는 그래프의 마지막 단계에서 항상 떼어 낸다.

**비유:** 신입 상담원에게 "바로 대답하지 말고, 메모지에 먼저 정리해 보고 답해"라고 하는 것. 메모지에 "이 손님은 요금을 묻네 → 요금은 기억에 의존하면 틀리니 전산 조회부터 → 고객 번호가 C0050 이니 고객 조회 → 거기 나온 요금제로 요금 조회"처럼 순서를 적고 나면, 실제로도 그 순서대로 움직인다. 메모 없이 바로 말하면 떠오르는 대로 "59,000원이요"라고 해 버린다.

**대가:** 메모를 쓰는 시간. 생각 글은 수백~수천 토큰이라 답이 늦어지고, 길이가 질문마다 들쭉날쭉하다.

**이 프로젝트에서:**
- 3주차 서빙 속도 측정에서는 **껐다** — 출력 길이가 들쭉날쭉하면 엔진 속도를 공정하게 비교할 수 없어서.
- 4주차 에이전트 측정도 그 설정을 물려받아 꺼 둔 채 시작했고, Qwen3-4B 는 업무 기능(도구)을 부르지 않고 "부르겠습니다"라고 글로만 썼다(27~54%).
- 3차에서 켜자 같은 Qwen3-4B 가 **92%** — 규칙 기준선(88%)을 처음 넘었다. 대신 과업당 13초로 약 5배 느려졌다(문제해결 이력 D24).
- 4차에 나눠 보니 생각 모드만 켜면 62%, 안전 기능까지 92%. 5주차에 '첫 단계(무엇을 찾을지 고를 때)만 생각'을 재 보니 시간은 절반(15.6 → 7.3초)인데 85% — 결과를 보고 다음을 고르는 단계에도 생각이 필요했다.
- 교훈: 속도를 재기 위해 정한 설정이 품질 측정의 결론을 바꿨다. 설정은 측정 목적마다 다시 정한다.

### 사람 승인 (human-in-the-loop) 과 체크포인터

**한 줄:** 상태를 바꾸는 일(티켓 생성 등)은 실행 직전에 멈추고 사람에게 묻는다. 기다리는 동안의 상태는 DB(체크포인터)에 저장해, 프로그램이 껐다 켜져도 이어 간다.

**비유:** 결재 서류. 상담원이 작업 지시서를 올리면 팀장 책상(승인 대기)에 놓이고, 팀장이 서명해야 현장으로 간다. 팀장이 퇴근했다 다음 날 와도 서류는 책상 위(DB)에 그대로 있다.
반려하면 지시서는 현장에 가지 않고, 상담원은 "반려됐습니다"를 손님에게 알린다.

**이 프로젝트에서:** LangGraph 의 `interrupt` 로 멈추고 `Command(resume=...)` 로 이어 간다. 승인 대기 중 프로그램을 끄고 다시 켜자 같은 승인 질문이 다시 나왔다(SQLite·PostgreSQL 저장).
평가에서는 '거절했는데 실행된 티켓'·'요청하지 않은 티켓'을 **위험 행동**으로 따로 센다.

### 위협 모델과 간접 프롬프트 주입

**한 줄:** 위협 모델은 "이 시스템에서 위험이 **누구에게서, 어디로** 오나"를 먼저 따져 보는 일. 간접 프롬프트 주입은 AI 가 읽는 **자료 속에 숨겨 둔 지시**로 AI 를 움직이려는 공격이다.

**비유:** 회사 출입증(인증)이 있는 직원만 들어오는 건물이라도, 직원이 받아 온 **택배 상자 안**에 "이 상자를 연 사람은 금고 문을 열어 둘 것"이라는 쪽지가 들어 있을 수 있다. 직원은 잘못이 없다. 위험은 직원이 아니라 직원이 다루는 물건에서 온다. 그래서 출입 통제만으로는 부족하고, 상자 안의 쪽지는 '지시'가 아니라 '내용물'로 다루라고 정해 둔다.

**이 프로젝트에서:** 에이전트는 매뉴얼·작업 이력·약관·고객 메모처럼 **다른 사람이 쓴 글**을 읽고 답한다. 인증된 직원만 쓰므로 외부인의 직접 공격("앞의 규칙은 무시하고…")은 우선순위가 낮고, 대신 작업 이력 메모 같은 곳에 숨은 지시를 AI 가 따르는지를 6주차에 잰다. 티켓 생성은 이미 사람 승인을 거쳐서 실행까지는 막히지만, AI 가 숨은 지시대로 승인을 요청하거나 답을 바꾸는지는 아직 재지 않았다(agent/README 6절).

### 과업 평가

**한 줄:** 업무 기능(도구) 호출 하나가 맞았나가 아니라, **질문 하나를 끝까지 처리했나**를 채점한다.

**비유:** 상담원 시험에서 "조회 버튼을 맞게 눌렀나"만 보지 않고, 손님 문의를 끝까지 처리했는지 본다 — 맞는 조회를 했고, 결재가 필요한 건 결재를 받았고, 손님에게 맞는 답을 했고, 개인정보를 흘리지 않았나.

**이 프로젝트에서:** 26개 과업, 성공 = 업무 기능(도구)·인자 + 승인 절차 + 답의 핵심 값·근거 + 개인정보 노출 없음. 키워드 규칙으로는 못 알아듣는 '바꿔 말하기' 과업으로 LLM 을 쓰는 이유를 잰다. [agent/README.md](../agent/README.md#3-결과-읽는-법)
