# 면접 예상 질문

이 저장소로 면접을 볼 때 나올 만한 질문과, 측정을 근거로 한 답을 모았다. 면접 전에 이 문서만 읽으면 되도록 썼다.

**읽는 법** — 질문마다 같은 순서다.
- **30초 답:** 소리 내어 말할 분량. 숫자 하나와 결정 하나를 넣는다.
- **근거:** 그 숫자가 나온 문서·측정 원본. 면접관이 저장소를 열어 볼 때 가리킬 곳.
- **꼬리 질문:** 이어서 나올 만한 질문과 짧은 답.

검색·서빙 숫자는 노트북(RTX 5070 Laptop 8GB)에서 잰 값이고, 에이전트 규칙 기준선(D5)은 클라우드 작업 환경에서 잰 값이다. 서빙의 최종 수치는 24GB GPU 에서 다시 잴 예정이라는 점을 먼저 말해 두면 "노트북 숫자 아니냐"는 질문을 막을 수 있다.
용어가 막히면: [쉽게_풀어쓴_개념.md](쉽게_풀어쓴_개념.md)

**근거:** [README](../README.md#계층-구성과-지금-기본값) 의 '지금 기본값' 표 — 계층마다 기본값과 근거 링크.

**꼬리 질문:** "그냥 써 본 것과 뭐가 다른가요?" → "X 를 썼다가 아니라 X 와 Y 를 이 조건에서 재 보고 이걸 골랐다를 남겼습니다. 결정마다 측정 원본(`reports/`)이 붙어 있습니다."

### A2. 설비 정비와 고객 상담, 왜 관계없는 두 분야를 했나요?

**30초 답:** "같은 엔진을 다른 고객사에 그대로 붙일 수 있다는 걸 보이려고 일부러 성격이 다른 둘을 골랐습니다. 두 시나리오의 차이는 시스템 프롬프트와 업무 기능(도구) 서버뿐이고 그래프·검색·평가 코드는 같습니다. 그리고 설비 쪽은 승인이 필요한 행동을, 상담 쪽은 개인정보 보호를 맡아서 둘을 합쳐야 기업용 에이전트에 필요한 것이 다 들어갑니다."

**근거:** [README — 왜 이렇게 만드나](../README.md#왜-이렇게-만드나) 의 비교표.

**꼬리 질문:** "실제 고객사라면 무엇을 바꾸나요?" → "업무 기능(도구) 서버(DB 연결·문서), 시스템 프롬프트, 과업 평가셋 세 가지입니다. 평가셋을 먼저 만들어야 바꾼 뒤에도 잘 되는지 잴 수 있습니다."

### A3. 왜 실제 데이터가 아니라 가상 데이터인가요?

**30초 답:** "설비 매뉴얼과 고객 정보는 실제로는 회사 밖으로 나갈 수 없는 자료라서, 같은 모양의 가상 데이터를 생성 스크립트로 만들었습니다. 고정 시드라 누구나 똑같이 재현되고, 정답도 사람이 손으로 적지 않고 데이터에서 계산합니다. 일부러 어렵게도 만들었습니다 — 한 글자만 다른 경보 코드 32종, 매뉴얼을 찾을 때 끼어드는 작업 이력 2,400건."

**근거:** [data/README.md](../data/README.md) · CI 가 생성 스크립트와 커밋된 데이터가 같은지 매번 확인.

**꼬리 질문:** "가상 데이터면 결과를 믿을 수 있나요?" → "절대 수치보다 비교와 실패 유형이 의미 있습니다. 예를 들어 '날짜 표기가 달라 검색이 이력을 못 찾는다'는 실제 데이터에서도 그대로 생기는 문제입니다."

### A4. 28년 통신 소프트웨어 경력이 AI 에이전트 일과 어떻게 이어지나요?

**30초 답 (예시, 본인 경험으로 바꿔 말할 것):** "이 프로젝트를 하면서 많은 부분이 통신에서 하던 일과 같은 구조라는 걸 느꼈습니다. LLM 게이트웨이는 교환기나 SIP 프록시처럼 대표번호로 받아 실제 회선으로 연결하고, 회선이 죽으면 우회합니다. 장애 대체를 정상 종료와 강제 종료 두 방식으로 시험하고, 측정이 흔들리면 반복해서 범위를 적는 것도 통신 장비 검증에서 하던 습관입니다."

**근거:** [쉬운 설명 — 게이트웨이(교환기 비유)](쉽게_풀어쓴_개념.md#게이트웨이-litellm) · [장애 대체 시험](../serving/README.md#43-장애-대체-시험-실행-방법-31)

### A5. 이 코드는 직접 짠 건가요? AI 업무 기능(도구)을 썼나요?

**30초 답 (그대로 솔직하게):** "코드 작성에는 AI 코딩 도우미(Claude)를 썼습니다. 저는 무엇을 잴지 정하고, 노트북에서 실제로 측정하고, 결과가 이상하면 원인을 같이 추적하고, 결정을 내렸습니다. 예를 들어 SGLang 이 동시 16명에서 느려진 원인을 시작 로그로 확인했고, 처음 판단이 틀렸다가 측정으로 바로잡은 기록도 문서에 그대로 남아 있습니다."

**근거:** [문제해결 이력](문제해결_이력.md) — 틀린 판단과 정정이 그대로 남아 있음(D1, D5, D14 등).

**꼬리 질문:** "그럼 본인은 뭘 할 줄 아나요?" → 이 문서의 B~D 질문을 숫자와 함께 설명할 수 있으면 된다. AI 업무 기능(도구)을 써서 빠르게 만들고, 측정으로 검증하는 방식 자체가 요즘 회사들이 원하는 일하는 방식이라는 점을 덧붙인다.

**30초 답:** "저도 그렇게 설계했다가 재 보고 두 번 바꿨습니다. 1주차에 bge-m3 임베딩으로 재니 같은 무게로 합친 하이브리드가 벡터 단독보다 낮았습니다 — 어려운 질문 정답률이 설비 0.75 → 0.62, 상담 1.00 → 0.75. BM25 가 필요 없는 질문에까지 끼어든 탓이라, 코드가 있는 질문에만 BM25 를 섞도록 바꿨습니다. 2주차에 문서를 키우자 그것도 부족해서, 지금은 질문에 코드(경보 코드·요금제 코드·고객 번호)가 있으면 BM25 단독, 없으면 벡터로 보냅니다."

**근거:** [README — 벡터DB 6종](../README.md#벡터db-6종) · [문제해결 이력 D3·D5](문제해결_이력.md#d5-같은-설정-숫자면-공정하다는-틀렸다)

**꼬리 질문:**

### B4. pgvector 를 쓸 때 주의할 점은?

**30초 답:** "필터를 건 검색입니다. pgvector 는 가까운 후보를 먼저 뽑고 나중에 조건으로 거르는데, 소수 문서(전체의 1.8%)를 필터로 찾으면 거르고 나서 결과가 거의 안 남습니다. 정답률이 0.77 에서 0.32 로 떨어졌고, pgvector 0.8 의 `iterative_scan` 을 켜서 회복했습니다. 무서운 점은 작은 표에서는 PostgreSQL 이 인덱스 대신 전부 훑어서 문제가 숨어 있다가, 데이터가 커지는 순간 오류 없이 정확도만 떨어진다는 것입니다."

**근거:** [문제해결 이력 D9](문제해결_이력.md#d9-pgvector-필터-검색이-데이터가-커지면-무너짐) · [쉬운 설명 — 인덱스 강제](쉽게_풀어쓴_개념.md#인덱스-강제와-iterative-scan)

**꼬리 질문:** "작은 데이터에서 그걸 어떻게 재현했나요?" → "`enable_seqscan = off` 로 인덱스를 강제해서, 데이터가 커졌을 때의 상황을 미리 만들었습니다."

## C. 서빙

### C1. 에이전트 서빙에서 가장 중요한 설정은?

**30초 답:** "접두사 캐시입니다. 엔진 선택보다 컸습니다. 에이전트 요청은 입력의 66~84% 가 앞 요청과 같습니다(시스템 프롬프트·업무 기능(도구) 설명·앞 대화). 캐시를 켜면 같은 GPU 로 받을 수 있는 처리량이 2~3배, 동시 16명이 몰릴 때는 약속 시간을 지킨 처리량이 14~26배 차이가 났습니다. 그래서 에이전트를 만들 때 시스템 프롬프트를 고정해 맨 앞에 두고, 날짜 같은 바뀌는 값은 넣지 않습니다."

**근거:** [serving/README 4.2 ②](../serving/README.md#42-본-측정-동시-14816명-단계당-요청-48개-업무-기능도구-호출-20문항-노트북) · [쉬운 설명 — 접두사 캐시](쉽게_풀어쓴_개념.md#접두사-캐시)

**꼬리 질문:** "짧은 질문에서도 그런가요?" → "아닙니다. 공유하는 앞부분이 짧은 일반 채팅에서는 차이가 약 4% 였습니다. 에이전트라서 큰 효과입니다."

### C2. vLLM 과 SGLang 중 무엇을 골랐고 왜인가요?

**30초 답:** "직접 공격은 우선순위가 낮다고 봤습니다. 대신 위험이 어디서 오는지 따져 보니 셋이 남았습니다. 첫째, AI 가 읽는 자료 — 작업 이력 메모처럼 다른 사람이 쓴 글에 숨은 지시(간접 주입). 둘째, 직원 너머의 사람 — 전화한 사람이 상담원을 통해 개인정보를 빼내려는 경우. 셋째, 실수 — 안전 질문을 상식으로 답하는 것. 그래서 보호 기능(가드레일)을 기술 목록대로 다 붙이지 않고 이 순서로 고르고, 정상 업무를 얼마나 막아 버리는지도 같이 잽니다."

**근거:** [agent/README 6절](../agent/README.md#6-6주차-계획-위협-모델에-맞춘-보호-기능가드레일) · [쉬운 설명 — 위협 모델과 간접 주입](쉽게_풀어쓴_개념.md#위협-모델과-간접-프롬프트-주입)

**꼬리 질문:** "이미 막혀 있는 건요?" → "티켓은 사람 승인, 개인정보는 업무 기능(도구) 서버에서 가림, 시나리오마다 업무 기능(도구) 서버를 따로 붙여 권한이 나뉩니다. 6주차에 재는 건 그 위에서 AI 가 숨은 지시를 따라 승인을 요청하거나 답을 바꾸는지입니다."

## E. 일하는 방식

### E1. 측정하다 틀린 적이 있나요?

**30초 답:** "여러 번 있었고 모두 기록했습니다. 대표적으로 장애 대체 시험에서 '0.72초 만에 대체 엔진으로 넘어갔다'는 결과가 나왔는데, 알고 보니 꺼지는 중이던 1순위가 마저 처리한 응답을 센 것이었습니다. '기다리던 엔진의 첫 응답'을 재도록 고치고, 요청별 원본 기록을 남기게 했습니다. 결과가 이상하게 좋거나 나쁘면 엔진보다 측정기를 먼저 의심합니다."

**근거:** [문제해결 이력 D16](문제해결_이력.md#d16-장애-대체가-072초-만에-일어난-것처럼-보임-3주차) — 측정기 결함은 D12·D15·D16, 설정 실수는 D11·D13

**다른 예:** 3턴 대화 처리량이 이상하게 낮았는데 대화가 2개뿐이라 동시 4명 중 2명이 놀고 있었던 것(D12), 게이트웨이 경유 요청이 전부 실패했는데 엔진 포트를 127.0.0.1 에만 열어 컨테이너에서 닿지 않았던 것(D13).
