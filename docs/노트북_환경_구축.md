# 노트북 환경 구축

이 프로젝트를 Windows 노트북에서 돌리기까지의 과정과, 각 단계의 결과를 읽는 법이다.
막혔던 문제와 해결은 [문제해결_이력.md](문제해결_이력.md)의 A 장에 따로 있다.

이 저장소에서 쓴 노트북
| 항목 | 사양 | 판단 |
|---|---|---|
| GPU | RTX 5070 Laptop, VRAM 8GB (Blackwell, 드라이버 592.19, CUDA 13.1) | 개발·기능 확인·경향 측정 가능, 최종 벤치마크는 24GB 이상 GPU |
| RAM | 24GB | WSL 에 16GB 배정. 벡터DB 서버 5종 + 엔진을 한꺼번에 띄우진 않는다 |
| 디스크 | 여유 782GB | 충분 (모델·Docker 이미지가 크므로 100GB 이상 권장) |
| OS | Windows 11 | vLLM·SGLang 은 Windows 에서 바로 안 돈다 → WSL2(Ubuntu) + Docker |

---

## 1. 사양 확인

**마우스로:** 시작 버튼 오른쪽 클릭 → **작업 관리자** → **성능** 탭.
- **메모리**: 오른쪽 위 숫자가 RAM 총량.
- **GPU**: NVIDIA 라고 적힌 쪽을 클릭. **전용 GPU 메모리**의 뒤 숫자가 VRAM(예: 0.4/8.0GB 면 8GB). "공유 GPU 메모리"는 일반 RAM 을 빌려 쓰는 것이라 VRAM 이 아니다. GPU 가 둘이면 하나는 보통 내장 그래픽.
- 디스크: 파일 탐색기 → 내 PC → C: 의 "사용 가능". Windows 버전: 설정 → 시스템 → 정보.

**PowerShell 로 한 번에:**
```powershell
Get-CimInstance Win32_OperatingSystem | Format-List Caption, Version
Get-CimInstance Win32_VideoController | Format-List Name
"RAM: {0} GB" -f [math]::Round((Get-CimInstance Win32_ComputerSystem).TotalPhysicalMemory/1GB)
nvidia-smi
```
`nvidia-smi` 가 표를 보여 주면 NVIDIA GPU 와 드라이버가 있다는 뜻. GPU 이름, VRAM, CUDA 버전이 한 번에 보인다.

**사양별 방향:** VRAM 24GB 이상이면 8B 모델 실험을 모두 로컬에서. 12~16GB 면 4B·양자화 8B 로 로컬, 큰 실험만 클라우드. NVIDIA GPU 가 없으면 서빙 실험만 클라우드, 벡터DB·에이전트·llama.cpp 는 로컬.

**주의:** RTX 50 시리즈(Blackwell)는 구버전 vLLM·SGLang·PyTorch 가 인식하지 못한다. 최신 버전과 CUDA 12.8 이상이 필요하다(SGLang 최신 이미지는 CUDA 13 전용).

## 2. WSL2 · GPU · Docker 확인

Ubuntu(WSL) 창에 붙여 넣는다.
```bash
grep PRETTY_NAME /etc/os-release; uname -r; free -h | head -2; nproc; df -h ~ | tail -1
nvidia-smi
docker --version
docker run --rm --gpus all ubuntu nvidia-smi
```

결과 읽는 법
- `uname -r` 에 `microsoft-standard-WSL2` 가 있으면 WSL2. 없으면 WSL1 이라 GPU 를 못 쓴다.
- `free -h` 의 total 은 WSL 에 배정된 메모리(기본은 RAM 의 절반 안팎).
- `nvidia-smi` 에 GPU 이름과 VRAM(8188MiB 정도)이 보이고, 오른쪽 위 **CUDA Version 이 12.8 이상**이면 통과. WSL 은 Windows 의 NVIDIA 드라이버를 그대로 쓴다.
- 마지막 줄은 **컨테이너 안에서** GPU 가 보이는지 시험. 위와 같은 GPU 표가 나오면 통과.
  "WSL 이 GPU 를 본다"와 "Docker 컨테이너가 GPU 를 본다"는 따로 확인해야 하는 별개의 단계다.
  `no known GPU vendor found` 가 나오면 → [문제해결 이력 A3](문제해결_이력.md) (nvidia-container-toolkit 설치).

## 3. WSL 메모리 늘리기 (11GB → 16GB)

노트북 안에서 Windows 와 Ubuntu(WSL2)가 함께 돈다. Ubuntu 는 Windows 위에 떠 있는 작은 가상 컴퓨터라서 RAM 24GB 를 통째로 쓰지 못하고, Windows 가 정해 준 만큼만 쓴다.
vLLM·벡터DB·에이전트를 함께 띄우면 11GB 로는 부족하다.

1. 한도를 적는 파일은 Windows 사용자 폴더의 `.wslconfig`. 사용자 이름이 한글이면 `cmd.exe` 경로가 깨지므로 직접 찾는다: `ls /mnt/c/Users/` ([문제해결 이력 A1](문제해결_이력.md))
2. 파일이 이미 있으면 덮어쓰지 말고 그 줄만 고친다: `sed -i 's/^memory=.*/memory=16GB/' /mnt/c/Users/<이름>/.wslconfig`
   없으면 새로 만든다:
   ```
   [wsl2]
   memory=16GB
   swap=8GB
   ```
3. Windows **PowerShell** 에서 `wsl --shutdown`, Ubuntu 창을 다시 연다.

`free -h` 결과 읽는 법
| 항목 | 예 | 뜻 |
|---|---|---|
| Mem total | 15Gi | Ubuntu 가 쓸 수 있는 메모리. 16GB 설정인데 15Gi 로 보이는 건 정상 (커널 몫, GiB 단위가 GB 보다 약간 큼) |
| used | 1.0Gi | 지금 쓰는 양 |
| available | 14Gi | 새 프로그램이 더 쓸 수 있는 양 |
| Swap total | 8.0Gi | 메모리가 모자랄 때 디스크를 임시 메모리로 쓰는 공간 |

Windows 쪽에는 약 8GB 가 남으니 작업 중엔 브라우저 탭을 많이 열지 않는다.

## 4. vLLM 첫 실행과 업무 기능(도구) 호출 확인

```bash
docker run --rm --gpus all --ipc=host -p 127.0.0.1:8000:8000 \
  -v ~/.cache/huggingface:/root/.cache/huggingface \
  vllm/vllm-openai:latest \
  --model Qwen/Qwen3-1.7B --max-model-len 8192 --gpu-memory-utilization 0.85 \
  --enable-auto-tool-choice --tool-call-parser hermes
```
이미지가 10GB 이상이라 첫 실행은 오래 걸린다. 로그 끝에 `Starting vLLM server on http://0.0.0.0:8000` 이 나오면 떴다.

**로그에서 눈여겨볼 숫자** (서빙 리포트의 '환경 표'에 그대로 쓰는 값)
| 로그 | 이 노트북 값 | 뜻 |
|---|---|---|
| Model loading took | 3.22 GiB | 모델 가중치가 차지한 GPU 메모리 |
| Available KV cache memory | 2.39 GiB | 대화 내용을 담아 두는 공간 ([KV 캐시](쉽게_풀어쓴_개념.md#kv-캐시)) |
| GPU KV cache size | 22,352 tokens | 그 공간에 동시에 담을 수 있는 토큰 수 |
| Maximum concurrency for 8,192 tokens | 2.73x | 8천 토큰짜리 요청을 동시에 약 2.7개 |
| init engine took | 117 s | 최초 준비 시간. 컴파일 결과가 저장돼 다음부터 짧아짐 |

8GB GPU 에서는 가중치가 메모리 절반 가까이를 차지해 KV 캐시 자리가 2.4GB 뿐이다. 본 벤치마크를 24GB 이상 GPU 에서 하는 이유가 이 숫자다.
`generation_config.json` 경고는 모델 제작사가 정한 기본값(temperature 0.6 등)을 쓴다는 안내 — 벤치마크에서는 요청마다 값을 명시한다.

**업무 기능(도구) 호출 시험** (서버 창은 두고 Ubuntu 창을 하나 더 연다)
```bash
curl -s localhost:8000/v1/chat/completions -H "Content-Type: application/json" -d '{
  "model": "Qwen/Qwen3-1.7B",
  "messages": [{"role": "user", "content": "CRB-03 경보 조치 방법을 매뉴얼에서 찾아줘"}],
  "tools": [{"type": "function", "function": {
    "name": "search_manual", "description": "설비 매뉴얼에서 경보 코드의 조치 방법을 검색한다",
    "parameters": {"type": "object", "properties": {"query": {"type": "string"}}, "required": ["query"]}}}],
  "chat_template_kwargs": {"enable_thinking": false}
}' | python3 -m json.tool
```

결과 읽는 법
- `"content": null` — 모델이 글로 답하지 않았다.
- `"tool_calls"` → `"name": "search_manual"` — 대신 매뉴얼 검색 업무 기능(도구)을 불러 달라고 요청했다.
- `"arguments"` — 업무 기능(도구)에 넘길 검색어. `경...` 은 한글이 코드로 표시된 것(풀면 "CRB-03 경보 조치 방법").
- `"finish_reason": "tool_calls"` — 업무 기능(도구) 호출 때문에 멈췄다.
- `usage` — 입력 179토큰(상당 부분이 업무 기능(도구) 정의), 출력 29토큰. **긴 입력, 짧은 출력**이라는 에이전트 부하의 모양이 이 한 번에도 보인다.

실제 에이전트는 이 다음에 프로그램이 검색을 실행하고 결과를 다시 모델에 넣어 최종 답을 받는다(4~5주차).

## 5. 측정을 오래 돌릴 때

- **전원 어댑터를 꽂는다.** 배터리로 돌면 절전이 빨리 걸리고 GPU 성능도 낮아져 측정값이 달라진다.
- **절전 끄기:** 설정 → 시스템 → 전원 및 배터리 → "화면, 절전 모드, 최대 절전 모드 시간 제한" → **전원 연결됨: 다음 시간 후 장치를 절전 모드로 전환 = 안 함.** 화면 끄기는 상관없다.
- **덮개를 닫지 않는다.** 닫아야 하면 같은 화면의 "덮개 및 전원 단추 컨트롤"에서 전원 연결 시 "덮개를 닫으면" = 아무 것도 안 함.
- **전원 모드는 측정 내내 같게** (이 저장소의 측정은 모두 "균형").
- 화면 잠금(Win+L)은 괜찮다. 잠금은 화면만 가리고 WSL·Docker·스크립트는 계속 돈다.
- 절전으로 중간에 끊기면 측정기는 결과를 마지막에 한꺼번에 저장하므로 그때까지 잰 것도 남지 않는다 → 처음부터 다시.

## 6. 엔진이 안 뜰 때 직접 보는 법

엔진이 준비될 때까지 기다리면서, 컨테이너가 죽었으면 바로 멈추고 로그를 본다(SGLang 예, 프로필 이름만 바꾸면 된다).
```bash
P=sglang
docker compose -f serving/compose.yml --profile $P up -d
until curl -sf localhost:30000/v1/models >/dev/null; do
  [ -n "$(docker compose -f serving/compose.yml --profile $P ps -a --status exited -q)" ] && { echo "컨테이너 종료됨"; break; }
  echo "준비 중..."; sleep 10
done
docker compose -f serving/compose.yml --profile $P logs --no-color | grep -iE "error|out of memory|cuda graph|traceback" | tail -20
docker compose -f serving/compose.yml --profile $P down
```
- 시간을 정해 두고 기다리면(예: `sleep 120`) 엔진이 아직 준비 중일 때 정보를 물어 빈 응답을 받는다. 준비될 때까지 기다린다.
- 측정기(`scripts/bench_serving.py --manage`)는 이 일을 자동으로 하고, 실패하면 로그를 `results/logs/` 에 남긴다.
- 엔진 옵션은 버전마다 이름이 바뀐다. 쓰는 버전의 `--help` 로 확인한다(예: SGLang 0.5.21 의 `--cuda-graph-max-bs-decode`, [문제해결 이력 D14](문제해결_이력.md)).
