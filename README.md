# onprem-agent

**폐쇄망에서 도는 엔터프라이즈 에이전트 레퍼런스 구현.**
서빙 엔진(vLLM · SGLang · llama.cpp), 벡터DB(Qdrant · Milvus · Elasticsearch · Weaviate · pgvector), 에이전트(LangGraph + MCP)를
**같은 평가셋으로 재서 비교하고, 그 근거로 고른다.**

> "X를 써 봤다"가 아니라 "X와 Y를 이 조건에서 재 보고 이걸 골랐다"를 보여 주는 저장소입니다.

## 왜 이렇게 만드나

- 에이전트를 실제 현장에 넣는 회사들은 대부분 여러 고객사·계열사에 **같은 엔진을 다른 데이터로** 깐다. 그래서 엔진과 도메인을 분리하고, 도메인 두 개로 교체를 실증한다.
- 고객사마다 쓰는 벡터DB와 서빙 엔진이 다르다. 하나를 깊게 쓰기보다 **공통 인터페이스 뒤에 여러 개를 두고 숫자로 비교**한다.
- 설비 매뉴얼·고객 정보는 외부 반출이 안 되는 경우가 많다. 모든 계층이 **사내망 안에서** 돌아야 한다.

## 계층 구성

| 계층 | 구성 | 비교 대상 |
|---|---|---|
| 시나리오 | ① 운영 장애 대응(설비 경보 → 진단 → 매뉴얼 조치) ② 고객 상담(요금제·약관 + 고객 DB) | 엔진은 그대로, 도메인만 교체 |
| 에이전트 | LangGraph, 도구는 MCP 서버 (SQL 조회 · 문서 검색 · 분석 모델 · 승인 필요한 실행) | 모델·설정별 과업 성공률 |
| 검색 | 하이브리드(BM25 + 벡터, RRF) + 리랭커, 한국어 토큰화 | Qdrant · Milvus · Elasticsearch · Weaviate · pgvector (+ Chroma) |
| 서빙 | OpenAI 호환 API, LiteLLM 게이트웨이로 한 주소 | vLLM · SGLang (GPU) · llama.cpp (CPU) |
| 공통 | 평가 하네스 · 가드레일 · Langfuse 추적 · K8s · CI/CD · 오프라인 설치 | |

진행 상황은 [docs/ROADMAP.md](docs/ROADMAP.md), 부딪힌 문제와 해결 과정은 [docs/문제해결_이력.md](docs/문제해결_이력.md).

## 1주차 결과: 검색 기준선

`configs/retrieval_baseline.yaml` — 모델 다운로드 없이 어디서나 돈다(CI 회귀 검사용). 전체 표: [reports/retrieval_baseline.md](reports/retrieval_baseline.md)

| 시나리오 | 갈래 | 코드 질문 R@3 | 바꿔 말하기 R@3 | 어려운 질문 R@3 |
|---|---|---|---|---|
| 운영 장애 | BM25 | 1.00 | 1.00 | 0.50 |
| 운영 장애 | 해시 벡터(기준선) | 0.77 | 0.75 | 0.38 |
| 고객 상담 | BM25 | 1.00 | 0.93 | 0.62 |
| 고객 상담 | 해시 벡터(기준선) | 1.00 | 0.83 | 0.56 |

- **코드 질문**(`CRB-03 조치 순서`): 경보 코드 32종 중 다수가 한 글자만 다르다. 글자로 찾는 BM25 가 강하다.
- **어려운 질문**(`회전체 쪽 떨림이 날마다 조금씩 심해져` → 진동 드리프트 DRF-08): 문서와 낱말이 겹치지 않는다. BM25 가 절반을 놓친다.
- 해시 벡터는 '뜻'을 모르는 배선 확인용 기준선이다.

### 실제 임베딩(bge-m3)으로 잰 결과 — "하이브리드가 항상 낫다"는 틀렸다

노트북(RTX 5070 Laptop 8GB)에서 측정. 전체 표: [reports/retrieval_bge.md](reports/retrieval_bge.md)

| 시나리오 | 갈래 | 전체 R@3 | 어려운 질문 R@3 | 질의 p50 |
|---|---|---|---|---|
| 운영 장애 | BM25 | 0.89 | 0.50 | 0.2 ms |
| 운영 장애 | bge-m3 단독 | **0.95** | **0.75** | 12.2 ms |
| 운영 장애 | 하이브리드(같은 무게 RRF) | 0.92 | 0.62 | 12.8 ms |
| 운영 장애 | 가중 RRF(BM25 0.3) | 0.92 | 0.62 | 14.4 ms |
| 운영 장애 | **코드 라우팅** | **0.95** | **0.75** | 13.2 ms |
| 고객 상담 | BM25 | 0.87 | 0.62 | 0.2 ms |
| 고객 상담 | bge-m3 단독 | **0.97** | **1.00** | 11.5 ms |
| 고객 상담 | 하이브리드(같은 무게 RRF) | 0.90 | 0.75 | 12.5 ms |
| 고객 상담 | 가중 RRF(BM25 0.3) | 0.90 | 0.75 | 13.0 ms |
| 고객 상담 | **코드 라우팅** | **0.97** | **1.00** | 12.0 ms |

- 의미 임베딩이 어려운 질문을 0.50→0.75, 0.62→1.00 으로 끌어올렸다.
- 같은 무게로 합친 하이브리드는 **단독보다 낮았다.** 손해는 전부 어려운 질문에서 났다 — BM25 가 엉뚱한 절을 상위에 올리고 RRF 가 그 등수를 섞어 정답을 밀어낸다.
- BM25 무게를 0.3 으로 낮춰도 회복되지 않았다. 문제는 무게가 아니라 **BM25 가 필요 없는 질문에까지 끼어드는 것**이었다.
- **코드 라우팅**(질문에 `CRB-03`·`PLN-5G55` 같은 코드가 있을 때만 BM25 를 섞음)이 벡터 단독과 같은 최고점을 냈다.
- 반대로 해시 임베딩처럼 벡터 쪽이 약하면 BM25 를 섞는 편이 낫다. 어떤 합치기가 좋은지는 임베딩 품질에 달려 있다.

**결정: 기본값은 코드 라우팅.** 지금 데이터에서는 벡터 단독과 점수가 같지만, 한 글자 차이 코드를 글자로 확인하는 안전장치를 남긴다.
문서가 수백 쪽으로 늘어나 비슷한 코드 절이 많아지면 벡터만으로는 코드를 헷갈릴 수 있다 — 2주차에 문서를 키워 이 가정을 다시 잰다.


## 2주차 결과: 문서를 키우자 판도가 바뀌었다 + 벡터DB 5종 비교

매뉴얼 45절 + 정비 작업 이력 2,400건(청크 2,445개). 이력은 같은 경보 코드·부품 이름을 써서 매뉴얼을 찾는 검색의 현실적인 경쟁자다.
노트북(RTX 5070 Laptop 8GB, Docker)에서 측정. 전체 표: [reports/retrieval_vectordb.md](reports/retrieval_vectordb.md)

### 검색 방식

| 갈래 | 전체 R@3 | 코드 질문 | 바꿔 말하기 | 어려운 질문 |
|---|---|---|---|---|
| BM25 | 0.84 | 1.00 | 0.94 | 0.38 |
| bge-m3 단독 | 0.70 | **0.31** | 1.00 | 0.75 |
| 코드 → 하이브리드, 나머지 → bge-m3 | 0.81 | 0.62 | 1.00 | 0.75 |
| **코드 → BM25, 나머지 → bge-m3** | **0.95** | **1.00** | **1.00** | **0.75** |

- 1주차(문서 45절)에는 bge-m3 단독도 코드 질문 1.00 이었다. 문서가 커지자 **0.31 로 무너졌다** — `CRB-01 조치 순서`에 대해 같은 코드를 언급한 작업 이력을 매뉴얼보다 위로 올린다. 1주차에 "문서가 커지면 벡터만으로는 코드를 헷갈릴 수 있다"고 적어 둔 가정이 그대로 확인됐다.
- **결정: 기본값을 '코드 → BM25, 나머지 → bge-m3' 라우팅으로 바꾼다.** 글자로 찾는 쪽과 뜻으로 찾는 쪽이 각자 강한 질문만 맡는다.
- 남은 오답 2개는 '매뉴얼이냐 이력이냐'의 문제다 → 다음 단계: 문서 종류 필터, 리랭커.

### 벡터DB 5종 (같은 벡터, 같은 HNSW 설정 m=16 · 구축 100 · 검색 128)

| DB | 근사 재현율@10 | 정답 R@3 | DB 검색 p50 | 적재 시간 |
|---|---|---|---|---|
| 전수 비교(정답 상한) | 1.00 | 0.70 | 0.6 ms | — |
| Qdrant | 1.00 | 0.70 | 5.5 ms | 1.5 s |
| Milvus | 1.00 | 0.70 | 7.4 ms | 4.0 s |
| Elasticsearch | 1.00 | 0.70 | 19.0 ms | 2.7 s |
| Weaviate | 0.99 | 0.68 | 3.5 ms | 1.6 s |
| Chroma | 0.95 | 0.54 | 2.5 ms | 0.9 s |
| **pgvector** | **0.81** | **0.30** | 2.6 ms | 0.6 s |

- **근사 재현율 평균만 보면 속는다.** pgvector 는 근사 재현율 0.81 인데 정답률은 0.70→0.30 으로 무너졌다. 놓친 것이 거의 다 매뉴얼 절이다 —
  근사 검색의 손실이 고르게 나지 않고 **소수 문서에 몰린다**. 다수인 작업 이력 사이에서 매뉴얼 절의 그래프 연결이 약해진 것으로 본다.
- 같은 설정에서 Qdrant·Milvus·Elasticsearch 는 정확했고, 차이는 속도에서 났다. Elasticsearch 가 가장 느리지만 이미 검색 인프라로 쓰는 회사라면 별도 DB 없이 쓸 수 있다는 장점이 있다.
- **설정 문제였다. 다만 "같은 설정 숫자면 공정하다"는 틀렸다.** HNSW 를 m=32 · 구축 200 · 검색 400 으로 키우자 pgvector·Chroma 모두 정답 상한(0.70)을 회복했다.
  같은 숫자의 설정에서 Qdrant·Milvus·Elasticsearch 는 정확했고 pgvector·Chroma 는 아니었다 — 엔진마다 근사 재현율을 재서 따로 맞춰야 한다.
  대가: pgvector 질의 지연 약 24 ms → 37 ms. 세 번 반복하면 기본 설정은 회차마다 흔들리고(pgvector R@3 0.32~0.38), 키운 설정은 세 번 모두 같았다.
  → [reports/retrieval_vectordb_hnsw.md](reports/retrieval_vectordb_hnsw.md)

### 문서 종류 필터 · 리랭커 · 날짜 표기 (2주차 후반)

이력 질문 10개("2025년 7월 1호기 LVL-06 이력")를 더했다. 전체 표: [reports/retrieval_filter_rerank.md](reports/retrieval_filter_rerank.md)

| 갈래 | 전체 R@3 | 이력 R@3 | p50 |
|---|---|---|---|
| 라우팅 (날짜 통일 전) | 0.74 | 0.00 | 16 ms |
| 리랭커 + 라우팅 (날짜 통일 전) | 0.94 | 1.00 | 521 ms |
| 라우팅 (날짜 통일 후) | 0.94 | 1.00 | 14 ms |
| **의도필터 + 라우팅 (날짜 통일 후)** | **0.96** | **1.00** | **19 ms** |
| 의도필터 + 리랭커 + 라우팅 | 0.96 | 1.00 | 844 ms |

- 처음엔 이력 질문이 라우팅에서 0점, 리랭커를 붙이면 만점이었다. 리랭커를 기본값으로 둘 수도 있었지만 원인을 먼저 봤다:
  질문 "2025년 **7**월"과 문서 "2025-**07**-14"가 BM25 에서 서로 다른 토큰이었다. 토크나이저가 둘 다 `2025-07` 로 맞추게 하자 **리랭커 없이 같은 점수, 지연은 1/45**.
- **결정: 기본값은 의도필터 + 라우팅.** 리랭커는 지금 데이터에서 이득이 없어 끈다.
- **pgvector 필터 검색의 함정:** HNSW 로 먼저 뽑고 나서 WHERE 로 거르므로, 소수 문서(매뉴얼 1.8%)를 찾으면 결과가 비어 R@3 0.77 → **0.32**.
  작은 표에선 플래너가 순차 스캔을 골라 숨어 있다가 데이터가 커지면 드러난다. `hnsw.iterative_scan`(0.8+)으로 0.77 회복. 다른 DB 는 모두 검색 중 필터라 상한과 같았다.

## 3주차: 서빙 (진행 중)

vLLM · SGLang · llama.cpp 를 같은 모델(Qwen3-1.7B)·같은 요청으로 비교하고 LiteLLM 게이트웨이 뒤에 둔다.
에이전트는 엔진 주소 대신 `agent-llm` 이라는 이름만 알고, vLLM 이 죽으면 게이트웨이가 llama.cpp 로 넘긴다.

**무엇을 재나** — 결과 읽는 법(용어·프리필/디코드·굿풋)은 [serving/README.md](serving/README.md#1-결과-읽는-법)에 한 번 정리했다.

| 지표 | 쉬운 말 |
|---|---|
| TTFT | 질문을 보내고 첫 글자가 나올 때까지 |
| TPOT | 첫 글자 이후 글자 하나가 나오는 간격 |
| 처리량 | 서버가 1초에 끝내는 요청 수·만드는 토큰 수 |
| 굿풋 | 목표(첫 글자 1초, 글자당 50ms)를 지킨 요청만 센 처리량 = 실제로 받을 수 있는 사용자 수 |
| 캐시 재사용 | 같은 앞부분(시스템 프롬프트·앞 대화)을 다시 계산하지 않은 비율 |
| 도구 호출 정확도 | 20문항에서 맞는 도구와 인자를 고른 비율 |

요청 모양은 짧은 질문(chat), 에이전트 첫 질문(rag: 긴 시스템 프롬프트 + 문서 3개), 3턴 대화(multiturn) 세 가지. 모두 이 저장소의 문서·질문으로 만든다.

**동작 확인 결과** (노트북 RTX 5070 Laptop 8GB, 동시 1·4명 짧은 측정 — 경향 확인용)
- **접두사 캐시가 엔진 선택보다 크다.** 에이전트 요청은 입력의 약 78%(시스템 프롬프트·도구 설명)가 모든 요청에서 같다. 캐시를 켜면 첫 글자가 약 2.8배(70 vs 199 ms), 3턴 대화는 약 5배(46 vs 240 ms) 빨라지고, 동시 4명 처리량이 27~32% 는다. 짧은 질문에서는 차이가 없다.
  → 에이전트 설계 원칙: 시스템 프롬프트·도구 설명은 요청마다 바꾸지 말고 맨 앞에 고정한다.
- **SGLang 이 vLLM 보다 처리량 15~17% 높다** (글자 간격 11.5 vs 13.4 ms). 요청 8개 1회 측정이라 본 측정에서 확인한다.
- **llama.cpp 는 혼자 쓰면 가장 빠르고(글자 간격 7.4 ms — Q8_0 양자화로 가중치가 절반이라서), 긴 입력이 4명 몰리면 처리량이 SGLang 의 절반(1.04 vs 2.11), 글자 간격 26 ms 로 무너진다.**
  → llama.cpp 는 1인용·현장 단말용, 다중 사용자 에이전트 서버는 vLLM·SGLang. 게이트웨이에서도 llama.cpp 는 장애 시 대체로만 둔다.
- 도구 호출: 세 엔진 모두 형식 오류 0. 5문항 중 vLLM·llama.cpp 가 같은 문항 하나에서 도구를 안 불렀다(모델 판단). 20문항 본 측정에서 비교한다.
- LiteLLM 게이트웨이 경유는 설정 실수로 전부 실패 → 고침. 본 측정에서 게이트웨이 지연을 잰다.
- 상세 표와 해석: [serving/README.md](serving/README.md#4-결과와-해석)

## 실행

```bash
pip install -e ".[chroma,dev]"
python scripts/make_data.py                                   # 가상 데이터·평가셋 생성 (결정적)
python scripts/eval_retrieval.py configs/retrieval_baseline.yaml --min-recall3 0.80
pytest -q

# 실제 임베딩 모델로 (bge-m3 약 2.3GB, 첫 실행 때 내려받음)
pip install -e ".[st]"
python scripts/eval_retrieval.py configs/retrieval_bge.yaml
```

측정 결과는 `results/`(Git 비추적)에 쓰이고, 확정본만 `reports/`에 옮겨 커밋한다. HNSW 는 만들 때마다 결과가 조금씩 달라서 DB 비교는 `--repeat 3` 으로 범위를 본다.

## 평가 원칙

1. 한 실험에서 바뀌는 것은 하나뿐이다. 문서, 청킹, 질문, k 는 고정.
2. 질문 유형별로 따로 채점한다. 평균 하나로 뭉치면 약점이 숨는다.
3. 정확도와 함께 색인 시간·지연(p50/p95)을 잰다.
4. 데이터는 생성 스크립트로 만들고, CI 가 스크립트와 커밋된 데이터가 일치하는지 확인한다.

> 모든 회사·제품·인물·전화번호는 가상입니다.
