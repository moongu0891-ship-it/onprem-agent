## 1. 결과 읽는 법

### 1.1 출력 한 줄

측정기는 "엔진 × 요청 모양 × 동시 사용자 수" 조합마다 아래와 같은 줄을 하나씩 찍는다. 모든 줄의 칸 구성이 같다.

```
[SGLang] rag  동시 4  2.11 req/s  271 tok/s  TTFT p50 236ms  TPOT p50 13.3ms  굿풋 2.11  캐시 —  오류 0
```

| 칸 | 뜻 | 쉬운 말 |
|---|---|---|
| `[SGLang]` | 잰 엔진 | |
| `rag` | 요청 모양 (1.2) | 어떤 종류의 질문을 보냈나 |
| `동시 4` | 동시 사용자 수 | 4명이 동시에, 답을 받자마자 다음 질문을 계속 보낸다 |
| `req/s` | 초당 처리한 요청 수 | 서버가 1초에 답을 몇 개 끝내나 |
| `tok/s` | 초당 만든 출력 토큰 수 | 서버 전체가 1초에 만드는 글자량. 토큰은 단어 조각으로, 한국어는 대략 1~2글자 |
| `TTFT` | Time To First Token | 질문을 보내고 **첫 글자가 나올 때까지** 걸린 시간 |
| `TPOT` | Time Per Output Token | 첫 글자 이후 **글자 하나가 나오는 간격**. 11ms 면 사용자 한 명당 초당 약 89토큰 |
| `p50` / `p95` | 중앙값 / 95번째 백분위 | 요청 100개를 줄 세웠을 때 50번째·95번째 값. p95 는 "운 나쁜 사용자"가 겪는 시간 |
| `굿풋` | goodput | 목표(SLO)를 **지킨 요청만** 센 초당 처리량 (1.4) |
| `캐시` | 캐시 재사용률 | 입력 토큰 중 다시 계산하지 않고 기억해 둔 걸 꺼내 쓴 비율. 엔진이 알려 줄 때만 숫자가 나오고, 아니면 `—` |
| `오류` | 실패한 요청 수 | |

결과 파일(`results/serving_*.md`)의 표도 같은 칸에 TTFT·TPOT 의 p95, 목표 달성 비율을 더한 것이다.

### 1.2 요청 모양 세 가지

모두 이 저장소의 실제 문서·질문으로 만든다 (`src/onprem_agent/serving/workloads.py`). 답변은 모두 128토큰으로 길이를 고정한다.

| 이름 | 보낸 내용 | 입력 길이 | 실제로 비슷한 것 |
|---|---|---|---|
| chat | "LVL-06 경보는 뭐예요?" 같은 짧은 질문 하나 | 짧음 | 일반 챗봇 |
| rag | 에이전트 지침·도구 설명(약 2,500자, **모든 요청이 같음**) + 검색 문서 3개 + 질문 | 김 | 에이전트의 첫 질문 |
| multiturn | rag 로 시작해 같은 대화에서 후속 질문 2개 | 턴마다 길어짐 | 에이전트와 주고받는 대화 |

### 1.3 LLM 이 답을 만드는 두 단계 — 결과 해석의 열쇠

1. **프리필(prefill) = 입력 읽기.** 질문 전체를 한 번에 읽는다. 입력이 길수록 오래 걸린다 → **TTFT** 에 나타난다.
2. **디코드(decode) = 한 글자씩 쓰기.** 답을 한 토큰씩 만든다. 토큰 하나를 만들 때마다 모델 가중치 전체(1.7B 모델이면 약 3.4GB)를 GPU 메모리에서 읽는다 → **TPOT** 에 나타난다.

여기서 나오는 세 가지 성질:

- **배칭(batching)은 거의 공짜다.** 디코드는 계산보다 '메모리 읽기'가 병목이라, 가중치를 한 번 읽을 때 여러 사용자의 다음 토큰을 같이 만들어도 시간이 거의 그대로다.
  그래서 동시 사용자를 늘리면 TPOT 는 조금만 늘고 처리량은 사용자 수만큼 는다. vLLM·SGLang 같은 서빙 엔진이 존재하는 가장 큰 이유.
- **긴 입력은 다른 사람을 잠깐 멈춘다.** 새 요청의 프리필이 끼어드는 동안 다른 사용자의 디코드가 밀린다.
  그래서 입력이 긴 에이전트 요청(rag)은 동시 사용자가 늘면 TTFT 가 크게 늘고 TPOT 도 조금 는다.
- **접두사 캐시(prefix cache)는 같은 앞부분을 다시 계산하지 않는다.** 앞부분이 같은 요청이 오면 이전 계산 결과(KV 캐시)를 꺼내 쓰고 새 부분만 프리필한다.
  vLLM 은 automatic prefix caching, SGLang 은 radix cache 라고 부른다. 에이전트는 모든 요청이 같은 시스템 프롬프트로 시작하고, 대화가 이어지면 앞 대화 전체가 같으므로 효과가 크다.
  효과는 같은 엔진의 '캐시 끔' 결과와 비교해 확정한다.

### 1.4 굿풋과 목표(SLO)

처리량만 보면 동시 사용자를 늘릴수록 좋아 보이지만, 그만큼 한 사람이 기다리는 시간이 길어진다.
그래서 목표를 정해 두고 그걸 지킨 처리량(굿풋)을 본다. 이 프로젝트의 목표는 **첫 글자 1초 이내, 글자당 50ms 이내**(초당 20토큰, 사람이 읽는 속도보다 빠름).

- 모든 요청이 목표를 지키면 굿풋 = 처리량.
- 동시 사용자를 늘리다 굿풋이 처리량보다 작아지기 시작하는 지점이 "이 서버로 받을 수 있는 사용자 수"의 실제 한계다.

### 1.5 도구 호출 검사

```
[vLLM] 도구 호출: 도구 선택 0.95, 인자까지 0.85, 형식 오류 0, 요청 오류 0
```

20문항(`eval/toolcalls.jsonl`)마다 정답 도구와 인자를 정해 두고 채점한다.

| 칸 | 뜻 |
|---|---|
| 도구 선택 | 맞는 도구를 골랐나. 인사처럼 도구가 필요 없는 질문은 "안 부름"이 정답 |
| 인자까지 | 도구도 맞고 인자(호기, 경보 코드, 연월, 우선순위 등)도 모두 맞은 비율 |
| 형식 오류 | 도구 인자가 JSON 으로 읽히지 않은 횟수. 엔진의 도구 호출 파서 문제일 때가 많다 |
| 요청 오류 | 엔진이 요청 자체를 거절·실패한 횟수 |

같은 모델이라도 엔진마다 모델 출력을 도구 호출 형식으로 바꾸는 파서가 달라서(vLLM `hermes`, SGLang `qwen25`, llama.cpp `--jinja`) 결과가 다를 수 있다.
에이전트에서는 속도보다 이게 먼저다.

## 2. 공정하게 재려고 지킨 것

- 세 엔진 모두 같은 모델 이름·같은 최대 길이(8192)·온도 0·출력 128토큰 고정(`ignore_eos`)·Qwen3 생각 모드 끔.
- 사용자 메시지 앞에 요청마다 다른 꼬리표를 붙인다. 같은 질문이 두 번 뽑혀도 캐시를 공짜로 얻지 않게.
  캐시가 재사용할 수 있는 건 '모든 요청이 공유하는 시스템 프롬프트'와 '같은 대화의 앞 턴'뿐이다.
- 동시 사용자 단계마다 다른 요청 묶음을 쓴다. 앞 단계가 남긴 캐시가 다음 단계를 돕지 않게.
- 3턴 대화는 최소한 동시 사용자 수만큼 만든다. 대화가 모자라면 일부 사용자가 놀아서 처리량이 낮게 나온다.
- 첫 요청 2개는 예열로 빼고 잰다.
- 캐시 효과는 같은 엔진의 '캐시 끔' 프로필(`--no-enable-prefix-caching`, `--disable-radix-cache`)과 비교한다.
- 차이: llama.cpp 는 GGUF 만 읽어서 Q8_0 양자화 모델을 쓴다. 결과에 함께 적는다.

## 3. 실행

노트북(RTX 5070 Laptop 8GB)에는 엔진이 하나씩만 올라간다. `--manage` 가 엔진마다 띄우고 → 재고 → 내린다.

```bash
git pull && pip install -e ".[serving]"
docker compose --profile all down          # 벡터DB 컨테이너를 내려 RAM 확보 (데이터는 남음)

# 1) 동작 확인: 동시 1·4, 요청 8개 (첫 실행은 이미지·모델 내려받기로 오래 걸림)
python scripts/bench_serving.py configs/serving_laptop.yaml --manage --quick

# 2) 본 측정: 동시 1·4·8·16, 단계당 요청 48개
python scripts/bench_serving.py configs/serving_laptop.yaml --manage
cat results/serving_laptop.md
```

한 엔진만: `--only SGLang`. 이미 떠 있는 엔진을 재려면 `--manage` 를 뺀다.

## 4. 결과와 해석

### 4.1 동작 확인 (`--quick`, SGLang, 노트북)

| 요청 모양 | 동시 | 요청/s | 토큰/s | TTFT p50 | TPOT p50 | 굿풋 | 오류 |
|---|---|---|---|---|---|---|---|
| chat | 1 | 0.66 | 85 | 33 ms | 11.2 ms | 0.66 | 0 |
| chat | 4 | 2.66 | 340 | 45 ms | 11.5 ms | 2.66 | 0 |
| rag | 1 | 0.64 | 82 | 78 ms | 11.6 ms | 0.64 | 0 |
| rag | 4 | 2.11 | 271 | 236 ms | 13.3 ms | 2.11 | 0 |
| multiturn | 1 | 0.65 | 83 | 48 ms | 11.7 ms | 0.65 | 0 |
| multiturn | 4 | 1.23\* | 158 | 63 ms | 12.3 ms | 1.23 | 0 |

\* 측정기 실수: 대화가 2개뿐이라 4명 중 2명이 놀았다. 이후 수정(2절).

- **SGLang 이 Blackwell 노트북 GPU(sm_120)에서 오류 없이 돈다.** CUDA 13 이미지(`lmsysorg/sglang:latest`) 그대로.
- **배칭이 거의 공짜라는 것이 그대로 보인다.** chat 에서 동시 1 → 4 로 처리량은 4배(0.66 → 2.66), TPOT 는 11.2 → 11.5 ms 로 거의 그대로.
  동시 1 요청 하나 = 첫 글자 33 ms + 128토큰 × 11.2 ms ≈ 1.5초 → 초당 0.66개.
- **에이전트 요청(rag)은 첫 글자가 늦다.** 입력이 길어 TTFT 33 → 78 ms. 동시 4 에서는 긴 프리필 4개가 GPU 를 다퉈 236 ms 로 커지고,
  끼어드는 프리필 때문에 TPOT 도 13.3 ms 로 늘었다. 그래서 처리량도 chat(2.66)보다 낮다(2.11). 에이전트가 일반 챗봇보다 서버 부담이 큰 이유.
- **캐시가 일하고 있다는 간접 증거.** multiturn 은 입력이 더 긴데도 동시 1 TTFT 가 rag 보다 짧다(48 vs 78 ms). 2·3턴째는 앞 대화를 radix cache 에서 꺼내 쓰고 새 질문만 계산했기 때문으로 본다.
  캐시 재사용률이 `—` 였던 건 SGLang 이 기본으로 알려 주지 않아서다 → `--enable-cache-report` 를 켰다. '캐시 끔'과의 비교로 확정한다.
- 모든 요청이 목표를 지켜 굿풋 = 처리량. 동시 4명은 이 노트북에 여유롭다. 한계는 본 측정(동시 8·16)에서 본다.

## 5. 문제가 생기면

- 엔진 로그: `docker compose -f serving/compose.yml --profile sglang logs --tail 50`
- SGLang 도구 호출 파서 이름이 버전에 따라 다르다: `SGLANG_TOOL_PARSER=qwen python scripts/bench_serving.py ...`
- SGLang 이 Blackwell 노트북 GPU 에서 커널 오류를 내면: `SGLANG_EXTRA="--attention-backend triton" ...`
- 이미지 버전 고정: `VLLM_IMAGE=vllm/vllm-openai:v0.x.y` 처럼 환경 변수로 바꾼다.
- 그 밖의 문제와 해결 과정: [docs/문제해결_이력.md](../docs/문제해결_이력.md)
