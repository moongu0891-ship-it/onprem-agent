## 1. 결과 읽는 법

> 같은 내용을 비유(상담 창구·레시피 카드)로 풀어 둔 설명: [docs/쉽게_풀어쓴_개념.md](../docs/쉽게_풀어쓴_개념.md#서빙)

### 1.1 출력 한 줄

측정기는 "엔진 × 요청 모양 × 동시 사용자 수" 조합마다 아래와 같은 줄을 하나씩 찍는다. 모든 줄의 칸 구성이 같다.

```
[SGLang] rag  동시 4  2.11 req/s  271 tok/s  TTFT p50 236ms  TPOT p50 13.3ms  굿풋 2.11  캐시 —  오류 0
```

| 칸 | 뜻 | 쉬운 말 |
|---|---|---|
| `[SGLang]` | 잰 엔진 | |
| `rag` | 요청 모양 (1.2) | 어떤 종류의 질문을 보냈나 |
| `동시 4` | 동시 사용자 수 | 4명이 동시에, 답을 받자마자 다음 질문을 계속 보낸다 |
| `req/s` | 초당 처리한 요청 수 | 서버가 1초에 답을 몇 개 끝내나 |
| `tok/s` | 초당 만든 출력 토큰 수 | 서버 전체가 1초에 만드는 글자량. 토큰은 단어 조각으로, 한국어는 대략 1~2글자 |
| `TTFT` | Time To First Token | 질문을 보내고 **첫 글자가 나올 때까지** 걸린 시간 |
| `TPOT` | Time Per Output Token | 첫 글자 이후 **글자 하나가 나오는 간격**. 11ms 면 사용자 한 명당 초당 약 90토큰 |
| `p50` / `p95` | 중앙값 / 95번째 백분위 | 요청 100개를 줄 세웠을 때 50번째·95번째 값. p95 는 "운 나쁜 사용자"가 겪는 시간 |
| `굿풋` | goodput | 목표(SLO)를 **지킨 요청만** 센 초당 처리량 (1.4) |
| `캐시` | 캐시 재사용률 | 입력 토큰 중 다시 계산하지 않고 기억해 둔 걸 꺼내 쓴 비율. 엔진이 알려 줄 때만 숫자가 나오고, 아니면 `—` |
| `오류` | 실패한 요청 수 | |

결과 파일(`results/serving_*.md`)의 표도 같은 칸에 TTFT·TPOT 의 p95, 목표 달성 비율을 더한 것이다.

### 1.2 요청 모양 세 가지

모두 이 저장소의 실제 문서·질문으로 만든다 (`src/onprem_agent/serving/workloads.py`). 답변은 모두 128토큰으로 길이를 고정한다.

| 이름 | 보낸 내용 | 입력 길이 | 실제로 비슷한 것 |
|---|---|---|---|
| chat | "LVL-06 경보는 뭐예요?" 같은 짧은 질문 하나 | 짧음 | 일반 챗봇 |
| rag | 에이전트 지침·도구 설명(약 2,500자, **모든 요청이 같음**) + 검색 문서 3개 + 질문 | 김 | 에이전트의 첫 질문 |
| multiturn | rag 로 시작해 같은 대화에서 후속 질문 2개 | 턴마다 길어짐 | 에이전트와 주고받는 대화 |

### 1.3 결과 해석의 열쇠 세 가지

LLM 은 입력을 한 번에 읽고(**프리필** → TTFT 에 나타남), 답을 한 토큰씩 쓴다(**디코드** → TPOT 에 나타남). 여기서 세 가지가 나온다. 자세한 원리와 비유: [쉽게 풀어쓴 개념](../docs/쉽게_풀어쓴_개념.md#프리필과-디코드-ttfttpot)

- **배칭은 거의 공짜다.** 동시 사용자를 늘려도 TPOT 는 조금만 늘고 처리량은 사용자 수만큼 는다. ([배칭](../docs/쉽게_풀어쓴_개념.md#배칭))
- **긴 입력은 다른 사람을 잠깐 멈춘다.** 입력이 긴 에이전트 요청이 몰리면 TTFT 가 크게, TPOT 도 조금 는다.
- **접두사 캐시는 같은 앞부분을 다시 계산하지 않는다.** 에이전트는 모든 요청이 같은 시스템 프롬프트로 시작하므로 효과가 크다. 효과는 같은 엔진의 '캐시 끔'과 비교해 확정한다. ([접두사 캐시](../docs/쉽게_풀어쓴_개념.md#접두사-캐시))

### 1.4 굿풋과 목표(SLO)

처리량만 보면 동시 사용자를 늘릴수록 좋아 보이지만, 그만큼 한 사람이 기다리는 시간이 길어진다.
그래서 목표를 정해 두고 그걸 지킨 처리량(굿풋)을 본다. 이 프로젝트의 목표는 **첫 글자 1초 이내, 글자당 50ms 이내**(초당 20토큰, 사람이 읽는 속도보다 빠름).

- 모든 요청이 목표를 지키면 굿풋 = 처리량.
- 동시 사용자를 늘리다 굿풋이 처리량보다 작아지기 시작하는 지점이 "이 서버로 받을 수 있는 사용자 수"의 실제 한계다.

### 1.5 도구 호출 검사

```
[vLLM] 도구 호출: 도구 선택 0.95, 인자까지 0.90, 형식 오류 0, 요청 오류 0
```

20문항(`eval/toolcalls.jsonl`)마다 정답 도구와 인자를 정해 두고 채점한다.

| 칸 | 뜻 |
|---|---|
| 도구 선택 | 맞는 도구를 골랐나. 인사처럼 도구가 필요 없는 질문은 "안 부름"이 정답 |
| 인자까지 | 도구도 맞고 인자(호기, 경보 코드, 연월, 우선순위 등)도 모두 맞은 비율 |
| 형식 오류 | 도구 인자가 JSON 으로 읽히지 않은 횟수. 엔진의 도구 호출 파서 문제일 때가 많다 |
| 요청 오류 | 엔진이 요청 자체를 거절·실패한 횟수 |

같은 모델이라도 엔진마다 모델 출력을 도구 호출 형식으로 바꾸는 파서가 달라서(vLLM `hermes`, SGLang `qwen25`, llama.cpp `--jinja`) 결과가 다를 수 있다.
에이전트에서는 속도보다 이게 먼저다.

## 2. 공정하게 재려고 지킨 것

- 세 엔진 모두 같은 모델 이름·같은 최대 길이(8192)·온도 0·출력 128토큰 고정(`ignore_eos`)·Qwen3 생각 모드 끔.
- 사용자 메시지 앞에 요청마다 다른 꼬리표를 붙인다. 같은 질문이 두 번 뽑혀도 캐시를 공짜로 얻지 않게.
  캐시가 재사용할 수 있는 건 '모든 요청이 공유하는 시스템 프롬프트'와 '같은 대화의 앞 턴'뿐이다.
- 동시 사용자 단계마다 다른 요청 묶음을 쓴다. 앞 단계가 남긴 캐시가 다음 단계를 돕지 않게.
- 3턴 대화는 최소한 동시 사용자 수만큼 만든다. 대화가 모자라면 일부 사용자가 놀아서 처리량이 낮게 나온다.
- 첫 요청 2개는 예열로 빼고 잰다.
- 설정 하나만 바꿔 비교할 때는 두 설정을 **같은 실행 안에서 나란히** 잰다(실행마다 몇 % 흔들리므로). 예: `configs/serving_sglang_graph.yaml`.
- 캐시 효과는 같은 엔진의 '캐시 끔' 프로필(`--no-enable-prefix-caching`, `--disable-radix-cache`)과 비교한다.
- 차이: llama.cpp 는 GGUF 만 읽어서 Q8_0 양자화 모델을 쓴다. 결과에 함께 적는다.

## 3. 실행

노트북(RTX 5070 Laptop 8GB)에는 엔진이 하나씩만 올라간다. `--manage` 가 엔진마다 띄우고 → 재고 → 내린다.

```bash
git pull && pip install -e ".[serving]"
docker compose --profile all down          # 벡터DB 컨테이너를 내려 RAM 확보 (데이터는 남음)

# 1) 동작 확인: 동시 1·4, 요청 8개 (첫 실행은 이미지·모델 내려받기로 오래 걸림)
python scripts/bench_serving.py configs/serving_laptop.yaml --manage --quick

# 2) 본 측정: 동시 1·4·8·16, 단계당 요청 48개
python scripts/bench_serving.py configs/serving_laptop.yaml --manage
cat results/serving_laptop.md
```

한 엔진만: `--only SGLang`. 이미 떠 있는 엔진을 재려면 `--manage` 를 뺀다.

### 3.1 장애 대체 시험

1순위 엔진을 멈췄을 때 게이트웨이가 대체 엔진으로 넘기는지 본다. 8GB GPU 에는 엔진 두 개가 동시에 올라가지 않으므로 **대체 엔진은 CPU 에서 도는 llama.cpp**(`llamacpp-cpu` 프로필)다 — GPU 서버가 한 대뿐인 사내 환경에서 "GPU 엔진이 죽어도 느리게나마 서비스는 이어진다"를 보이는 구성.

```bash
python scripts/failover_test.py      # 5~10분. SGLang(GPU)·llama.cpp(CPU)·LiteLLM 을 함께 띄우고 끝나면 내린다
cat results/failover.md
```

단계: ① 정상 15초 → ② 요청을 계속 보내는 도중 1순위(SGLang) 컨테이너를 멈추고 30초 → ③ 1순위를 다시 띄우고 준비된 뒤 20초.
어느 엔진이 답했는지는 게이트웨이 응답 헤더(`x-litellm-model-api-base`, 없으면 `x-litellm-model-group`)와 llama.cpp 의 처리 토큰 누계 증가, 두 가지로 확인한다.
갑작스러운 고장(프로세스 강제 종료)을 재려면 `FAILOVER_KILL=1 python scripts/failover_test.py` — 두 방식 모두 쟀다(4.3).

## 4. 결과와 해석

### 4.1 동작 확인 (`--quick`: 동시 1·4명, 단계당 요청 8개)

짧은 측정이라 경향만 봤고, 경향은 모두 본 측정(4.2)에서 확인됐다: 접두사 캐시가 에이전트 요청의 첫 글자를 2.3~5배 줄이고(첫 질문 2.3~2.6배, 3턴 대화 약 5배), SGLang 이 vLLM 보다 조금 빠르며, llama.cpp 는 혼자일 때 가장 빠르지만 긴 입력 4명에서 무너진다.
이 단계에서 측정기·설정 실수 세 가지를 찾아 고쳤다 — SGLang 캐시 보고 꺼짐, 3턴 대화 수 부족, 게이트웨이 주소 (문제해결 이력 D11~D13).

### 4.2 본 측정 (동시 1·4·8·16명, 단계당 요청 48개, 도구 호출 20문항, 노트북)

- 엔진 버전: vLLM 0.31.0 · SGLang 0.5.21 · llama.cpp b11371 (Q8_0). 총 요청 약 3,000개, 오류 0.
- 전체 표: [reports/serving_laptop.md](../reports/serving_laptop.md). 아래는 판단에 필요한 줄만 골랐다.
- 목표(SLO): 첫 글자 1초 이내, 글자당 50 ms 이내. "목표 달성"은 그걸 지킨 요청의 비율, "굿풋"은 지킨 요청만 센 초당 처리량.

**① 이 노트북으로 에이전트 사용자를 몇 명까지 받나: 캐시를 켜면 약 8명, 끄면 약 4명**

에이전트 첫 질문(rag) 기준:

| 동시 | vLLM 목표 달성 | vLLM 캐시 끔 | SGLang 목표 달성 | SGLang 캐시 끔 | llama.cpp |
|---|---|---|---|---|---|
| 1 | 100% | 100% | 100% | 100% | 100% |
| 4 | 100% | 100% | 100% | 100% | **31%** |
| 8 | 100% | 92% | 100% | **50%** | 33% |
| 16 | 88% | **10%** | 75% | **10%** | **0%** |

- vLLM·SGLang 은 캐시를 켜면 동시 8명까지 모든 요청이 목표를 지켰고, 16명에서 75~88% 로 내려가기 시작한다. → 이 노트북 GPU 하나로 에이전트 동시 사용자 **약 8명**이 안전선.
- 캐시를 끄면 16명에서 목표 달성 10%, 첫 글자 p95 가 5초를 넘는다. 사실상 서비스 불가.
- 3턴 대화(multiturn)도 같은 모양이다 (캐시 켬 16명 90~92%, 끔 8%).

**② 접두사 캐시: 같은 GPU 로 받을 수 있는 양이 2~3배, 몰릴 때는 14~26배 차이**

| 요청 모양 | 엔진 | 최대 굿풋 캐시 켬 | 최대 굿풋 캐시 끔 | 동시 16 굿풋 켬 / 끔 | 캐시 재사용률 |
|---|---|---|---|---|---|
| rag | vLLM | 3.59 | 1.83 | 3.59 / 0.24 | 66% |
| rag | SGLang | 3.37 | 1.57 | 3.20 / 0.23 | 66% |
| multiturn | vLLM | 4.05 | 1.66 | 4.05 / 0.17 | 84% |
| multiturn | SGLang | 4.49 | 1.48 | 4.49 / 0.17 | 84% |
| chat | vLLM | 8.09 | 7.77 | — | 25% |

- 에이전트 요청은 입력 약 1,600토큰 중 66%(3턴 대화는 84%)를 캐시에서 꺼내 썼다. 그만큼 프리필을 건너뛰어, 받을 수 있는 최대 처리량(최대 굿풋)이 첫 질문 **약 2배**·3턴 대화 **2.4~3배**, 동시 16명일 때는 **14~26배** 차이가 났다.
- 짧은 질문(chat)은 재사용할 앞부분이 짧아 차이가 4% 이내.
- 동작 확인(4.1)의 결론이 본 측정에서 그대로 확인됐다: **에이전트 서빙에서는 접두사 캐시가 엔진 선택보다 큰 변수다.**

**③ vLLM 대 SGLang (기본 설정): 중간 부하에서는 SGLang, 동시 16명에서 SGLang 이 급히 느려짐 → ③-2 에서 원인 해결**

| 요청 모양 | 동시 | vLLM 처리량 | SGLang 처리량 | vLLM TPOT | SGLang TPOT |
|---|---|---|---|---|---|
| rag | 8 | 2.78 | **3.37** (+21%) | 18.9 | 14.9 |
| rag | 16 | 4.10 | 4.26 (+4%) | 25.3 | 23.9 |
| multiturn | 8 | 2.97 | **3.71** (+25%) | 19.0 | 14.7 |
| multiturn | 16 | 4.53 | 4.89 (+8%) | 24.1 | 22.0 |
| chat | 8 | 4.31 | **5.08** (+18%) | 14.0 | 11.9 |
| chat | 16 | **8.09** | 5.86 (−28%) | 14.4 | **20.4** |

- 동시 8명까지는 SGLang 이 처리량 18~25% 높다. 글자 간격이 더 짧다.
- 그런데 동시 16명에서 SGLang 의 글자 간격이 갑자기 11.9 → 20.4 ms 로 뛴다(chat). 캐시를 꺼도 같아서(18.9 ms) 캐시 문제는 아니다.
  **추정:** SGLang 은 GPU 메모리가 작으면 'CUDA 그래프'(디코드 계산을 미리 녹화해 두고 재생하는 최적화, [쉬운 설명](../docs/쉽게_풀어쓴_개념.md#cuda-그래프))를 작은 배치 크기까지만 만든다. 동시 사용자가 그 크기를 넘으면 녹화 없이 계산해 느려진다.
  **확인됨:** SGLang 시작 로그 `Capture target decode CUDA graph ... bs=[1, 2, 4, 8]` — 이 노트북에서는 8명분까지만 만든다(GPU 여유 0.3GB). (문제해결 이력 D14)
- vLLM 은 이런 계단이 없었다(chat 동시 8 → 16 에서 글자 간격 14.0 → 14.4 ms).

**③-2 SGLang 의 CUDA 그래프 상한을 16으로 올리자 (`--cuda-graph-max-bs-decode 16`, 같은 실행에서 기본과 나란히 측정)**

- 동시 1·4·8명 줄은 두 설정이 사실상 같았다(대부분 3% 이내, 동시 1명의 rag·multiturn 만 5~6% — 측정 흔들림 범위). 그래프가 이미 있던 구간이므로 같아야 정상 — 원인을 정확히 짚었다는 대조 확인이다. 전체 표: [reports/serving_sglang_graph.md](../reports/serving_sglang_graph.md)
- 기본 설정 쪽은 본 측정 수치를 다시 재현했다(chat 동시 16 글자 간격: 본 측정 20.4 · 옵션 이름 실수로 16 쪽이 못 뜬 첫 비교 실행 19.9 · 이 비교 20.4 ms).
- 상한을 올린 SGLang 은 동시 16명에서도 vLLM 보다 처리량 12~29%, 굿풋 8~32% 높다. 남은 약점은 에이전트 첫 질문(rag)의 첫 글자 p95(1,067 ms)가 목표 1초를 살짝 넘어 목표 달성률이 vLLM 보다 낮은 것(77% 대 88%) — 긴 프리필이 몰리는 구간이다.
- **결정 (잠정): 게이트웨이 1순위를 SGLang(그래프≤16)으로 바꾼다.** 모든 동시 사용자 구간에서 vLLM 보다 처리량·굿풋이 높고(동시 1명은 양자화한 llama.cpp 가 더 빠르지만 여럿을 못 받는다, ④), 도구 호출 정확도도 셋 중 가장 높았다(⑥).
  잠정인 이유: vLLM 은 다른 실행(본 측정)의 수치와 비교했다. 24GB GPU 에서 두 엔진을 같은 실행으로 다시 재서 확정한다.
- 교훈: 기본 설정 그대로 엔진을 비교하면, 엔진의 실력이 아니라 **그 GPU 에서 엔진이 고른 기본값**을 비교하게 된다. 성능이 특정 지점에서 계단처럼 꺾이면 엔진 시작 로그부터 본다.

- **끊기지 않았다: 요청 62개 모두 성공.** 1순위를 멈추자 게이트웨이가 대체 엔진으로 넘겼고, 1순위가 다시 뜨자 1순위로 돌아왔다.

- **정상 종료라 처리 중이던 요청도 잃지 않았다.** `docker stop` 은 종료 신호를 보내고, SGLang 은 받아 둔 요청을 마저 처리한 뒤(약 14초) 끝났다. 장애 단계의 SGLang 6건이 그것이다.
  갑작스러운 고장도 따로 쟀다 → 아래 '강제 종료' 표.
- **대신 대체 엔진은 매우 느리다.** 16토큰짜리 짧은 답에 p50 11초, p95 42초 — SGLang(0.25초)의 약 40배. CPU 하나로 두 요청을 처리하는 데다, 같은 시각 SGLang 재시작(모델 적재·CUDA 그래프 녹화)이 CPU 를 함께 쓴다.
  보통 길이(128토큰) 답이면 수십 초~분 단위가 된다. **CPU 대체는 '서비스가 끊기지 않는다'까지이지 '같은 품질'이 아니다.**
  → 운영 판단: GPU 서버 한 대 구성에서 CPU 대체는 최후 수단. 실제 서비스라면 GPU 를 두 장(또는 두 대) 두거나, 대체 중에는 에이전트가 "응답이 지연되고 있습니다"를 알리고 답 길이를 줄이게 한다(4~5주차 에이전트 설계에 반영).

## 5. 다음: 24GB GPU 본 측정 계획

노트북(8GB)은 KV 캐시 자리가 2.4GiB 뿐이라 동시 16명이 한계다. 리포트용 최종 수치는 24GB 이상 GPU(L4 · RTX 4090 · A100 등)를 몇 시간 빌려 잰다. 스크립트는 그대로 쓴다.

에이전트 부하는 채팅과 세 가지가 다르다 — 매 호출마다 긴 앞부분(시스템 프롬프트·도구 정의)이 반복되고, 출력은 짧은 도구 호출 JSON 이 많고, 각 단계가 앞 단계 응답을 기다린다.
그래서 첫 글자 시간, 캐시 효과, **과업 전체 시간**이 일반 채팅 벤치마크보다 중요하다. ([쉬운 설명](../docs/쉽게_풀어쓴_개념.md#에이전트-부하의-모양))

**원칙**
1. 내 에이전트의 실제 토큰 분포(공통 앞부분 길이, 단계마다 새로 붙는 길이, 출력 길이, 과업당 호출 수)부터 재고, 그 숫자로 합성 부하를 맞춘다.
2. 한 실험에 변수는 하나. GPU·모델·정밀도·최대 길이·클라이언트·데이터·시드 고정.
3. 두 엔진을 같은 클라이언트로 잰다(이 저장소의 측정기, 교차 확인용으로 `vllm bench serve`).
4. 메모리 조건을 맞춘다. 옵션 이름이 엔진마다 달라서(vLLM `--gpu-memory-utilization`, SGLang `--mem-fraction-static`) 시작 로그의 KV 캐시 용량(토큰 수)을 비슷하게 맞춘다.
5. 예열 후 3회 반복, 버전·드라이버·플래그와 원본 JSON 을 남긴다. 비교할 둘은 같은 실행 안에서.

**실험**
| # | 질문 | 방법 |
|---|---|---|
| 1 | GPU 한 장으로 몇 명까지 받나 | 동시 1 → 64, 처리량-지연 곡선이 꺾이는 지점과 굿풋. 대기 요청·선점이 늘기 시작하는 곳이 한계 |
| 2 | 접두사 캐시로 얼마나 버나 | 캐시 켬/끔, TTFT 와 적중률 |
| 3 | 양자화로 무엇을 얻고 잃나 | BF16 · FP8 · AWQ, KV 캐시 FP8. 이득은 속도보다 **동시 처리 수**(가중치가 준 만큼 KV 캐시 자리가 는다). 반드시 도구 호출 정확도와 함께 본다 |
| 4 | vLLM 대 SGLang | 1~3 을 두 엔진에서 같은 실행으로 (노트북의 잠정 결정 확정) |
| 5 | 사용자 N명이면 과업 하나에 몇 초 | 에이전트 평가셋을 동시 N개로 → 과업 시간 p95, 분당 과업 수, 성공률 |
| 선택 | 구조화 출력, speculative decoding | 도구 호출 JSON 강제의 지연 비용·형식 오류율 / 동시 요청이 적을 때의 이득 |

모델은 Qwen3-8B(24GB 기준)와 노트북과 같은 1.7B 를 함께 재서 "8GB 노트북 대 24GB 서버"를 한 줄로 비교한다(폐쇄망 소형 장비 이야기와 연결).

**흔한 함정**
- Qwen3 의 생각(thinking) 모드는 기본으로 켜져 있어 출력이 길어진다. 두 엔진 모두 같은 설정으로.
- 합성 부하(출력 길이 고정 `ignore_eos`)와 실제 부하를 한 표에서 비교하지 않는다.
- 양자화를 속도만 보고 판단하지 않는다.
- 엔진의 기본값이 GPU 크기에 따라 달라진다(이 노트북의 SGLang CUDA 그래프 상한 8, 문제해결 이력 D14). 시작 로그를 남긴다.

참고: [vllm bench serve](https://docs.vllm.ai/en/latest/cli/bench/serve.html) · [vLLM Production Metrics](https://docs.vllm.ai/en/latest/usage/metrics.html)

## 6. 문제가 생기면

- 엔진 로그: `docker compose -f serving/compose.yml --profile sglang logs --tail 50`
- SGLang 도구 호출 파서 이름이 버전에 따라 다르다: `SGLANG_TOOL_PARSER=qwen python scripts/bench_serving.py ...`
- SGLang 이 Blackwell 노트북 GPU 에서 커널 오류를 내면: `SGLANG_EXTRA="--attention-backend triton" ...`
- 이미지 버전 고정: `VLLM_IMAGE=vllm/vllm-openai:v0.x.y` 처럼 환경 변수로 바꾼다.
- 엔진이 안 뜰 때 준비 대기·로그 보는 법: [docs/노트북_환경_구축.md](../docs/노트북_환경_구축.md#6-엔진이-안-뜰-때-직접-보는-법)
