## 1. 결과 읽는 법

### 1.1 출력 한 줄

측정기는 "엔진 × 요청 모양 × 동시 사용자 수" 조합마다 아래와 같은 줄을 하나씩 찍는다. 모든 줄의 칸 구성이 같다.

```
[SGLang] rag  동시 4  2.11 req/s  271 tok/s  TTFT p50 236ms  TPOT p50 13.3ms  굿풋 2.11  캐시 —  오류 0
```

| 칸 | 뜻 | 쉬운 말 |
|---|---|---|
| `[SGLang]` | 잰 엔진 | |
| `rag` | 요청 모양 (1.2) | 어떤 종류의 질문을 보냈나 |
| `동시 4` | 동시 사용자 수 | 4명이 동시에, 답을 받자마자 다음 질문을 계속 보낸다 |
| `req/s` | 초당 처리한 요청 수 | 서버가 1초에 답을 몇 개 끝내나 |
| `tok/s` | 초당 만든 출력 토큰 수 | 서버 전체가 1초에 만드는 글자량. 토큰은 단어 조각으로, 한국어는 대략 1~2글자 |
| `TTFT` | Time To First Token | 질문을 보내고 **첫 글자가 나올 때까지** 걸린 시간 |
| `TPOT` | Time Per Output Token | 첫 글자 이후 **글자 하나가 나오는 간격**. 11ms 면 사용자 한 명당 초당 약 89토큰 |
| `p50` / `p95` | 중앙값 / 95번째 백분위 | 요청 100개를 줄 세웠을 때 50번째·95번째 값. p95 는 "운 나쁜 사용자"가 겪는 시간 |
| `굿풋` | goodput | 목표(SLO)를 **지킨 요청만** 센 초당 처리량 (1.4) |
| `캐시` | 캐시 재사용률 | 입력 토큰 중 다시 계산하지 않고 기억해 둔 걸 꺼내 쓴 비율. 엔진이 알려 줄 때만 숫자가 나오고, 아니면 `—` |
| `오류` | 실패한 요청 수 | |

결과 파일(`results/serving_*.md`)의 표도 같은 칸에 TTFT·TPOT 의 p95, 목표 달성 비율을 더한 것이다.

### 1.2 요청 모양 세 가지

모두 이 저장소의 실제 문서·질문으로 만든다 (`src/onprem_agent/serving/workloads.py`). 답변은 모두 128토큰으로 길이를 고정한다.

| 이름 | 보낸 내용 | 입력 길이 | 실제로 비슷한 것 |
|---|---|---|---|
| chat | "LVL-06 경보는 뭐예요?" 같은 짧은 질문 하나 | 짧음 | 일반 챗봇 |
| rag | 에이전트 지침·도구 설명(약 2,500자, **모든 요청이 같음**) + 검색 문서 3개 + 질문 | 김 | 에이전트의 첫 질문 |
| multiturn | rag 로 시작해 같은 대화에서 후속 질문 2개 | 턴마다 길어짐 | 에이전트와 주고받는 대화 |

### 1.3 LLM 이 답을 만드는 두 단계 — 결과 해석의 열쇠

1. **프리필(prefill) = 입력 읽기.** 질문 전체를 한 번에 읽는다. 입력이 길수록 오래 걸린다 → **TTFT** 에 나타난다.
2. **디코드(decode) = 한 글자씩 쓰기.** 답을 한 토큰씩 만든다. 토큰 하나를 만들 때마다 모델 가중치 전체(1.7B 모델이면 약 3.4GB)를 GPU 메모리에서 읽는다 → **TPOT** 에 나타난다.

여기서 나오는 세 가지 성질:

- **배칭(batching)은 거의 공짜다.** 디코드는 계산보다 '메모리 읽기'가 병목이라, 가중치를 한 번 읽을 때 여러 사용자의 다음 토큰을 같이 만들어도 시간이 거의 그대로다.
  그래서 동시 사용자를 늘리면 TPOT 는 조금만 늘고 처리량은 사용자 수만큼 는다. vLLM·SGLang 같은 서빙 엔진이 존재하는 가장 큰 이유.
- **긴 입력은 다른 사람을 잠깐 멈춘다.** 새 요청의 프리필이 끼어드는 동안 다른 사용자의 디코드가 밀린다.
  그래서 입력이 긴 에이전트 요청(rag)은 동시 사용자가 늘면 TTFT 가 크게 늘고 TPOT 도 조금 는다.
- **접두사 캐시(prefix cache)는 같은 앞부분을 다시 계산하지 않는다.** 앞부분이 같은 요청이 오면 이전 계산 결과(KV 캐시)를 꺼내 쓰고 새 부분만 프리필한다.
  vLLM 은 automatic prefix caching, SGLang 은 radix cache 라고 부른다. 에이전트는 모든 요청이 같은 시스템 프롬프트로 시작하고, 대화가 이어지면 앞 대화 전체가 같으므로 효과가 크다.
  효과는 같은 엔진의 '캐시 끔' 결과와 비교해 확정한다.

### 1.4 굿풋과 목표(SLO)

처리량만 보면 동시 사용자를 늘릴수록 좋아 보이지만, 그만큼 한 사람이 기다리는 시간이 길어진다.
그래서 목표를 정해 두고 그걸 지킨 처리량(굿풋)을 본다. 이 프로젝트의 목표는 **첫 글자 1초 이내, 글자당 50ms 이내**(초당 20토큰, 사람이 읽는 속도보다 빠름).

- 모든 요청이 목표를 지키면 굿풋 = 처리량.
- 동시 사용자를 늘리다 굿풋이 처리량보다 작아지기 시작하는 지점이 "이 서버로 받을 수 있는 사용자 수"의 실제 한계다.

### 1.5 도구 호출 검사

```
[vLLM] 도구 호출: 도구 선택 0.95, 인자까지 0.85, 형식 오류 0, 요청 오류 0
```

20문항(`eval/toolcalls.jsonl`)마다 정답 도구와 인자를 정해 두고 채점한다.

| 칸 | 뜻 |
|---|---|
| 도구 선택 | 맞는 도구를 골랐나. 인사처럼 도구가 필요 없는 질문은 "안 부름"이 정답 |
| 인자까지 | 도구도 맞고 인자(호기, 경보 코드, 연월, 우선순위 등)도 모두 맞은 비율 |
| 형식 오류 | 도구 인자가 JSON 으로 읽히지 않은 횟수. 엔진의 도구 호출 파서 문제일 때가 많다 |
| 요청 오류 | 엔진이 요청 자체를 거절·실패한 횟수 |

같은 모델이라도 엔진마다 모델 출력을 도구 호출 형식으로 바꾸는 파서가 달라서(vLLM `hermes`, SGLang `qwen25`, llama.cpp `--jinja`) 결과가 다를 수 있다.
에이전트에서는 속도보다 이게 먼저다.

## 2. 공정하게 재려고 지킨 것

- 세 엔진 모두 같은 모델 이름·같은 최대 길이(8192)·온도 0·출력 128토큰 고정(`ignore_eos`)·Qwen3 생각 모드 끔.
- 사용자 메시지 앞에 요청마다 다른 꼬리표를 붙인다. 같은 질문이 두 번 뽑혀도 캐시를 공짜로 얻지 않게.
  캐시가 재사용할 수 있는 건 '모든 요청이 공유하는 시스템 프롬프트'와 '같은 대화의 앞 턴'뿐이다.
- 동시 사용자 단계마다 다른 요청 묶음을 쓴다. 앞 단계가 남긴 캐시가 다음 단계를 돕지 않게.
- 3턴 대화는 최소한 동시 사용자 수만큼 만든다. 대화가 모자라면 일부 사용자가 놀아서 처리량이 낮게 나온다.
- 첫 요청 2개는 예열로 빼고 잰다.
- 캐시 효과는 같은 엔진의 '캐시 끔' 프로필(`--no-enable-prefix-caching`, `--disable-radix-cache`)과 비교한다.
- 차이: llama.cpp 는 GGUF 만 읽어서 Q8_0 양자화 모델을 쓴다. 결과에 함께 적는다.

노트북(RTX 5070 Laptop 8GB)에는 엔진이 하나씩만 올라간다. `--manage` 가 엔진마다 띄우고 → 재고 → 내린다.

```bash
git pull && pip install -e ".[serving]"

# 1) 동작 확인: 동시 1·4, 요청 8개 (첫 실행은 이미지·모델 내려받기로 오래 걸림)

python scripts/bench_serving.py configs/serving_laptop.yaml --manage
cat results/serving_laptop.md
```

한 엔진만: `--only SGLang`. 이미 떠 있는 엔진을 재려면 `--manage` 를 뺀다.

## 4. 결과와 해석

### 4.1 동작 확인 (`--quick`: 동시 1·4명, 단계당 요청 8개, 노트북)

요청 수가 적은 짧은 측정이라 **경향만** 본다. 수치 비교는 4.2 본 측정으로 한다.
아래 표는 결과 파일(`results/serving_laptop_quick.md`)에서 골라 옮겼다. 단위: TTFT·TPOT 는 ms(p50), 처리량은 요청/s.

**① 접두사 캐시: 에이전트 요청에서 첫 글자가 3~5배 빨라진다**

| 요청 모양 | 엔진 | 캐시 켬 TTFT | 캐시 끔 TTFT | 캐시 켬 처리량 (동시 4) | 캐시 끔 처리량 (동시 4) | 캐시 재사용률 (vLLM) |
|---|---|---|---|---|---|---|
| chat | vLLM | 27 | 28 | 2.28 | 2.24 | 23% |
| rag | vLLM | 70 | 199 | 1.84 | 1.45 | 78% |
| rag | SGLang | 78 | 210 | 2.11 | 1.60 | — |
| multiturn | vLLM | 46 | 240 | — | — | 94% |
| multiturn | SGLang | 48 | 248 | — | — | — |

- 짧은 질문(chat)은 공유하는 앞부분이 짧아 켜나 끄나 같다.
- 에이전트 요청(rag)은 입력 1,612토큰 중 약 78%(시스템 프롬프트·도구 설명)가 모든 요청에서 같다. 캐시를 켜면 그만큼 프리필을 건너뛰어 첫 글자가 약 2.8배 빨라지고, 동시 4명 처리량이 vLLM 27%·SGLang 32% 늘었다.
- 3턴 대화는 앞 대화 전체가 재사용되어 재사용률 94%, 첫 글자 약 5배 빠름.
- **결론: 에이전트 서빙에서는 접두사 캐시가 엔진 선택보다 큰 변수다.** 그리고 그 효과를 살리려면 시스템 프롬프트·도구 설명을 요청마다 바꾸지 말고 맨 앞에 고정해야 한다(5~6주차 에이전트 설계에 반영).
- multiturn 동시 4 줄은 측정기 실수(대화가 2개뿐이라 2명이 놀았음, 문제해결 이력 D12)로 처리량을 비교에서 뺐다.

**② 엔진 비교: SGLang 이 vLLM 보다 조금 빠르다 (이 노트북·이 버전 기준)**

| 요청 모양 | 동시 | vLLM 처리량 | SGLang 처리량 | vLLM TPOT | SGLang TPOT |
|---|---|---|---|---|---|
| chat | 4 | 2.28 | 2.66 (+17%) | 13.4 | 11.5 |
| rag | 4 | 1.84 | 2.11 (+15%) | 15.5 | 13.3 |

- 차이는 주로 글자 간격(TPOT)에서 난다. 두 엔진 모두 같은 BF16 가중치이므로, 디코드 커널·CUDA 그래프 같은 엔진 구현 차이로 본다.
- 요청 8개짜리 1회 측정이고 두 엔진의 버전·기본 설정이 다르다. 결론은 본 측정(요청 48개, 동시 16까지)과 24GB GPU 재측정으로 확인한다.

**③ llama.cpp: 혼자 쓰면 가장 빠르고, 여럿이 쓰면 가장 먼저 무너진다**

| 요청 모양 | 동시 | llama.cpp 처리량 | SGLang 처리량 | llama.cpp TPOT | llama.cpp TTFT |
|---|---|---|---|---|---|
| chat | 1 | 0.95 | 0.66 | 7.4 | 60 |
| chat | 4 | 2.72 | 2.66 | 10.4 | 146 |
| rag | 1 | 0.88 | 0.64 | 8.1 | 88 |
| rag | 4 | **1.04** | 2.11 | **26.3** | **546** |

- 혼자 쓸 때 글자 간격이 7~8ms 로 가장 빠르다. 엔진이 좋아서라기보다 **Q8_0 양자화로 가중치가 절반 크기**라서다. 디코드는 메모리 읽기가 병목이므로(1.3) 읽을 바이트가 절반이면 빨라진다. 양자화의 효과이지 엔진 비교가 아니다.
- 긴 입력을 4명이 동시에 보내면 처리량이 1명일 때와 거의 같고(0.88 → 1.04), 글자 간격은 3배(26ms), 첫 글자는 0.5초를 넘는다. 짧은 질문(chat)에서는 4명도 잘 받는다.
  긴 프리필을 여러 사용자의 디코드와 섞어 처리하는 능력(vLLM·SGLang 의 연속 배칭·청크 프리필)이 약해, 에이전트처럼 입력이 긴 요청이 몰리면 버티지 못한다.
- **결론: llama.cpp 는 1인용·현장 단말·GPU 없는 환경용, 여러 사용자를 받는 에이전트 서버는 vLLM·SGLang.** 이 프로젝트의 게이트웨이도 llama.cpp 를 1순위가 아니라 장애 시 대체 엔진으로 둔다.

**④ 도구 호출 (빠른 측정이라 5문항만)**

| 엔진 | 도구 선택 | 인자까지 | 형식 오류 | 지연 p50 |
|---|---|---|---|---|
| vLLM | 0.80 | 0.80 | 0 | 372 ms |
| SGLang | 1.00 | 1.00 | 0 | 294 ms |
| llama.cpp | 0.80 | 0.80 | 0 | 246 ms |

- 세 엔진 모두 도구 인자를 JSON 으로 제대로 냈다(형식 오류 0). 파서 설정은 맞다.
- vLLM·llama.cpp 가 틀린 문항은 같다: `tc03` "설비 점검 들어가기 전에 지켜야 할 안전 수칙이 뭐죠?"에서 매뉴얼 검색 도구를 부르지 않고 바로 답했다. 형식 문제가 아니라 모델의 판단이다.
  같은 모델·온도 0 인데 SGLang 만 도구를 부른 건 엔진마다 계산 순서가 달라 생기는 미세한 수치 차이로 본다. 5문항으로는 결론을 내지 않는다 — 20문항 본 측정에서 본다.

**⑤ 실패: LiteLLM → vLLM 요청 16개가 모두 실패 (측정기·설정 실수)**

- 원인: 게이트웨이 컨테이너가 엔진을 `host.docker.internal:8000` 으로 찾게 했는데, 엔진 포트는 호스트의 `127.0.0.1` 에만 열려 있어 컨테이너에서 닿지 않았다.
- 해결: 같은 compose 네트워크의 서비스 이름(`vllm:8000`)으로 붙게 고쳤다. 결과 파일에 오류 메시지 예시도 찍게 했다. (문제해결 이력 D13)

**모든 요청이 목표(첫 글자 1초, 글자당 50ms)를 지켰다.** 동시 4명은 세 엔진 모두에게 여유롭다. 한계는 본 측정(동시 8·16)에서 본다.

### 4.2 본 측정 (동시 1·4·8·16명, 단계당 요청 48개, 도구 호출 20문항, 노트북)

- 엔진 버전: vLLM 0.31.0 · SGLang 0.5.21 · llama.cpp b11371 (Q8_0). 총 요청 약 3,000개, 오류 0.
- 전체 표: [reports/serving_laptop.md](../reports/serving_laptop.md). 아래는 판단에 필요한 줄만 골랐다.
- 목표(SLO): 첫 글자 1초 이내, 글자당 50 ms 이내. "목표 달성"은 그걸 지킨 요청의 비율, "굿풋"은 지킨 요청만 센 초당 처리량.

**① 이 노트북으로 에이전트 사용자를 몇 명까지 받나: 캐시를 켜면 약 8명, 끄면 약 4명**

에이전트 첫 질문(rag) 기준:

| 동시 | vLLM 목표 달성 | vLLM 캐시 끔 | SGLang 목표 달성 | SGLang 캐시 끔 | llama.cpp |
|---|---|---|---|---|---|
| 1 | 100% | 100% | 100% | 100% | 100% |
| 4 | 100% | 100% | 100% | 100% | **31%** |
| 8 | 100% | 92% | 100% | **50%** | 33% |
| 16 | 88% | **10%** | 75% | **10%** | **0%** |

- vLLM·SGLang 은 캐시를 켜면 동시 8명까지 모든 요청이 목표를 지켰고, 16명에서 75~88% 로 내려가기 시작한다. → 이 노트북 GPU 하나로 에이전트 동시 사용자 **약 8명**이 안전선.
- 캐시를 끄면 16명에서 목표 달성 10%, 첫 글자 p95 가 5초를 넘는다. 사실상 서비스 불가.
- 3턴 대화(multiturn)도 같은 모양이다 (캐시 켬 16명 90~92%, 끔 8%).

**② 접두사 캐시: 같은 GPU 로 받을 수 있는 양이 2배, 몰릴 때는 15배 차이**

| 요청 모양 | 엔진 | 최대 굿풋 캐시 켬 | 최대 굿풋 캐시 끔 | 동시 16 굿풋 켬 / 끔 | 캐시 재사용률 |
|---|---|---|---|---|---|
| rag | vLLM | 3.59 | 1.83 | 3.59 / 0.24 | 66% |
| rag | SGLang | 3.37 | 1.57 | 3.20 / 0.23 | 66% |
| multiturn | vLLM | 4.05 | 1.66 | 4.05 / 0.17 | 84% |
| multiturn | SGLang | 4.49 | 1.48 | 4.49 / 0.17 | 84% |
| chat | vLLM | 8.09 | 7.77 | — | 25% |

- 에이전트 요청은 입력 약 1,600토큰 중 66%(3턴 대화는 84%)를 캐시에서 꺼내 썼다. 그만큼 프리필을 건너뛰어, 받을 수 있는 최대 처리량이 **약 2배**, 동시 16명일 때는 **약 15배** 차이가 났다.
- 짧은 질문(chat)은 재사용할 앞부분이 짧아 차이가 4% 이내.
- 동작 확인(4.1)의 결론이 본 측정에서 그대로 확인됐다: **에이전트 서빙에서는 접두사 캐시가 엔진 선택보다 큰 변수다.**

**③ vLLM 대 SGLang: 중간 부하에서는 SGLang, 짧은 요청이 많이 몰리면 vLLM**

| 요청 모양 | 동시 | vLLM 처리량 | SGLang 처리량 | vLLM TPOT | SGLang TPOT |
|---|---|---|---|---|---|
| rag | 8 | 2.78 | **3.37** (+21%) | 18.9 | 14.9 |
| rag | 16 | 4.10 | 4.26 (+4%) | 25.3 | 23.9 |
| multiturn | 8 | 2.97 | **3.71** (+25%) | 19.0 | 14.7 |
| multiturn | 16 | 4.53 | 4.89 (+8%) | 24.1 | 22.0 |
| chat | 8 | 4.31 | **5.08** (+18%) | 14.0 | 11.9 |
| chat | 16 | **8.09** | 5.86 (−28%) | 14.4 | **20.4** |

- 동시 8명까지는 SGLang 이 처리량 18~25% 높다. 글자 간격이 더 짧다.
- 그런데 동시 16명에서 SGLang 의 글자 간격이 갑자기 11.9 → 20.4 ms 로 뛴다(chat). 캐시를 꺼도 같아서(18.9 ms) 캐시 문제는 아니다.
  **추정:** SGLang 은 GPU 메모리가 작으면 'CUDA 그래프'(디코드 계산을 미리 녹화해 두고 재생하는 최적화)를 작은 배치 크기까지만 만든다. 동시 사용자가 그 크기를 넘으면 녹화 없이 계산해 느려진다.
  확인 방법: `curl localhost:30000/get_server_info` 의 `cuda_graph_max_bs` 값을 보고, `SGLANG_EXTRA="--cuda-graph-max-bs 16"` 으로 다시 잰다. (아직 확인 전)
- 동시 16명에서 SGLang 은 첫 글자 p95 가 길어 목표 달성이 vLLM 보다 낮다(rag 75% 대 88%).
- **결정 (잠정): 게이트웨이 1순위는 vLLM 유지.** 받을 수 있는 최대 인원 근처(동시 16)에서 목표 달성률이 더 높고, 짧은 요청이 몰릴 때 확실히 강하다.
  SGLang 은 중간 부하에서 더 빠르므로, CUDA 그래프 가설을 확인하고 24GB GPU 에서 다시 재서 최종 결정한다.

**④ llama.cpp: 혼자 쓸 때만**

| 요청 모양 | 동시 | 처리량 | TTFT p50 | TPOT p50 | 목표 달성 |
|---|---|---|---|---|---|
| chat | 1 | **1.01** (셋 중 최고) | 48 | **7.4** | 100% |
| chat | 16 | 3.35 | 2,857 | 14.4 | 17% |
| rag | 1 | 0.90 (셋 중 최고) | 69 | 8.0 | 100% |
| rag | 4 | 1.15 | **1,987** | 12.5 | **31%** |

- 혼자 쓸 때 가장 빠르다. Q8_0 양자화로 가중치가 절반이라 디코드가 빠른 것(1.3절) — 엔진보다 양자화의 효과.
- 에이전트 요청은 동시 4명부터 첫 글자가 2초 가까이 걸려 목표 달성 31%. 동시 16명이면 짧은 질문도 첫 글자 약 3초.
  여러 사용자의 긴 입력과 글자 생성을 섞어 처리하는 능력이 vLLM·SGLang 보다 약하다. 결과의 흔들림도 크다(동작 확인에서 rag 동시 4 의 첫 글자는 546 ms 였다).
- **결정: llama.cpp 는 1인용·현장 단말·장애 시 대체 엔진으로만 쓴다.** 게이트웨이 설정(`agent-llm-backup`)과 일치.

- 그 대가로 에이전트 코드가 엔진 주소를 몰라도 되고, 엔진 교체·장애 시 대체·요청 기록을 한곳에서 한다. **비용 대비 가치가 있다 → 게이트웨이 유지.**
- 장애 시 대체(vLLM 을 끄면 llama.cpp 로 넘어가는지)는 아직 시험하지 않았다. 다음 단계.

**⑥ 도구 호출 (20문항): 엔진보다 모델 크기가 문제**

| SGLang | **1.00** | **0.95** | 0 | 522 ms |

- 세 엔진 모두 형식 오류 0. 엔진별 도구 호출 파서 설정은 모두 맞다.
- 세 엔진이 **똑같이** 틀린 문항: `tc12` "2호기 CRB-01 센서 점검 요청 등록해줘. **급하지 않아요.**" → 우선순위를 `low` 가 아니라 `normal` 로 넣었다.
  도구 설명에 "급하지 않으면 low"라고 적어 두었는데도 놓쳤다. 엔진과 상관없는 **1.7B 모델의 한계**다.
- vLLM·llama.cpp 는 `tc03`(안전 수칙 질문)에서 매뉴얼 검색 없이 바로 답했다. SGLang 만 검색 도구를 불렀다. 같은 모델·온도 0 인데 엔진마다 계산 순서가 달라 생기는 미세한 수치 차이로 본다.
- **다음 단계:** 에이전트(5~6주차)에는 1.7B 가 아니라 더 큰 모델(Qwen3-4B·8B)을 쓰고, 이 20문항으로 모델 크기별 정확도를 잰다. 4B 는 노트북 8GB 에 양자화로 올릴 수 있다.

## 5. 문제가 생기면

- 엔진 로그: `docker compose -f serving/compose.yml --profile sglang logs --tail 50`
- SGLang 도구 호출 파서 이름이 버전에 따라 다르다: `SGLANG_TOOL_PARSER=qwen python scripts/bench_serving.py ...`
- SGLang 이 Blackwell 노트북 GPU 에서 커널 오류를 내면: `SGLANG_EXTRA="--attention-backend triton" ...`
- 이미지 버전 고정: `VLLM_IMAGE=vllm/vllm-openai:v0.x.y` 처럼 환경 변수로 바꾼다.
- 그 밖의 문제와 해결 과정: [docs/문제해결_이력.md](../docs/문제해결_이력.md)
